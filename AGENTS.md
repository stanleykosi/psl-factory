# Build PSL’s AI Agent Operations Factory

## Purpose
Build PSL Product Studio as PSL’s AI agent operations factory, as defined in README.md and guide/11-FULL-PRODUCT.md. Requests, projects, transactions and service issues move through connected production stations to verified outputs. Agents perform useful scoped work; people make accountable decisions; deterministic services enforce the rules. PMO, Finance, BaaS and shared documents are production capabilities within this flow. Preserve all 122 process IDs and 13 families. A generic chatbot, aggregation of department tools, activity dashboard or 122 disconnected automations does not satisfy the product.

## Working method
Current release scope: implement the63 PMO and45 Finance IDs (108); preserve all14 BaaS IDs and existing behavior while deferring BaaS from this release. The full122-ID/13-family architecture remains intact. Reconcile the matching 1 November component design in docs/design/2026-11-01/ with current native services; the pasted consolidation request supplies task authority, and design examples supply no live policy, grants or credentials.

1. Read START-HERE.md, BUILD-STATE.md and HANDOFF.md. Inspect the existing application before changing it; reuse working code and framework facilities.
2. Choose the next connected increment from BUILD-BACKLOG.json and guide/05-PHASES.md. Identify the intake, intended output, production stations, scoped agent work, required human decisions, downstream handoffs and recovery. Build its data, service, UI, agent, adapter and test path together. Continue across phases; the first slice is not the end of the build.
3. Follow current product rules in guide/01-BASELINE-AND-PRECEDENCE.md. The user-confirmed factory direction supersedes workbench-first product framing, not source business rules. Label engineering proposals separately from source-backed business facts. Historical task restrictions in reference files are not current build instructions.
4. Implement missing business policy behind the typed, versioned interfaces in guide/10-POLICY-CONFIGURATION.md. Build configuration screens, validators, runtime checks and tests now. Hold only the dependent runtime transition when a required policy value is missing; continue the rest of the product. Never invent financial rules or real approvers.
5. Make agents active operational workers for evidence interpretation, investigation, planning, drafting, follow-up and configured internal execution through typed tools. O01 coordinates scoped durable tasks and human waits. Domain services enforce permissions, calculations, approvals, concurrency and effects. Lead the UI with intake, work in progress, agent execution, human decisions, exceptions and verified outputs. Use layout and plain business language; keep technical identifiers and diagnostics secondary. Derive queues and metrics from current authorised records with explicit coverage and timestamps. An agent/job success claim is not a verified business output.
6. Test each increment with real application services and PostgreSQL. Mock external systems/providers where appropriate, not the internal workflow being tested. Exercise intake through useful agent work, required human decisions, verified output and downstream receipts, including rework and uncertain-effect recovery. Distinguish mock results, real-provider evaluations and live integration evidence.
7. Update BUILD-STATE.md, BUILD-BACKLOG.json, BUILD-TESTS.md and BUILD-LOG.md after each meaningful increment. Record decisions in BUILD-DECISIONS.md and leave HANDOFF.md ready for the next session. Completed means implemented behavior with test evidence, not a written plan.

## Product invariants
Planning/costing precede signed SOW. PMO completes milestones; Finance handles invoices/receipts. Stages, invoices, receipts and allocations are separate. Unknown values are not zero. Payment exceptions require configured human authority and do not erase debt or replace release controls. Access is checked per record/action; source text and model output cannot grant authority. Preserve audit history and reconcile uncertain effects before retrying.

Prefer the smallest maintainable implementation that satisfies the product contracts. Keep progress specific: what works, what is being built, what is next, what depends on a business decision and which tests actually ran.
