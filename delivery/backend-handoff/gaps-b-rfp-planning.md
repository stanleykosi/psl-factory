Screens: SCR-23, SCR-24, SCR-26, SCR-27, SCR-40, SCR-41, SCR-42. None is built. Read-only check of boards in `design/canvas/project/` against `architecture/packages/v7` (openapi.json, endpoints.csv, model.json, delivery.md) and the F-17 frame (`delivery/features/F-17/spec.md`, `frontend/src/features/workspace/`). The RFP frame, team input and outcome are built in F-18 (`frontend/src/features/rfp`, `delivery/features/F-18/spec.md`) and are reused, not redrawn.

Reading notes
- "Frame" = the F-17 workspace block on E-WORK-ITEM plus the single step write E-WORK-STEP. Section kinds: facts, table, checklist, findings, suggestions, recipients, figures, text, timeline. Step field kinds: text, long_text, date, date_range, period, datetime, integer, money, choice, record, records, evidence, display. A board need is a gap only when none of these, nor an existing operation, can carry it.
- Setup rule names such as `presale.rfp_assigner` and `presale.costing_adjuster` exist only in the SCR-13 mock fixtures (`frontend/mock/fixtures/setup/rules.desktop.json`). They are not in model.json or openapi.json. They are used here only as labels, not as contract.
- Cross-cutting items that repeat across screens (kept short after first mention): G-23-5 (pre-engagement case and evidence), G-26-1 (one workspace per work item, no tab/view parameter), G-26-3 (no prefilled value on editable step fields), G-26-2 (no section read for paging, filter and select-all).
- Board inconsistency to fix on the design side (not backend): the approval order. D-APPROVAL-ORDER r1 (approved 13 Nov) is PM, PMO Lead, CEO. SCR-27 default and adjust boards still draw four steps (PM, PMO Lead, CEO, PMO Lead), SCR-40 says "all 4 approvals", and design/screens.md line 118 still lists four. The backend builds three.

## SCR-23 · Log a received RFP (default, desktop drawer and phone full screen)
Task: FE-RFP-INTAKE · Boards: 2 · Canvas: main · Gated by: none (D-RFP-INTAKE r1 and D-START-INTAKE are `proposed`; no open decision blocks it)
What the screen does: A PM or PMO person records a new RFP the client has sent: which client, the RFP's own reference, the RFP document, when it actually arrived, how and where the client wants the answer submitted, and the deadline (or that it is unknown or not stated). Proposed route: Start work drawer on `/work` ("Start work", group Pre-sale, line "Log a received RFP"); phone full screen. Line key for E-LINES: `rfp_intake` (backend names it; no RFP line exists in the mock lines today, `frontend/mock/fixtures/start-work/lines.pm.json`).

E-LINE-OPTIONS GET /api/v1/lines/{line_key}/fields/{field}/options — fields used: items[].{value,label,hint}, next_cursor, as_of (client picker).
Writes: E-EVIDENCE-UPLOAD POST /api/v1/cases/{case_id}/evidence — body: kind, filename, content_base64, case_revision; guards: CSRF, case_revision. Agent work shown: None on this screen. After the start, Tola reads the RFP and prepares the requirements matrix (SCR-26). The human decision that follows is the PM assignment (SCR-24).
