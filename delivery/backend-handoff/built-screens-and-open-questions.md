### 1.2 Behaviour the backend must honour, per feature

Rules that apply to every built write (from the shared client `frontend/src/api/client.ts` and `errors.ts`):
- CSRF: every POST and PUT carries `X-CSRFToken` taken from `/me` `csrf_token`, kept in memory. A missing or wrong token must fail with 403 (the mock uses code `csrf_failed`) and write nothing.
- Error mapping: 401 signed-out view (with the page as `next`), 403 and 404 both show a "no access" view that names nothing about the record, 409 = stale, 422 = invalid, 5xx and network failure = **uncertain effect**.
- One write at a time per page, a synchronous double-press guard, and **no automatic retry of any write, ever**. After a 5xx or network failure the page re-reads once (a GET) and does not resend.
- Shared rules: unknown is not zero (an unknown amount is `unknown: true` with no `amount`; a known `"0.00"` is shown as 0.00); restricted values are hidden by the backend, and the frontend also hides them if sent.
- The shared `call()` drops the `fields[]` of a 422. F-17, F-19 and F-20 read it from the raw reply. Operations that declare `fields` in v7: E-WORK-START, E-WORK-STEP, E-WORK-ASSIGN, E-PERSON-ROLES, E-INVITE, E-DEACTIVATE, E-TEMPLATE-VERSION, E-RECEIPT, E-CLIENT-CONTACT. All other writes return only `code` and `message`, so the frontend reads field names out of the message text (see BQ-17).

Per feature:

- **F-01 (E-ME).** `destinations` decide which top-bar links show; `roles` are shown as text only; nothing is derived from roles. `startable_lines` non-empty shows "+ Start". `csrf_token` is required on every sign-in. 401 shows the signed-out view; there is no sign-in screen (D-SIGNIN).
- **F-02 (E-WORK-LIST).** The frontend never filters, sorts or derives `kind` from `state`: order, `kind`, `counts` and `next_cursor` must be right. `counts` missing shows "–", not 0. `unassigned` count present is what shows the fourth tab (Leads only); 403 `queue=unassigned` for others. `next_cursor` is opaque and must be absent (not null, not empty) on the last page. `limit` is 10, 20 or 50. Refresh every 15 s re-reads page 1 only. `line` filter values are line titles taken from loaded rows, not from `filters.lines`.
- **F-03 and F-14 (E-WORK-ITEM, E-WORK-HISTORY).** Per-record access: 404 for a record the caller may not see (no id, title or client may appear in the reply). `revision` is the value later writes send as `expected_revision`. History `kind` filter values are `decisions`, `agent_work`, `evidence`; the mock filters on a private `_kind`, so the real filter meaning is the backend's. `restricted` history rows must carry no detail. Every `tasks[].you_can_act` and `allowed_actions` must be right, because the frontend never guesses permission.
- **F-04 and F-16 (E-TASK-CLAIM, E-TASK-DECIDE).** Claim before write: the page claims once per task id and revision (`{expected_revision}`), then decides with the revision the claim returned. Because the backend may bump the revision on claim, the claim response must return the new `revision`. A decide sends `{expected_revision, action, note?}`. `note` is limited to 2000 characters and required for return, reject and revoke; the frontend enforces it, the schema only says it in a description. 409 = a newer version arrived: the page reloads and shows both versions and never approves the newer one automatically. 403 = reload; the buttons come back only if the reloaded task is still actionable at the same revision. Uncertain effect (5xx or network on the decide): the page re-reads; it does not resend until the re-read shows the task is still open at the same revision. The mock checks revision (409) before eligibility (403); see BQ-6. `revoke` is not built (mock answers 422).
- **F-05 (E-WORK-START).** Body is exactly `{line, case_id, case_revision, intake, idempotency_key}`. One key per attempt; the key is kept for "Check again" after an uncertain result and discarded when the drawer closes. 201 must carry `work_id`; any other success status shows as uncertain for good. 422 `fields[]` name the intake field names. 409 means stale `case_revision` (or key misuse; see BQ-3). `next.summary` parts are joined by " · ". `journey_url` is checked by the frontend to be a same-site path.
- **F-06 (E-EXCEPTIONS).** Sends `q` and `what` (both in v7). If the backend ignores them the list looks filtered but is not (BQ-14). `open_count` must be the total across pages; if sent only on page 1 the count disappears after Show more.
- **F-07 (E-PROJECTS, E-PROJECT).** `status` is sent only for Closed and All; Active sends none, so the default response must be the active projects. Every extra field is optional and shown as "—" or "Not known" when absent. A project the caller may not see is 404.
- **F-08 (E-OVERVIEW).** Line tag colour comes only from `lines[].status.tone`; nothing is derived from state names. `waiting` is not in the v7 tone enum (BQ-19). Figures refresh every 15 s.
- **F-09 (E-EVIDENCE-UPLOAD, E-TASK-CLAIM, E-RESPONSE, E-WORK-ACTION).** Order of calls: upload proof first (each upload returns a new `case_revision`, used by the next upload and by the record), claim if `response.claim_required`, then E-RESPONSE once per press. E-RESPONSE has no idempotency key; `expected_revision` and the in-flight lock are the only duplicate guards. 5xx or network on E-RESPONSE or E-WORK-ACTION is uncertain: one re-read, no resend; if the re-read still shows the task open, the person may press again deliberately. The reconcile panel is shown only when the item has `reconcile` and `allowed_actions` contains `reconcile`. Reconcile `delivered` needs `evidence_id` and `case_revision`; the other outcomes send neither. E-EVIDENCE-UPLOAD 409 means the `case_revision` is stale; the file is not re-sent automatically.
- **F-10 (E-MONTH-END).** For any row the caller may not open, omit `work_id` or set `restricted: true`; the link target is `/work/{work_id}`. A known zero and an unknown amount are different (`cash_received_detail.known` and `has_unknown`).
- **F-11 (E-SETUP-RULES, E-SETUP-RULE-SAVE).** Only rows with `editor.kind = "role_set"` and `can_change` are editable. Save sends `{expected_revision (exactly as read, 0 for Not set), value: {roles}, starts, reason?, evidence_id?}`. 409 clears every edit and reloads; 422 keeps edits; 5xx or network reloads once and does not resend; if the revision did not move the person may save again. Hidden values: a `restricted` row must carry no `value`.
- **F-12 and F-15 (E-NOTIFICATIONS, E-NOTIFICATION-READ, E-ALERT-PREFS-READ, E-ALERT-PREFS).** Own records only; another person's notification id is 404. Mark-read runs before navigation; if it fails the page still navigates, the alert stays NEW, and nothing retries. The masked WhatsApp number is shown byte for byte and never sent back. Save sends `channel` and `frequency` exactly as read (a value outside the PUT enum must give the API's 422), `expected_revision` exactly as read (omitted when none was read), and every event `{key, whatsapp, email}` in returned order with locked events as read. 409 reloads and drops edits. The mock assumes `total` is the filtered count and `unread_count` is all of the person's unread alerts.
- **F-17 and F-21 (E-WORK-ITEM `workspace`, E-WORK-STEP, E-WORK-ACTION).** Step controls appear only for `workspace.steps` and only when `workspace.revision` is a number. Body: `{expected_revision: workspace.revision, step, item_ids?, inputs?, evidence_ids?, note? (<=2000), idempotency_key}`. One key per attempt; a double click sends one request; a new key only after done, a definitive 409 or 422, or a reopened form. Outcomes `done`, `queued`, `effect_uncertain` (the page then disables every step on that item and mounts the reconcile panel only if the reloaded item carries `reconcile` and `allowed_actions` has `reconcile`). 409: inputs kept, one reload, next press uses the new revision and a new key. 422: each `fields[].name` maps to an input; a general message shows on top only if some named field is not on the form. 5xx or network on a step with `sends: true`: no resubmit control at all, reload only. A step with `task_id` is a link to the decide page and never calls E-WORK-STEP. Duplicate-send protection is **not proved**: the mock accepts a second `approve_send`.
- **F-18 (E-RFP-OUTCOME, E-RFP-FOLLOWUP, E-RESPONSE team input).** An outcome of won or lost cannot be recorded again; only pending and unknown offer "Record the outcome" again, and only while the backend still returns `results`. E-RFP-OUTCOME has no idempotency key: a repeat after success must fail on `expected_revision` (409). Awarded amount: blank is omitted, "Amount not known" sends `{currency, unknown: true}` with no `amount`, never 0. Lessons are sent as `lessons` text; `lessons_items` is not sent. E-RFP-FOLLOWUP is sent only by a person's click (`INV-AGENT`), with `{expected_revision, version, body? (only if edited), idempotency_key}`; the key is kept per (version, text). `status: effect_uncertain` blocks any resend until the backend reconciles. `can_send` and `can_edit` are the only permission signals; an agent or a viewer without them gets 403.
- **F-19 (E-CLIENTS, E-CLIENT, E-CLIENT-CONTACT).** The form shows only when the detail says `can_change: true`; nothing comes from `/me`. A client the caller may not see is 404 and must leak no name. PUT sends `{expected_revision, name, email}` only (`reason` is not sent). No idempotency key: a repeat after success is 409 on `expected_revision`. 422 `fields[].name` must be `name` or `email`. `blocked[]` strings are shown as returned; nothing is derived from `billing_contact.set`.
- **F-20 (E-TEMPLATES, E-TEMPLATE-VERSION).** Upload sends `{expected_revision, filename, content_base64, note?}` with `expected_revision` exactly as read, **including 0** (see BQ-27). `can_upload === true` is what shows the control. No idempotency key: a repeat after success is 409. The "all templates are test templates" banner shows only if the list is complete (`next_cursor` absent) and every row has `test_template: true`. 422 `fields[].name` may be `filename`, `content_base64`, `note`.
- **Frame and follow-ups.** No backend behaviour.
