## Summary
- Authority is handled correctly. The add panel, the phone button and the From, To and Authority fields come only from the read: `can_add === true`, a numeric `revision`, `from_options`, `delegate_options` and `authorities`. Nothing in `Delegation*` or `useDelegation*` reads `/me` roles or the persona. The only `/me` use is `SetupGate`'s `setup` destination, which the spec allows.
- On submit, every value is taken again from the current lists (`DelegationForm.tsx:84-102`), so an unlisted or dropped value is never sent. Each press sends one PUT through the shared client, which adds the CSRF header and `expected_revision` exactly as read (0 included). A ref checked synchronously and shared by the panel and the sheet blocks a second send (`useDelegationAdd.ts:27-33`).
- The unconfirmed-write path cannot create a duplicate. If the revision is unchanged, Add is enabled again, but the next press is sent against that same revision. So if the first request was still in flight and lands later, one of the two writes gets a 409. If the revision moved, Add is held until "Start again". If the re-read fails, the form is locked, and "Try again" only reads the list and then settles against the revision that was sent (`DelegationView.tsx:105-158`). A re-read that returns no `revision` also counts as "changed", which is the safe choice.
- The 422 and 409 handling matches the spec. The new mock and the overlay follow the spec's check order. `server.mjs`, `proposals/setup.json` and `api.ts` only add lines: the two removed lines are the `M1_OPERATIONS` line and one import, each replaced with a longer version. Removing Delegation from `RESERVED` in `setup.spec.ts` is legitimate: the tab is no longer reserved, F-20 made the same change for Templates, and the other four tabs are still asserted.
- I found only non-blocking issues: one mock path is unreachable, the From/To pairing is inconsistent between the mock and the frontend when there is no From list, and the 409 message is wrong when the re-read fails.

## Findings
- TECH-1-1 | non-blocking | low | frontend | The mock's "no `can_add` → 403" step cannot be reached with the shipped fixtures, and no test covers it. The only fixture without `can_add` is `readonly`, and it has no options, so every add from it fails earlier with a 422 at the delegate check. Expected: the check-order step exists and is tested. Actual: dead code at `frontend/mock/delegations.mjs:151`; build.md (AC 21) admits this. Because of the spec's order, a view-only caller probing the mock also gets a 422 or 409 instead of a 403. That is acceptable for a mock, but the backend developer should know it is a choice to confirm. Fix: in `setup-delegation-mock.test.ts`, add a test that drives `saveDelegation` against a `default`-shaped fixture with `can_add` removed (for example, a `readonly_options` scenario or a fixture override that only the test can use), and assert the 403. Or record the order (403 after the 409) as a backend question in build.md.
- TECH-1-2 | non-blocking | low | frontend | The frontend and the mock pair To options differently in two cases. (a) When `from_options` is absent but `for_person_id` is present, the frontend shows the whole `delegate_options` list (`DelegationForm.tsx:61-62`). The mock's `delegatesFor(data, undefined)` then accepts only unpaired options (`frontend/mock/delegations.mjs:97-101`), so every option offered gets a 422. (b) In a mixed list, the mock still accepts options without `for_person_id`, while the frontend drops them (exact match). Only backend values are ever sent and the backend's 422 decides, so this does not break authority. But the mock does not model what the page offers. Fix: make `delegatesFor` use the frontend's exact match, and list "pairing with no From list" as an open question in build.md's contract proposals. The spec does not define that case.
- TECH-1-3 | non-blocking | low | frontend | On a 409 whose re-read fails without losing access, the page still shows "This changed while you were working. The list has been reloaded; check it and add again." The list was not reloaded, and the page keeps the old revision (`DelegationView.tsx:135-137`, `useDelegationAdd.ts:42-43`). Nothing unsafe follows: the next press gets another 409. But the sentence is untrue. Fix: when `outcome.page` is an `ApiError`, show the backend message, or a "couldn't reload the list" sentence with the read's retry.
