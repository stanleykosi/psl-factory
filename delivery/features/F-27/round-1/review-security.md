The overlay contract says that leaving it out means "the caller". So the screen shows one delegator while the request asks the backend to record another.

The add controls appear only when `can_add === true` and a revision is present.

## Findings
- SEC-1-1 | blocking | medium | frontend | **Problem.** With exactly one entry in `from_options[]`, the read-only From shows that person, but `from_person_id` is not sent. The overlay schema defines an absent `from_person_id` as "absent means the caller" (`frontend/mock/proposals/setup.json`, delegation_body.from_person_id; G-SCR13A-1 "defaults to the caller"). **Concrete case, `authority` scenario.** The person signed in is admin Ada Okafor. The page shows "From: Kemi Adebayo · PMO Lead" and narrows To to Kemi's paired delegate. It then sends `{expected_revision, delegate: 'P-FEMI', authority, ...}` with no From. A backend that follows the proposed contract would record Ada → Femi, not Kemi → Femi. The success notice still reads "Kemi Adebayo to Femi Ade" when it falls back to the form summary. So the page implies an identity and an eligibility pairing that the request does not ask for. The mock hides this because, against its own schema text, it falls back to the single option (`frontend/mock/delegations.mjs:133-134`). The test locks the behaviour in (`frontend/tests/setup-delegation.test.tsx:365`, body without `from_person_id`). Code: `frontend/src/features/setup/DelegationForm.tsx:100` (`if (fromOptions.length > 1 && fromPerson) body.from_person_id = ...`). The spec line in Contract/E-DELEGATION ("sent only when From came from `from_options[]` with two or more choices") causes this, so the spec writer should note the correction. **Fix.** Whenever From is drawn from `from_options[]` (one or more entries), send `from_person_id = fromPerson.person_id`, so the request names exactly the person the screen shows. In the mock, treat an absent `from_person_id` as the caller (the `is_you` row) and not as the single option. Update the `authority` test to expect `from_person_id: 'P-KEMI'`, and add a mock test showing that a single-option add without `from_person_id` is recorded from the caller.
- SEC-1-2 | non-blocking | low | frontend | **Problem.** When `delegate_options[].for_person_id` is present but `from_options[]` is absent (From reads "You"), `paired` is false and To lists every option, including delegates the backend paired with other delegators (`frontend/src/features/setup/DelegationForm.tsx:61-62`). The backend still decides, so this grants nothing, but the page offers choices the backend marked as belonging to someone else. **Fix.** When pairing keys are present and no From option is offered, show only the options with no `for_person_id` (or none) and record the case for the backend developer. Do not fall back to the whole list.

## Notes
- Checked and holding:
  - **DOM tampering.** `submit` re-resolves From, To and Authority through `find` on the current page's lists (`DelegationForm.tsx:84-101`). A planted option, or a delegate the next read drops, is never sent (tests at `setup-delegation.test.tsx:271-298`).
  - **Duplicate writes.** The ref is checked synchronously (`useDelegationAdd.ts:32`) and shared by the panel and the sheet.
  - **Uncertain writes.** An uncertain write re-reads once. With the same revision, a re-add uses the same `expected_revision`, so a late-landing first write turns the second into a 409, not a duplicate. A moved revision holds Add until "Start again". A failed re-read locks the form, and "Try again" only reads.
- **Per-record view-only.** `canAdd` needs `can_add === true` and a numeric `revision` (`DelegationView.tsx:46`). No row control is built even when `can_change` is true. The only `/me` use is the existing `SetupGate` destination gate.
- **Notices on 403/404.** The PUT's 403/404 notice shows the backend `message` verbatim (`DelegationView.tsx:136`). That is safe as text, but it relies on the backend not naming hidden records in that message. Record this for the backend developer alongside G-SCR13A-5.
- **Status wording.** `NOT_REFRESHED` ("The delegation was added…") appears only after a 200 and repeats the returned outcome, so it is not an effect claim.
- **D-DELEGATION-VIEW proposal.** It is still a proposal, and D05 and D-ADMIN-AUTHORITY are still open. Until the backend enforces G-SCR13A-1/-5, nothing on this page is a security control. All enforcement is the backend's.
