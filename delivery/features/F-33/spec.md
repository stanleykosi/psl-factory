## What is sent, and what stays held (read first)

- **Sent (to the local mock only):** the review claim (E-TASK-CLAIM), one decision per press (E-TASK-DECIDE, verdict `approve`, `return` or `reject`, with a note for return and reject), and the preparer's correction (E-WORK-STEP `correct_and_resubmit`). Nothing posts to the ledger, nothing is exported, no adjustment is created, nothing goes to anyone outside the app.
- **Held, because a product or backend decision is open:** (1) who reviews schedules: `finance.income_schedules.reviewer` is NOT SET, so the real review cannot start; the review fixtures are sample-marked and a "reviewer not set" fixture shows the backend's hold; (2) the income detail rules (`finance.income_schedules.income_detail`, NOT SET) and inventory rules (`.inventory`, NOT SET); (3) whether a return gives the preparer a "Correct and resubmit" task (D-RETURN, open; built as the working assumption); (4) which verdicts a schedule review offers (G-C-1); (5) the Setup link from a hold (G-C-3). The page shows whatever the re-read work item says and adds no rule.
- **Held to part 2:** possible-duplicate settlement (held board, G-54-1, G-54-2), Export as an adjustment (G-54-5), Withdraw approval (verdict `revoke`, G-54-4), the inventory kind (G-54-6).

### E-TASK-CLAIM `POST /api/v1/tasks/{task_id}/claim` and E-TASK-DECIDE `POST /api/v1/tasks/{task_id}/decision`
- **Through `useDecision(work_id, task_id)` only;** no new write path. The claim is sent once per task revision, only when the task's `you_can_act` is true; until it answers, the buttons are off with the existing "getting this review ready" line.
- **Decide request:** `{verdict, note?, expected_revision: <task revision as read or claimed>}`, header `X-CSRFToken`, no extra keys. `note` is required and non-blank for `return` and `reject`, at most `NOTE_MAX` (2000); checked before any request, with the message under the Note field ("Add a note to return it." / "Add a note to reject it."), announced, focus on the note. Approve sends no note.
- **200:** the item is re-read; the page draws the re-read state (returned, verified or rejected). The panel's done notice is the existing `VERDICT_WORDS` heading ("Schedule v1 is approved"); "Verified" appears only from the re-read `state: verified` / status tone `verified`.
- **Errors:** 401 → signed-out; 403 → the read-only view keyed on the re-read `cannot_act_reason` (403 and 404 alike on read); 409 → the existing stale view, entries kept, no automatic resend; 422 → the backend message under the note; 5xx, network or timeout → re-read first, `UncertainNotice`, never "approved", "returned" or "rejected" from the click, and the next decide only on a new deliberate press.
- **Permission and tenant:** buttons only when `tasks[i].you_can_act` is true for the step's `task_id`; otherwise `cannotActCopy(cannot_act_reason, task)` and no button. No role, person or `prepared_by` rule in the page; `/me` is not read.

### E-WORK-STEP `POST /api/v1/work/{work_id}/steps` (correct and resubmit)
- **Request:** `{expected_revision: workspace.revision, step: "correct_and_resubmit", inputs: {row_12_relationship: <one options[].value>}, idempotency_key: <UUID, new per press, reused on a manual retry of the same press>}`, header `X-CSRFToken`, through the existing `useWorkspaceStep`.
- **200 `done`:** re-read; the page shows the item back in review as the re-read says (W-2703 → `W-2703.next.json`, "You prepared Schedule v1, so someone else must review it."). Notice from the response `message` or the F-17 default.
- **Errors:** as F-30: 409 re-read and the stale sentence, choice kept; 422 under the named field; 5xx/network/timeout → "Not recorded" after a re-read, Try again with the same key; `outcome: uncertain` → the existing reconcile panel, never "resubmitted".

### Screen states
- **Loading:** existing skeleton. **Empty:** a workspace with no sections draws the header and status only. **Error:** the problem card with Retry. **Success:** the four board states plus W-2705…W-2711. **Held:** W-2706. **Restricted:** a section or item with `restricted: true` draws "Restricted"; its value is never shown.

## Acceptance criteria

### Page
1. **Four states from data.** `/work/W-2701`…`W-2704` show the status label and tone, stations, sections, agent card, quote, facts and "Next" of their fixture and nothing else; no board string is in `src` (`grep -rn "CHIDI INVESTIGATING\|AWAITING FINANCE DECISION\|CORRECT AND RESUBMIT\|THESE 38 ROWS\|Service revenue" frontend/src` returns nothing). — verify: `cd frontend && npx vitest run tests/income-schedule.test.tsx`; pages at 1440 and 390.
2. **Amounts as returned.** On W-2702 the report line reads "₦12,400,000.00" at 1440 and at 390 (no "₦12.4M"); changing the fixture's amount to `"12400000.10"` shows "₦12,400,000.10" exactly. — verify: component test at both widths.
3. **The page computes nothing.** Changing W-2701's figure values (e.g. "31 ROWS" to "30 ROWS") leaves the section title "Income detail · 38 rows" unchanged; changing W-2702's "2 OF 2" or W-2704's `next` text changes only that text; no new or changed file under `frontend/src/features/workspace/` adds `parseFloat`, `Number(`, `reduce(`, `compactAmount` or arithmetic on an amount or count. — verify: component tests on modified copies; `git diff -U0 frontend/src | grep -nE "parseFloat|Number\(|\.reduce\(|compactAmount"` returns nothing.
4. **Unknown is never 0, blank or a dash.** W-2707 shows "Unknown" for the report line and for Detail rows; the page contains no "₦0", no "0.00", no empty value cell and no "-" or "—" in their place. — verify: component test on W-2707.
5. **Sample-marked.** Every fixture page shows the shared `SampleLabel` ("SAMPLE DATA") because the record says `sample: true`; a copy with `sample: false` does not. — verify: component test.
6. **Reviewer not set is a hold.** W-2706 shows the backend's status, the "Who reviews schedules · NOT SET" fact and its `next` sentence; there is no Decide panel, no button, no claim or decide request, and no reviewer's name or role anywhere on the page. — verify: component test with a recording `fetch` (zero POSTs); `document.body.textContent` checked for "Ada Okafor" and "Schedules reviewer" (absent).
7. **Decide controls only from `you_can_act` and the steps.** W-2702 shows "Approve schedule", "Return with a note" and "Reject" under "Decide · Schedules reviewer"; W-2709 shows only Approve and Return; W-2711 shows neither the `revoke` nor the `post` step; W-2710 draws its step as the existing link (the step's own label) to `/work/W-2710/decide?task=T-2710`. W-2705 shows "You prepared Schedule v1, so someone else must review it." and W-2708 the `not_your_role` copy, each with no button and no claim sent. The same pages for personas `finance_lead`, `ceo` and `pm` draw the same controls; the new code does not read `/me` (`grep -rn "useMe\|/me\b" frontend/src/features/workspace/InlineDecide.tsx` returns nothing). — verify: component tests with three personas and a recording `fetch`.
8. **Agent work is not a decision.** On W-2701 Chidi's steps, sources, "WORKING" and "CHIDI CHECKING" render in the agent style; there is no decide control; the possible duplicates are never shown as "none" or "no duplicates"; "Ask Chidi" links to `/assistant`. — verify: component test; link href.
9. **Verified only when the response says so.** W-2704 shows "VERIFIED" from its status; pressing Approve on W-2702 shows "Verified" only after the re-read serves `W-2702.approve.json` (`state: verified`); with the decide answering 200 but the re-read still serving the review state (test double), the page does not say "Verified". "Posted to the ledger: NO" and "THESE 38 ROWS ONLY" come from `facts`; W-2704 has no Export or Withdraw button. — verify: component tests with a recording `fetch`.

### Writes
10. **Approve.** On W-2702, the page sends one E-TASK-CLAIM to `/api/v1/tasks/T-2702/claim`, then pressing "Approve schedule" sends exactly one POST `/api/v1/tasks/T-2702/decision` with the CSRF header and `{verdict: "approve", expected_revision: 1}` (validates against the generated request schema, no note, no extra keys); a double press sends one. — verify: component test; e2e request log.
11. **Return and reject need a note.** Pressing "Return with a note" or "Reject" with an empty or blank note sends nothing and shows the note message under the field, announced, with focus on it; a note over 2000 characters is refused before sending. With a note, one POST with `verdict: "return"` (or `"reject"`) and the trimmed note; the re-read shows the returned (or rejected) state. — verify: component tests; e2e request log shows no decision POST without a note.
12. **No write when the person cannot act.** On W-2705, W-2706 and W-2708 no claim and no decision is sent, whatever is pressed or typed. — verify: e2e request log (zero task POSTs).
13. **Backend refusals are shown.** With `psl_mock_scenario` 403 the decide shows the read-only view and no "approved"; 409 shows the stale view, keeps the note and sends again only on a new press with the new revision; 422 shows the message under the note. — verify: component tests; `tests/income-schedule-mock.test.ts`.
14. **Uncertain decide.** A network failure, timeout or 500 on decide re-reads the item before anything else, shows `UncertainNotice`, never shows "approved", "returned" or "rejected" from the click, and sends no second decision automatically. — verify: component test with fake timers (one POST after 60 s); e2e with a routed abort.
15. **Correct and resubmit.** On W-2703 (and on `W-2702` after a return), "Correct and resubmit" opens the step form with "Row 12 relationship" as a required choice of three with nothing selected; submitting without a choice sends nothing and shows the field message; with a choice, one POST `/api/v1/work/W-2703/steps` with CSRF, `expected_revision`, `step: "correct_and_resubmit"`, `inputs.row_12_relationship` one of the options, and a UUID `idempotency_key`; a retry after a 500 reuses the same key; on 200 the re-read shows the item back in review with the `prepared_by_you` copy. The page never says "resubmitted" before the re-read. — verify: component tests; e2e request log.
16. **No D-RETURN wording of our own.** The returned page shows the reviewer's quote and the step's `consequence` as returned and no "Proposal: every return…" note (absent from the fixture); `grep -rn "backend only waits\|every return" frontend/src` returns nothing. — verify: grep; component test.
17. **Access.** 401 on read or write → signed-out with `next=/work/<id>`; 403 and 404 on read look the same and show no title, amount or fact; persona `none` gets the same not-open view with no further call. — verify: component tests with a recording `fetch`.
