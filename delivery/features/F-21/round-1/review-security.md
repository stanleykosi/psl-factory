## Notes
What the backend must enforce before a real send (contract mock only now; none of this is claimed as built):
1. **Refuse a resend while uncertain.** While a report version has an uncertain delivery (`reconcile` open), E-WORK-STEP must refuse `approve_send` and any other step that sends for that item, whatever key or `expected_revision` arrives. The answer is 409 or 422 and nothing goes out. The server should also leave `approve_send` out of `steps` (or give it a `disabled_reason`) and return `allowed_actions: ["reconcile"]` only. The frontend lock should not be the only signal.
2. **Idempotency.** The server stores the key per actor, item and step for the length of the longest client wait. A repeated key gets the first reply back with no second effect, even if the first attempt is still running or its result is uncertain. The same key with a different body is refused. A new key with a stale `expected_revision` gets a 409. The send itself carries a provider-side idempotency reference, so an uncertain effect can be reconciled before any retry.
3. **The approved version is the sent version.** `approve_send` must bind to the version under review (`expected_revision` plus `version.number`/`document_id`), so "Approving sends this exact version" holds. An edit or return between review and approval gives a 409, not a send of newer words.
4. **Reconcile resend.** W-2205's `reconcile.resend` offers "one resend of the same version". E-WORK-ACTION must allow at most one resend, of the same document, only after an authorised person records "didn't arrive", and that resend is itself keyed for idempotency. This is the F-09 contract, restated because the weekly report goes to a client.
5. **Authority.** Each step is checked per record and actor: only the item's PM may `send_to_tola` or `save_draft`; only a configured PMO Lead may `approve_send` or `return`. This must not depend on which buttons the item returned. Section text, the agent note, the draft words or the model's assembled output can never add a step, a recipient or an approver. The recipient list comes from configuration, never from the report text.
6. **Prefilled words.** The new prefill in `StepForm.tsx` puts a descriptor's `value` into text and long text fields, skipping restricted ones. The backend must fill `value` only with the PM's own saved draft and never with model text, so "the words to the client are yours" holds.
7. **No leaks on 403 or 404.** E-WORK-ITEM and E-WORK-STEP on a wrong tenant or user answer with no client name, title or id in the body. The frontend already shows `NoAccessState` with none of these.
