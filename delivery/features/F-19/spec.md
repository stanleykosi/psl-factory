## Summary
- A new **Clients** list at `/clients` (name, projects, owed, whether a billing contact is set, "as of" time, "Show more" by `next_cursor`) and a **client detail** at `/clients/[clientId]` (billing contact, projects linking to the existing project journey, money: invoiced, received, owed).
- On the detail, a person the backend allows (`can_change: true`) **sets the billing contact** (name and email) with one `PUT`, CSRF header, `expected_revision` taken from the detail's `revision`. No automatic retry. A 409 reloads and shows the newer version; a 422 puts each message beside the right input.
- Money that is not known reads **"Unknown"**, never 0 and never blank (INV-UNKNOWN). The page decides no eligibility: it shows what the backend returns (`billing_contact.set`, `blocked[]`, `can_change`) and nothing is derived from `/me` roles.
- Each of the 4 boards passes the fidelity tool on the contract mock at its own width (coverage 100% after approved exceptions, visual >= 90).
- Contract mock only. D-CLIENTS-VIEW is still `proposed`; it is used under the recorded exception (`architecture/sources/decisions-2026-11-15.md` items (g) and (i), same basis as F-09 and F-17): the backend developer may change or refuse any field and nothing is released. The PR must not claim a real backend. One PR, one commit.

## Contract

### Operations (v7, unchanged; built against on the mock only)
| Operation | Request | 200 | Errors | Permission, tenant, versioning |
|---|---|---|---|---|
| E-CLIENTS `GET /api/v1/clients` | optional `limit` (10, 20, 50; the page sends none, the backend default is 20) and `cursor` (= previous `next_cursor`, opaque) | `{items:[{client_id, name, projects?, owed?{amount?,currency,unknown}, billing_contact_set, sample?}], next_cursor?, as_of}` | 401 signed-out callout with `next=/clients`; 403 and 404 `NoAccessState`; 5xx or network `WorkErrorCard` with Try again | `case.read` on at least one of the client's cases. The backend filters; the page never narrows or widens the list. |
| E-CLIENT `GET /api/v1/clients/{client_id}` | path id (encoded) | `{client_id, name, revision, billing_contact{name?,email?,set}, projects:[{case_id,title,stage?}], money?{invoiced?,received?,owed?}, blocked?[string], can_change?, sample?}` | as above; 404 hides records the person may not see (no id, name or title appears) | As E-CLIENTS. |
| E-CLIENT-CONTACT `PUT /api/v1/clients/{client_id}/billing-contact` | `{expected_revision = detail.revision, name, email}` + CSRF (`reason` is optional in the schema and is **not sent**) | `{client_id, revision}` | 401 signed-out; 403 reload, then read-only; 404 `NoAccessState`; 409 keep what is shown, reload once, show the newer version; 422 `fields[].name` (`name`, `email`) shown beside the input, entries kept; network or 5xx: uncertain notice, one reload, no resend | "client contact authority as the backend allows": the page asks nothing of `/me`; it shows the form only when the detail has `can_change: true`. No idempotency key exists: a repeat after a success fails on `expected_revision` (409). One write at a time; the double-press guard (a ref, set synchronously) is the protection. No automatic retry. |

The frontend adds no field, endpoint or local type for anything the schema lacks (see Conflicts).

### What each screen shows, and from where
Every element is drawn from the returned field. A missing field leaves its element out; there is no placeholder and no board copy standing in for data. Times use WAT (`Africa/Lagos`, `formatDay`/`formatClock` from `features/response/labels.ts`). Money uses `formatAmount` (`features/decide/format.ts`) for a known amount and the word **Unknown** when `unknown` is true or the amount is absent; an absent `owed`/`money` block shows nothing (not "Unknown", not 0) unless the board column needs a cell, in which case the cell shows "Not given". A known `"0.00"` from the backend shows as the amount it is.

**1. Clients list** (`/clients`, SCR-35 default; desktop and mobile)
- Heading `h1` "Clients"; eyebrow "PROJECTS" at desktop. Phone: `usePhoneBack({label:'Projects', href:'/projects'})`; `main` carries no back link of its own.
- Desktop table (CLIENT, PROJECTS, OWED, BILLING CONTACT) built from `items`, in the order returned; phone: one card per row (name, tag, projects line, owed line). Each row links to `/clients/{client_id}` (`encodeURIComponent`).
  - CLIENT: `name`, plus a "Sample" tag when `sample: true`.
  - PROJECTS: `projects` as a number ("1", "0"); absent shows "Not given". The board's word "active"/"closed" is not carried by the list contract (Conflicts 3).
  - OWED: `owed` (amount or "Unknown"; absent "Not given"). Extra to the board (Conflicts 4), required by readiness.
  - BILLING CONTACT: "Set" when `billing_contact_set` is true, else "Missing · invoices can't start" (the board's wording, shown as copy; it enforces and derives nothing). No email in the list (Conflicts 2). The tag beside it ("READY"/"NEEDS DETAILS" on the board) is **not** drawn from any field other than this flag: "Set" tag or "Billing contact missing" tag, same words (Conflicts 1).
- Line under the title: "{n} clients as of {WAT time}" where `n` is the number of rows loaded and, **only when `next_cursor` is absent**, it is the whole list; with a `next_cursor` it reads "{n} clients loaded as of {time}" (no total is invented; the board's "2 missing billing contact" count is shown only on a complete list, from the loaded rows, Conflicts 5).
- **Show more**: a button shown only when `next_cursor` is present; it appends the next page (`cursor=next_cursor`), disabled and "Loading…" while in flight. On error the loaded rows stay and a small `role="alert"` message with "Try again" appears. Extra to the board (Conflicts 6).
- States: **Loading** `LoadingState`; **Error** 5xx or network `WorkErrorCard` ("We couldn’t load the clients. Your work is safe; nothing was changed."), 401 `SignedOutState`, 403 and 404 `NoAccessState`; **Empty** (`items: []`, no `next_cursor`) a plain message "No clients to show yet." (no board draws it; built from the F-07 empty pattern, Conflicts 9); **Success** as above. Tab title "Clients · PSL Factory"; on 403/404 a generic title.

**2. Client detail** (`/clients/[clientId]`, SCR-35 detail; desktop and mobile)
- Desktop crumb "CLIENTS / {NAME}" (the "Clients" part links to `/clients`), `h1` = `name`. Phone: `usePhoneBack({label:'Clients', href:'/clients'})`, `h1` = `name`.
- **Banner** (the board's amber sentence): one line per entry of `blocked[]` exactly as returned. When `blocked` is absent or empty, no banner. Nothing is derived from `billing_contact.set`.
- **Billing contact** section. Fields "Billing contact name" (`name`) and "Billing email" (`email`) with the static helper "Needed before any invoice can start" under the name (the board's words, kept as copy because they restate REC-CLIENT's constraint; Conflicts 7).
  - `can_change === true`: two inputs prefilled with `billing_contact.name`/`email` when present (empty otherwise), and the button **"Save billing contact"** (Conflicts 8). It stays on (blue, as both detail boards draw it); a press with a blank name or email sends nothing, shows the message beside that field and moves focus to the first blank one (D-75a, replaces "off until both are non-blank"); busy state "Saving…". Client-side checks refuse only blank values; the email format is the backend's to judge (422).
  - `can_change` false or absent: the same labels with read-only values ("Not set" when `billing_contact.set` is false and the field is absent), no form, no button, and the line "You can't change this client's details." (new copy, Conflicts 10).
  - Success (200): reload the detail once and show the returned values, then a polite `role="status"` line "Billing contact saved." The form is not closed or hidden by any local rule; the reloaded `can_change` decides. If the reload fails, the page keeps the entered values, shows "Saved. We couldn’t refresh the page; reload to see the latest." and the form is off until a successful reload (its next press would carry a stale revision).
  - 409: reload once, show the newer values in the fields only if the person has not typed (otherwise keep their typed text and show the newer saved values under the field as "Current: {name} · {email}"), and the notice "This client changed while you were editing. Check the details and save again." Nothing resends. The next press carries the reloaded `revision`.
  - 422: `role="alert"` summary "Check the highlighted details." and each `fields[].message` beside its input (`aria-invalid`, `aria-describedby`); an unknown `fields[].name` shows its message in the summary. Entries kept. If `fields` is absent, the response `message` is shown in the summary.
  - 403: reload once; the reloaded `can_change` decides; the server message shows. 401: signed-out callout. 404: `NoAccessState`.
  - Network or 5xx: "We couldn’t confirm the change was saved." reload once, no resend; if the reload also fails the form is off and "Try again" only reads the client.
- **Projects** section from `projects[]` in order returned: each row `title` and `stage` (when present), linking to `/projects/{case_id}` (the existing journey, `ProjectJourney`). Empty list: "No projects yet." The board's "Active · PM Tunde Bello · 4 milestones" is not in the contract (Conflicts 3).
- **Money** section from `money`: three rows Invoiced, Received, Owed. A row whose block is missing is left out; `unknown: true` shows "Unknown" (the word, plus a visually-hidden "amount not known"); never 0. Extra to the board (Conflicts 4).
- "Sample" tag next to the title when `sample: true`.
- States: **Loading**, **Error** (WorkErrorCard "We couldn’t load this client. Your work is safe; nothing was changed."), 401, 403/404 `NoAccessState` (no id or name in the document, tab title or phone bar; title "Client · PSL Factory"), **Success**. **Empty** does not apply.

## Conflicts with the boards and the contract
Each place the contract, the existing code or this spec adds, moves or removes something a board draws. The design engineer decides before the build; each is an exception candidate, provisional until signed. Per readiness, the contract is not extended locally: every "needs a field" item below goes to build.md as a contract proposal for the backend developer (as F-14 did) or is a fidelity exception.

## Out of scope
- The backend (T-CLIENTS, REC-CLIENT), OpenAPI, `schema.d.ts` regeneration, `src/api/**`, `architecture/**`, any new npm dependency.
- Any invoice, receipt, allocation or payment behaviour; deriving or enforcing invoice eligibility; Finance release logic. The billing contact is a client record field only.
- Real sends or any contact notification. Nothing leaves the mock.
- Search (`q`), a Filter control, sorting, a page-size picker, creating or deleting clients, editing the client name, address, tax ID or legal name, a contacts list, a `reason` field.
- Project tabs and the project report (FE-M3-PROJECT-TABS, FE-M3-REPORT) beyond linking to the existing journey; a "Clients" link in the Projects page or shell (Conflicts 13).
- An automatic retry or background refresh of any write; offline editing.

## Assumptions
- Routes are `/clients` and `/clients/[clientId]`. Reason: the boards imply them (crumb "CLIENTS / …") and the API paths match.
- The form shows only when `can_change === true`; absent means read-only. Reason: the schema says authority is "as the backend allows"; showing a form that cannot save is worse than hiding it.
- The page sends no `limit` (backend default 20). Reason: the board draws no page-size control.
- `reason` is not sent. Reason: optional in the schema and no board field.
- "Not given" shows for an absent `projects` or `owed` in a list cell. Reason: unknown is never zero or blank; the board has no word for it.
- The count line counts loaded rows and claims a total only without `next_cursor`. Reason: no total is returned.
- A 200 PUT is followed by exactly one GET of the detail. Reason: the response carries only `revision`, and the form should show stored values.
- The email format is judged by the backend (422), not the frontend. Reason: no source gives the rule; the mock mirrors a minimal "@" check.
- The mock's list rows come from one dataset per persona-independent cookie; personas pm, ceo, finance_lead and admin see the same clients. Reason: no source says they differ; `none` gets 403.
- Ports 4631 to 4633 are free. Reason: F-18 used 4621 to 4623.
- Wrong or missing optional fields are tolerated by leaving elements out. Reason: D-CLIENTS-VIEW can change at any time.
