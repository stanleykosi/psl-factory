## Findings
- QA-2-1 | non-blocking | low | integration | An upload answering 413 or 415 shows "Couldn't upload. Try again." with a Try again that will fail the same way, and the backend's message is lost. The contract lists only 401/403/404/409/422 for E-EVIDENCE-UPLOAD, and the spec has the backend send its limits as 422, so this is within spec. But a proxy or Django body-size limit will answer 413 before the view does. The backend handoff should confirm that size and type limits answer 422 with a message, and that the request-body limit is above the largest allowed file. `frontend/src/api/errors.ts:4-10` maps 413 and 415 to `server`, and `frontend/src/features/response/useEvidenceUpload.ts:104` then makes them retryable.
- QA-2-2 | non-blocking | low | backend | A 403 or 404 on the start shows "You can't start this here." followed by the backend's own message, word for word. The mock's messages are safe ("Your role does not allow you to start this line." and "We could not find that record."). A faked message holding a case id and a file name was shown in full, and the two messages tell 403 apart from 404. This is F-05 code that this head does not change (`frontend/src/features/start-work/useStartWork.ts:375-376`). The backend should keep 403/404 messages free of record and file names; or the frontend could show only the lead sentence in a later slice.
