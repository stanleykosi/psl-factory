## Summary
- Starting a leadership report works live: report type, period, template, audience and "include" domains, sent with `POST /projects/{case_id}/leadership-report-intake`. The backend chooses the projects (D-33). The page shows a plain no-access note when `all_projects_available` is false.
- `/work/{id}` for a leadership report draws a `leadership-report` panel through F-85's line adapter: state while drafting, the narrative sections with coverage, the per-source counts with capture time (D-34), review verdicts, recipients and `next_action`.
- The monthly review is decided in place: approve, return or refuse through `POST /work/{id}/reviews`, only the verdicts the readback allows, with a note rule.
- Editing a draft uses `POST /work/{id}/leadership-report` with `expected_revision`, `case_revision` and a reason.
- The received board shows each recipient's receipt. An uncertain delivery is checked with F-87's "Check what happened" control (`action:"reconcile"`, 202); this feature adds no second one and never resends.
- Parts the live API cannot supply are not drawn (listed under "Conflicts with the boards"). Nothing is derived, computed or filled in.

- The adapter produces sections in the order below. Writes are not a section: the review form and the edit form are small components under `src/features/work-item/live/leadership/` mounted by `PanelView` for this key only (the adapter interface stays as F-85 left it, plus an optional `Actions?: ComponentType<{...}>` slot on `LineAdapter` for the panel's own forms, added once and documented in `adapter.ts`).

### Setup (start) form (SCR-52 setup)
Registered as a line in F-86's registry (`src/features/start-work/lines/`) under live line key `pmo-leadership-report/v1`; it uses F-86's project picker, then this form. It starts with the leadership intake route, not `POST /work`.
- On project chosen: `GET .../leadership-report-intake?kind=<chosen kind>` (re-read when the kind changes). Hold `revision` is NOT used; the start body's `case_revision` is the picker row's `case_revision`.
- Fields:
  | Field | Control | Source / rule |
  |---|---|---|
  | Report | two options: "Internal Tuesday", "Monthly executive" | `selection.kind` `internal_tuesday` / `monthly_executive`; required, no default chosen for the person |
  | Audience | Tuesday: shown as "Internal", not editable. Monthly: two options, "Internal" and "Management"; required, none preselected | `selection.audience`. The API names no member list, so none is shown |
  | Period | two date fields, From and To | `selection.start_at`, `selection.end_at` (ISO date-time at the start of From and the end of To in the viewer's timezone); required; To not before From checked client side; every other period rule is the backend's answer, shown as returned (422 `fields[]`) |
  | Include | six checkboxes: Meetings, Actions, Milestones, Issues, Changes, Escalations | `selection.scope.domains` (the six enum values); all checked at first; at least one required. `selections{}` record ids are never sent |
  | Template | one option per `templates[]` as "{name} v{version}"; preselected when exactly one; person picks when several; "No template" only when `templates[]` is empty | `selection.template_id` (null when none). `content_id` is not sent |
  | Reference | text, 1 to 160 characters, required | `reference` |
  | Background | not shown | `background:false` |
- No-access note: when `all_projects_available` is false, show above the form "You can only include the projects you have access to. This report will cover your own projects." (one constant) and the project chosen. When true, show "The report covers every project your role may report on. The factory chooses the project list." No project list, record pickers or include flags per record are drawn (D-33).
- `automatic_project_scope`: shown nowhere. It is a backend flag; the builder records the live value in the PR (D-33 says the automatic all-projects selection is backend work not yet confirmed shipped).
- `setup_actions[]` and `owner_evidence[]`: read and kept in the hook; no control is drawn (the three `draft_*` actions belong to Setup rules, out of scope). When `setup_actions` is empty nothing changes.
- Submit: `POST /api/v1/projects/{case_id}/leadership-report-intake`, body exactly `{action:"start", case_revision, key, reference, background:false, selection:{template_id, start_at, end_at, kind, audience, scope:{domains}}, sections:null}`, with `X-CSRFToken`. `key` is made once per form opening with `newIdempotencyKey()` and kept across retries of the same attempt. A 201 opens `/work/{work_id}`.
- Errors: 401 signed-out state; 403 `csrf_failed` refreshes the session and says "Refresh your session and try again" (nothing was sent); 403 other and 404 "This record is unavailable."; 409 "This project changed. Reload and try again." (the picker re-reads `case_revision`); 422 maps `fields[]` to the control (`reference`, `selection.start_at`/`end_at`, `selection.kind`, `selection.audience`, `selection.scope`, `selection.template_id`), any other name shown as a general message with the server's text; 429 and 503 "Try again shortly."; network or 5xx after a send: uncertain, "We couldn't confirm that the report was started. Check My work before trying again." and the form keeps the same `key` (a second press sends the same key, never a new one).
- States: project loading; intake loading (skeleton); intake error (retry, same mapping, form not offered); empty (no startable project: "No projects to start this on."); success as above.

### Drafting (SCR-52 drafting)
- `GET /work/{id}` `state` only, drawn by the shared page (F-85): "Drafting" wording from `STATE_TAGS`, `current_activity.label` or `progress.status` when present. No steps, no "step 3 of 4", no figures. Polling follows F-85.
- When the leadership readback is available (it can answer before sections exist), show once, under the state, one fixed sentence only if `coverage.project_register` has any entry with `unavailable_domains` not empty: "Some projects are left out of this report for the sources you can't see: {project names}." Never a count of the left-out sources. If `editable_sections` is null, no section list is drawn.

### Review (SCR-52 review, monthly)
Shown when `kind` is `monthly_executive` and `document_version_id` is not null.
- Header facts, from `coverage`: scope in words (`selected_records` "Selected records", `approved_project_scope` "Your approved projects", `all_psl_projects` "All PSL projects"); "As of {captured_at}" with the viewer's local date and time; "Projects covered: {projects}" (a number, no "of N": no total exists); per-source rows "Meetings", "Actions", "Milestones", "Issues", "Changes", "Escalations" each "{count} in this report" from `coverage.counts[]` in that fixed order. A domain absent from `counts[]` reads "Not recorded", never 0; a count of 0 from the API reads 0. Nothing is summed or derived. The design's "Invoices verified" has no source and is not drawn.
- Left out: for each `project_register` entry with `unavailable_domains` not empty, "{name}: {domains in words} not available to you."
- Sections: for each key of `editable_sections` in API order (delivery_health "Delivery health", risks "Risks", performance "Performance", escalations "Escalations", critical_incidents "Critical incidents"): the text, a coverage tag (supported "Supported", partial "Partly supported", unknown "Unknown", not_applicable "Not applicable"), "{n} records cited" (no labels, as F-85). Empty `text` reads "Not recorded". A section with coverage `unknown` is never filled in by the page. `editable_sections:null` draws "The draft isn't ready yet."
- Decide panel: one button per verdict in `review_verdicts[]`, in the order "Approve and send" (approve), "Return with a note" (return), "Refuse" (reject); none when the array is empty and then no decide card, no explanation invented. A note field (required to return or refuse, optional to approve, max length the server's) and the sentence from the board "Approving sends this exact version to the audience." Who reviews is not named anywhere.
- Send: `POST /api/v1/work/{work_id}/reviews` `{kind:"document", expected_revision, case_revision, version_id: document_version_id, verdict, note}`; all three tokens come from the panel readback (`expected_revision`, `case_revision`, `document_version_id`); a null one disables the buttons with "This report can't be decided right now." Success 200 `{..., review_id}`: re-read the readback and the work item and show what comes back; one press, buttons disabled while in flight.
- Errors: 403 not allowed "You can't decide this review."; 404 "This record is unavailable."; 409 (a newer revision) re-read both and show "This report changed. Read the new version before deciding."; 422 shows the first `fields[].message` (note rule); 429/503 "Try again shortly."; network or 5xx after a send: uncertain: re-read, lock the buttons and say "We couldn't confirm that your decision was recorded. Check the page before trying again." They unlock only when the re-read still shows a pending review (`review_verdicts` non-empty and the same `document_version_id`).
- Request-review: not built. The contract has no route or flag for it. If `next_action` carries words about asking for review, show them as text only. Recorded as a gap (see Assumptions).

### Edit the draft (monthly and Tuesday)
- Shown when `can_correct` is true and `editable_sections` is not null: an "Edit the report" control opens a form with one text field per section (existing text, evidence ids kept as read, coverage kept as read) and a required "Reason". Evidence ids and coverage are not editable.
- Send `POST /api/v1/work/{work_id}/leadership-report` `{expected_revision, case_revision, reason, selection:<the readback selection with kind, audience, template_id, start_at, end_at, selections, scope.domains only (the readback's scope mode/actor/configuration are dropped)>, sections:<all sections, text changed, evidence_ids and coverage unchanged>}`. 200 re-reads. No new key (the revision is the guard).
- Errors as in Review (409 re-read and keep the typed text in the form, say "This report changed. Your edits are kept below; check them against the new version."). `can_correct:false` hides the control.

## Assumptions
- The panel key is `leadership-report`, by the weekly-report naming (C-20). Reason: the contract does not name it; the builder confirms live (Contract, Panel and adapter).
- Include checkboxes map to `selection.scope.domains`. Reason: it is the only API field for a domain choice and the board draws these six names; readiness says not to invent include flags per record, which this does not.
- All six Include boxes start checked. Reason: the board's default and the least surprising reading; the person can uncheck.
- The start uses `POST /projects/{case_id}/leadership-report-intake` with `sections:null`, not `POST /work` `line:"pmo-leadership-report/v1"`. Reason: the connection map and readiness name the intake route; the worker drafts the sections.
- `background:false`. Reason: no board control or backend rule for background start.
- Tuesday audience is fixed "Internal" and monthly audience has no default. Reason: the API's own purposes (`internal_tuesday:internal`, `monthly_executive:internal`/`:management`); which monthly audience is right is a business choice not given.
- Period is two date fields, From at the start of the day and To at the end of the day in the viewer's timezone. Reason: the API wants `start_at` and `end_at`; no other period rule is shown (the board's "Up to a year" is not enforced here).
- Counts are labelled "in this report", not "completed" or "open". Reason: D-34 gives per-source counts of the selection manifest, not statuses.
- "Received by every recipient" is shown only when state is `verified` and every row has a receipt. Reason: no field says all were delivered; this uses two supplied facts and invents nothing.
- Refuse is the label for verdict `reject`. Reason: the board's note hint says "return or refuse".
- Edit sends all sections with text changed only. Reason: the correct body needs the full `sections` object.
- Nothing about who reviews is shown. Reason: the board says "set in Setup › Rules" but no API field names the reviewer; no approver is invented.
- Request-review gap: D-35 says the work offers the authorised request-review action once eligible, but the live contract (API 1.24.0 types) has no leadership route, field or `actions[]` value for it. Reason: nothing to build; reported to the coordinator for the backend (`delivery/connect/backend-questions.md`).
