## Findings
- TECH-2-1 | blocking | medium | frontend | The same-origin check on `journey_url` can be bypassed. `safePath` (`frontend/src/features/start-work/LineForm.tsx:120-122`) checks the raw string with `startsWith('/')` and rejects `//` and `/\`. Browsers' URL parsers strip ASCII tab and newline before resolving, so `"/\t/evil.example"` and `"/\n/evil.example"` pass the check but resolve to `http://evil.example/`. I confirmed this with `new URL("/\t/evil.example", "http://localhost:3511").href`. Next's `Link` treats a non-local URL as external, so the click goes off-site. The value comes from our own E-LINES (v6 types it only as `string, minLength 1`), so the risk is a bad or compromised server value. But round 2 claims and tests this rule, and the coordinator named it as high-risk. Expected: resolve before comparing, e.g. `const u = new URL(url, window.location.origin); return u.origin === window.location.origin ? u.pathname + u.search + u.hash : undefined`, or reject any control character. Also add `'/\t/elsewhere.example'` and `'/\n/elsewhere.example'` to the `it.each` at `tests/start-work.test.tsx:646`.
- TECH-2-2 | non-blocking | low | frontend | The greyed-after-422 button (UX-1-3) has no test. The 422 tests at `tests/start-work.test.tsx:469-502` never check that the start button is disabled after the 422, or enabled again after a change. The e2e "1 thing to fix" cases don't check it either. Expected: one component assertion with `disabled === true` after the 422 and `false` after `pick(...)`. A related point to note: when the only problem is one the person can't fix in the form (the billing-contact 422), the button stays grey until they change some unrelated value. That matches the board, but it is an odd retry path.
- TECH-2-3 | non-blocking | low | backend | "What happens next" now depends on a separator the contract doesn't define. `WhatHappensNext` (`LineForm.tsx:136-152`) splits `next.summary` on `" · "` and inserts the decision after the first part. The phone line takes the first two words when the first word is the agent's name. To make the board render, the fixtures' summary changed from the spec's `"...signed SOW; issue, delivery..."` (spec.md:188) to `" · "`. A backend that sends the spec's text gets the decision after the whole sentence, which reads fine but is not what the board shows. Expected: record in D-START-INTAKE, or the backend handoff, that `summary` parts are joined by `" · "` (or carry the parts as an array). Until then, treat it as a presentation convention only.
- TECH-2-4 | non-blocking | low | frontend | `ProblemBox` is keyed by `problem.name` (`LineForm.tsx:282`). If a 422 names the same unrendered field twice, React gets duplicate keys. Also, a 422 for the disabled `proof` field would be drawn inline under a control the person can't use, and the button would stay grey. Expected: key by index or name plus index, and treat a problem for a disabled evidence field like an unmatched one, or accept that for now.
