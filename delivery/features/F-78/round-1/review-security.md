## Summary
- The server enforces who may complete a milestone, so the UI does not need to. Both the options read and the POST call `require(..., 'milestone.complete')`, and the POST checks it again under a row lock (`lock_case`, `guard_complete`). Removing the client `useMe` check does not open anything: unauthorised users get 403/404 and the page shows "isn't available to you".
- LB-2 is still open and belongs to the backend. The server checks an explicit `milestone.complete` grant, not "is the PMO Lead". No staff role gives that action, the PMO Lead included. Details under Notes.
- Duplicate completions are prevented on both sides. The client blocks a second press while one is in flight and never resends after an uncertain result. The server checks the revision under `select_for_update` (409 on mismatch), enforces `UniqueConstraint(case, name)`, and runs the whole write in `transaction.atomic`.
- CSRF is enforced by Django `CsrfViewMiddleware` with no exemption. The shared client sends `X-CSRFToken` from memory only. File type is never taken from the client: the write accepts only a real PDF (magic bytes plus a strict pypdf parse) that is the caller's own upload on this case.
- Two non-blocking findings: the server accepts any milestone name taken from the URL, and the page tests do not assert the CSRF header. Nothing blocks.

## Notes
- **LB-2: what the server does.** `require()` (`apps/identity/services.py:28-43`) passes only in one of two cases. (a) The user holds an active per-case `Grant(action='milestone.complete')`, and `legacy_projects` lets it count. For a project, it counts only when the user has no `StaffMembership` at all, or has an active `admin`/`cto`/`ceo` membership on that case. (b) `role_cases` finds a lead role whose actions include `milestone.complete`. None does: it is missing from `LEAD_ACTIONS['pmo-lead']` and from every `DEPARTMENT_READS` set (`apps/identity/factory_access.py:13-36`). So no "PMO Lead" check exists. A role-managed PMO Lead without an admin/CTO/CEO membership gets 403 on the options read (no link, "isn't available" page). A legacy account with no memberships and a grant can complete whatever its role. This existed before this change and is not made worse by it. The UI follows `can_complete`, the 403 and the 404 and invents no role rule, as the spec requires. It belongs in the PR body (criterion 20) and in `backend-questions.md` LB-2, which already has it.
- **`can_attach_pdf` and the write can disagree (backend, pre-existing).** `can_attach_pdf` uses raw `active_case_grants(..., ['evidence.add'])` (`project_operations.py:199`). The write uses `require(..., 'evidence.add')` via `owned_pdf` and `add_evidence`, which is role-aware and filtered by `legacy_projects`. The PDF zone may appear for someone the write then refuses, or the reverse. The write still enforces, so access is safe.
- **Removed `useMe` check.** It only affected display. Access to the options read, the project read and the re-read is all checked on the server, and the page's metadata title names neither the project nor the milestone. The URL name is shown only after an authorised options read succeeds.
- **Upload handling.** `POST /cases/{id}/files` (`apps/agents/upload_views.py:25-37`) requires `evidence.add`, is capped at 5 MiB and accepts any type. On the write, `owned_pdf` (`apps/core/factory_api/work_proofs.py:34-39`) requires the upload to belong to the caller and this case. `pdf_bytes` (`apps/workflows/factory_ppe_opening.py:42-62`) then requires a `.pdf` name, a `%PDF-` header, a strict parse and no encryption. The shared lane C `EvidencePicker` checks client side for `.pdf/.png/.jpg/.jpeg/.eml` up to 10 MiB, while the spec says ".pdf only" up to `PROOF_MAX_BYTES`. A PNG or a 7 MiB file is refused by the server with a 422, so this is a UX/QA point, not a security one.
- **Ownership of `evidence_id`.** The write filters `public_evidence(case.evidence.filter(kind='completion'))`, so evidence from another case or private evidence returns 404.
- **Error text.** 403, CSRF, 400, 413, 415 and 429 use fixed client wording. A 422 shows the server's `ValidationError` sentence (for example "Milestone identity must be nonempty and unique" or "Choose a valid PDF proof file."). These carry no ids, emails, tokens or stack details; some wording is technical, which is a UX point. Unhandled exceptions are not caught by `endpoint`, so Django's 500 handler runs and the client shows its own uncertain wording.
- **Mock differs from live.** Mock `name_in_use` on POST returns 409; live returns 422 `action_unavailable`. This is not a security issue. It is worth an integration smoke check (criterion 19).
- **Open redirect.** `SignedOutState` builds `next` from `/projects/<encoded caseId>/milestones/complete?name=<encoded>`. `safeNext` (`src/shell/signInNext.ts`) rejects `//`, backslashes, control characters, dot segments and routes outside the frame. I found no open redirect.
- **XSS.** URL and server text is rendered as React text. Hrefs use `encodeURIComponent`. The diff adds no `dangerouslySetInnerHTML`, `innerHTML` or `window.location` writes.
- **Secrets and dependencies.** The diff adds no secrets, storage writes or logging. The mock CSRF values are fixture data. No package or lockfile changes.
- **Abuse.** The write needs a signed-in user with a grant, and its only effect is an internal `Outbox` row with a narrow payload. Nothing outbound and no anonymous path, so no rate limit is needed for this change.
- **Run.** `npx vitest run tests/milestone-complete.test.tsx`: 25 passed. I ran no backend tests, because they need test-database writes.
