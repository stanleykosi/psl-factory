## Findings
- TECH-1-1 | blocking | medium | frontend | A stale record whose cause is the case revision can never succeed with another press. The `useEvidenceUpload` hook keeps `revision.current` from the last upload, and `caseRevision()` prefers it over the item's (`frontend/src/features/response/useEvidenceUpload.ts:53,71,162`). After an E-RESPONSE 409, `afterRefusal` → `reread` → `settle` puts the reloaded item into the form (`frontend/src/features/response/useResponse.ts:142-155,117-128`). The item's new `case_revision` reaches the hook as a prop, but `revision.current` still overrides it. So the next press sends the same stale `case_revision` (`useResponse.ts:203-204`), and the mock (`frontend/mock/response.mjs:144`) or the backend answers 409 again. This happens whenever someone else uploads to the same case: W-1601 and W-1608 share C-1601 on purpose, and so would another task or the reconcile proof on that case. The page tells the user "Check the details and record again", but pressing again can only fail. The hidden way out (remove the proof and add it again) is not something a user would find. Expected: after any reload in the record flow (stale, 403, uncertain-open), the hook carries the reloaded item's `case_revision`. The already-uploaded evidence ids stay valid because evidence is append-only. For example, a `proof.sync(item.case_revision)` that `settle` calls, the same way the upload 409 path already does at `useEvidenceUpload.ts:91`. Add a component test: the upload returns 5, the record answers 409, the reload has `case_revision` 7, and the second press sends `case_revision` 7. The existing 409 test (`frontend/tests/response.test.tsx:557`) stops after the first press, so it doesn't cover this.
- TECH-1-2 | non-blocking | low | frontend | The header comment of `frontend/src/features/work-item/WorkItemOverview.tsx:1-2` still says "Read-only; the only link that leads to an action is "Open the decision"". The file now mounts `ResponseEntryLink` and a `ReconcilePanel` that writes through E-WORK-ACTION. Update the comment so it matches the file.
- TECH-1-3 | non-blocking | low | frontend | When the page is opened on a task that is already recorded, `load` builds the done view without a `responderId` (`frontend/src/features/response/useResponse.ts:86`). The success eyebrow then drops the organisation, and the heading uses the item's station after the move, not "the station that was current before recording" (spec section 7). build.md lists this as a decision. It doesn't happen after a press, but a reader of a recorded task sees "REL-0077" and "Go-live readiness" instead of "REL-0077 · LAGOON HEALTH" and "Client UAT response". Accept it as a decision, or use the single responder when there is exactly one, and raise the station name with the backend as a `recorded` field.
