## Summary
- The shared footer, `usePagedRows` and the Table frame are sound: rows grow and trim in place, shown rows keep their DOM nodes, the disabled-option rule is right where the total is known, and no contract parameter is invented (every `limit` sent is declared by its operation; Setup Rules and Templates send none).
- Blocking: after every send, start or ended working conversation the assistant list re-reads page 1 and drops the pages already loaded, which breaks D-138 ("the shown conversations never reload") (TECH-1-1).
- Blocking: Projects and Payments do not pass the total the contract returns to the footer, so the count reads "N showing" and the inactive rule is missed while a cursor remains (TECH-1-2).
- Non-blocking: the automatic top-up has no stop on an empty page that carries a cursor; the page-size rounding over-fetches; the focus hand-off is a module-level global; a few per-list wrappers and a stale comment remain.

## Findings
- TECH-1-1 | blocking | medium | frontend | After a send (useSend.ts:67, 80, 99, via ThreadPage.tsx:35), a start or an ended working conversation, `useConversationList.refresh` (useConversationList.ts:27) replaces `items` with the first page only and sets `next` from it, so every later page already shown is dropped and the list jumps back to 10 rows. Expected (spec AC8, D-138): "the shown conversations never reload"; the rows already shown stay in place, the first page's rows are merged at the top (the same idea as MyWork's `mergeRefresh`), and the loaded later pages and their cursor are kept. Actual: the person who scrolled to row 45 and sends a reply loses those rows, their scroll place, and has to fetch them again.
- TECH-1-2 | blocking | medium | frontend | Projects (ProjectsList.tsx:190) and Payments (PaymentsView.tsx:288) call `usePagedRows` without `total`, although E-PROJECTS and E-INVOICES return a top-level `total` (schema.d.ts E-PROJECTS, E-INVOICES). Result: while a cursor remains the footer reads "10 showing" rather than "10 of 74 showing", and the 20 and 50 options stay active when the list's total is at or below them (for example 15 invoices with 10 loaded keeps 50 active), where the spec says an option is inactive when the total is at or below the next smaller option. Expected: pass the same total the result count already uses (ProjectsList computes it at about line 296 from `list.total` or the tab count; Payments reads `body.total`), as NotificationsPage.tsx:144 already does. Owner: frontend.
- TECH-1-3 | non-blocking | medium | frontend | ShowMore.tsx:63 tops up automatically whenever `missing > 0 && next && !busy && !failed`. A page that returns zero rows while still giving a cursor leaves `missing` unchanged, and the `busy` true-to-false change re-runs the effect, so the same cursor is requested again until the cursor runs out, or forever if the server echoes it. Exceptions is filtered by grants after the query, so empty pages are plausible. Expected: stop the automatic top-up after a page that adds no rows and leave Show more to the person. Owner: frontend.
- TECH-1-4 | non-blocking | low | frontend | ShowMore.tsx:24 (`limitFor`) rounds the missing rows up to the next allowed size. From 20 shown to 50, 30 missing rows request `limit=50`, so 20 rows load unseen. The spec says only the extra rows are fetched; the contract accepts only 10, 20 or 50, so an exact fetch would need two calls (20 then 10). Accept and note it in the build, or split the request. Owner: frontend.
- TECH-1-5 | non-blocking | low | frontend | ShowMore.tsx:105 (`let focusSize`) is module-level. It is cleared only when a matching option is drawn, so if the footer unmounts after a choice, the next footer that mounts on any list takes focus. Expected: keep the pending focus per footer instance (a ref) and drop it on unmount. Owner: frontend.
- TECH-1-6 | non-blocking | low | frontend | features/projects/model.ts:61 says `limit` is left out "when 20"; the default is now 10. Owner: frontend (docs).
- TECH-1-7 | non-blocking | low | frontend | Per-list paging wrappers and failure notices remain: `.my-work__foot` (MyWork.tsx:391) and `.projects__foot` (ProjectsList.tsx:278) carry their own CSS and each list writes its own "couldn't load more" Callout with different wording (MyWork, Projects, Exceptions, Notifications, Clients, RecordPicker). Spec: "no list draws its own paging markup or CSS". Expected: one shared failure notice owned by the footer or a shared component, or a note that the wording stays per list (spec: "don't change wording"). Owner: frontend.

## Notes (taste and checked items, not findings)
- Checked and fine: `usePagedRows` grows and trims without refetching shown rows; the auto top-up is gated by `busy` and `failed`; Show more after a failure retries the same size; focus after Show more lands on the first added row on Projects, MyWork, Clients and Payments; the unit tests cover same DOM nodes, trim without fetch, the 3-row and 15-row cases and the busy state (tests/components/show-more.test.tsx).

- Setup Rules and Templates reveal 10 of the server's loaded page instead of sending `limit`, because their operations declare no `limit`. This matches the builder's stated exception and "no contract change"; the server's default page size is not visible to the reader.
- Tests: no `.skip`, `.only`, `todo` or `fixme` added. Removed assertions in the diff are the old 20/50 defaults, the dropdown, the "earlier entries" button and the old footer text. Not checked line by line.
