## Summary
- The issue's work item, reached from the Issues register row's `work_id`, draws the F-17 line workspace in four states: in progress, no response, no owner, follow-up verified. It is a thin view over `workspace` (facts, severity, a "What has happened" timeline, "Chasing", the agent note, "Next") with three writes: post an owner update or record a reply (E-WORK-STEP), set an owner (E-WORK-ASSIGN).
- Every control is drawn only when the response sends it (step or `assign`); no role, `/me` value or state name grants one. The state and tone come from the backend; overdue status is never worked out from dates.
- Writes carry CSRF, `expected_revision` as read, and (steps) a fresh `idempotency_key`. A failed, timed-out or uncertain write never says "recorded"; the item is re-read first.
- Unknown values read "Unknown". Agent text is shown as returned and never counts as a verified output. Nothing closes, reopens or re-grades an issue: that stays in the register.
- New in this feature: the assign form (E-WORK-ASSIGN is not yet used anywhere in `frontend/src`), the `starts_line` button, four fixtures, the E-WORK-ASSIGN mock handler, and the stale project tab bar fix (Conflicts 8). Contract mock only.

### E-WORK-STEP `POST /api/v1/work/{work_id}/steps` (post update, record reply)
- **Request:** `{expected_revision: workspace.revision, step: <steps[].key>, inputs: {update_type, update} | {reply}, note?: string, idempotency_key: <UUID, new per press, reused on a manual retry of the same press>}`, header `X-CSRFToken`. Built by the existing `useWorkspaceStep`; no new write path. The `inputs` contain only the fields the step lists; `update_type` is one of the step's `options[].value`.
- **200:** `outcome: done` → the re-read item is drawn (the new timeline item and any changed status come from the re-read, not the 200 body), the polite notice from the response's `message` or the F-17 default "Done: …"; focus returns to the step button's section heading. The timeline item shows the backend's own attribution, e.g. "Owner update · recorded by PM", never composed by the page.
- **Errors:** 401 → signed-out; 403/404 → not-open view, same for both; 409 → re-read, the stale sentence, entries kept, next press sends the new revision, no automatic resend; 422 → messages under the named fields (`fields[]`), top summary, focus to the first, entries kept; 5xx / network / timeout → "Not recorded" problem notice with Try again (same key) after a re-read; an uncertain result (`outcome: uncertain`) → never "recorded", the reconcile panel from the re-read item.
- **Idempotency/versioning:** one send per press; a double press sends one; a retry after a failure repeats the same key; a stale `expected_revision` is a 409.

### E-WORK-ASSIGN `POST /api/v1/work/{work_id}/assignment` (set an owner)
- **Request:** `{expected_revision: workspace.revision, person_id: <assign.candidates[].person_id>, note?: string (≤ 2000)}`, header `X-CSRFToken`. No idempotency key (not in the typed body); one send per press, a double press sends one; a repeat press after an uncertain result is refused until a re-read shows the owner (so a second assignment is never sent blind).
- **200:** `{work_id, state, revision, assigned_to}`: the item is re-read; the lead, status and `next` come from the re-read (the page does not change the state from the 200 body). Notice "Owner set: <assigned_to>" from the response; focus to the page heading.
- **Errors:** as E-WORK-STEP (401, 403 and 404 alike, 409 stale with re-read, 422 with `fields[]` under "Owner" or "Note", 5xx and network with a re-read before Try again).
- **Permission and tenant:** the form exists only when the response carries `assign` with at least one candidate; with `assign` but no candidates the section reads "No one can be chosen yet." and no control. The page never filters candidates or reads `/me`.

### Screen states (every board state has these)
- **Loading:** the existing skeleton. **Empty:** a workspace with no sections draws only the header and the status ("Nothing here yet." from `WS_TEXT`). **Error:** the problem card with Retry. **Success:** the four fixture states above.
- **Restricted / unknown:** an item or section with `restricted: true` draws "Restricted" and its content is never shown; an absent age, owner or date reads "Unknown", never blank or 0.
