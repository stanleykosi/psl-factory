# Log a received RFP and assign its accountable PM through the live API

> Tasks: FE-CONNECT-1. Architecture: v9, contract API 1.24.0 (`contracts/psl-factory.openapi.json`; manifest digest not re-verified by the spec writer, readiness did not check it either). Revised under D-185; the earlier 1.22.0 text is replaced. Design: 13 Nov approval under the recorded exception in `design/review.json`; screens: SCR-23, SCR-24.

## Summary
- SCR-23: the Start work drawer entry for the received bid (registered in F-86's `lines/index.ts`) logs a received RFP with one multipart `POST /received-bids`, the client chosen from `GET /received-bids/organisations`, and confirms by reading the receipt.
- SCR-24: the Assign PM drawer over the Unassigned list reads `GET /received-bids/assignments` and `GET /received-bids/{case_id}/assignment`, and assigns with `POST /received-bids/{case_id}/assignment`. "Assigned" shows only after a re-read.
- 1.24.0 now serves the Note (`note`, returned on the receipt) and the Assign PM `next_steps`, so both are built as drawn (D-185). Two changes from the boards remain, forced by the contract: proof and reason are required on Assign PM (LC-Q7), and the nominee's role and hint are not served (see Conflicts with the boards).
- Proof on Assign PM is either a listed proof or a file uploaded through the F-85 picker and sent as `upload_id` with `checked: true` (answers §1).
- Frontend only. No backend change. Sizing: one PR; if the work spreads beyond the two forms and five calls, split SCR-24 into its own PR.
- Builds after F-85 (shared evidence picker and per-line adapter) and F-86 (Start work first slice, which also edits `src/features/start-work`).

## Contract

### SCR-23, Log a received RFP
Reads and writes (all under `/api/v1`):

| Step | Call | Notes |
|---|---|---|
| Client picker | `GET /received-bids/organisations` -> `{items:[{id:int, organisation:string}]}` | The chosen `id` is sent as `authority`. Empty list: say "You can't log a received RFP for any organisation yet." and disable submit. |
| Log | `POST /received-bids`, `multipart/form-data`, header `X-CSRFToken` | Fields: `authority` (int, required), `start_key` (uuid, required), `reference` (1-160, required), `received_at` (date-time, required), `deadline_status` (`unknown`\|`stated`\|`not_stated`, required), `deadline_at` (date-time; required when `stated`, else omit), `note` (up to 4000, optional), `prospect_name` (1-160, optional), `submission_method` (`email`\|`portal`\|`by_hand`\|`not_stated`, optional), `submission_target` (non-empty, optional), `context_attested` (boolean, optional), `document` (file, Word or PDF, at most 5 MiB, required). Response 200 `{receipt_id, case_id, django_url}`. |
| Confirm | `GET /received-bids/{case_id}/receipts/{receipt_id}` | Read `reference`, `received_at`, `deadline_status`, `deadline_at`, `customer_instructions{prospect_name,submission_method,submission_target}`, `note`, `original{filename,bytes}`, `number`, `current`. |

Rules:
- Do not call `GET /lines`, `GET /lines/{line}/fields/*/options`, `POST /work` or the base64 evidence upload for this line. The form's fields are fixed in the frontend; other lines in F-86's Start work are unchanged.
- `start_key` is one uuid generated when the drawer opens (`newIdempotencyKey` in `useStartWork.ts`) and reused on every resend of the same form. It changes only after a confirmed success or when the person changes a field after a failure that said nothing was recorded.
- After a timeout, 5xx or network failure the person gets "Check again", which resends the same body and the same `start_key`. It never silently creates a second RFP. If the status is unknown the words are "Not confirmed. Check before trying again." (as for other Start work lines).
- Fields as drawn: Client (organisation picker), RFP reference, RFP document, Actually received (date and time), Deadline (unknown / stated with a date / not stated), Submission method and Where to submit (optional; board 12 Nov), Note (optional, 4000 limit with a counter), and "Client name as written in the RFP" (`prospect_name`, optional; C-9: it records the captured name only and neither creates nor matches a client).
- `definition` is deprecated and optional: do not send it. `context_attested` is the person's confirmation of the captured client name and submission instructions (C-8). One optional tick-box, shown only when a client name or a submission detail is filled in, labelled "I confirm the client name and submission details above match the RFP.", sent as `true` only when ticked, otherwise omitted. Wording is LC-Q17.
- The file travels in the POST. Show the file name and size; reject over 5 MiB or a non Word/PDF type before sending; a 413 or 415 from the server shows the same words.
- Success: "RFP logged." with the reference and received time read back from the receipt, the file name, the Note when one was saved (read back from the receipt's `note`, C-10), and a link "Open Unassigned" to `/work` (Unassigned list). The new RFP is reached through the receipt and the assignments list; no work id is shown or invented (C-7: a generic work id is unnecessary on this path). If the receipt read fails after a 200, show "RFP logged. We couldn't read the receipt back." with the `receipt_id` kept for a retry of the read only (never a resend of the POST).
- Replay (C-11, LC-4): the same actor, organisation, `start_key` and exact input return the original receipt with 200, so "Check again" after an uncertain result is safe and shows the same success. A second intake with the same organisation and reference is refused with 422 `action_unavailable` and a message; there is no duplicate-specific code, so the screen shows the API's `message` in the error callout (and against a field only when `fields[]` names one) and never tests for a code of its own.
- Errors by status: 401 signed out (existing `SignedOutState`); 403 "You can't log RFPs for this organisation."; 409 or 422 show the API's own `message` (and `fields[]` mapped to their fields), nothing invented; 413 "The file is larger than 5 MB."; 415 "Use a Word or PDF file."; 429 "Too many tries. Wait a moment."; 5xx or network: uncertain, as above.

Screen states: loading (picker loading), empty (no organisations), validation (required-field summary using `ValidationSummary`), submitting (button busy, one write at a time via the existing synchronous guard), error, uncertain, success.

Fixture example (mock, `frontend/mock/start-work.mjs` plus a new `frontend/mock/received-bids.mjs`):
- organisations `{items:[{id:11,organisation:"Northwind Bank"},{id:12,organisation:"Harbour Insurance"}]}`
- POST ok `{receipt_id:501,case_id:"2f0c8a54-6b0e-4f7a-9d1a-0c5b2f6f1a11",django_url:"/received-bids/501/"}`
- duplicate reference: `422 {code:"action_unavailable",message:"This reference has already been logged for this organisation."}` (no `fields`), as the backend answered (C-11).
- replay: the same `start_key` and body again returns 200 with the same `receipt_id`.
- receipt `{id:501,case_id:"2f0c8a54-6b0e-4f7a-9d1a-0c5b2f6f1a11",reference:"RFP-2026-041",number:1,current:true,received_at:"2026-11-20T09:30:00Z",deadline_status:"stated",deadline_at:"2026-12-05T17:00:00Z",customer_instructions:{prospect_name:"Northwind Bank plc",submission_method:"email",submission_target:"bids@northwind.example",source_version:1},note:"Client wants a draft by Friday.",original:{filename:"rfp.pdf",bytes:482113,download_url:"/api/v1/..."}}`.

### SCR-24, Assign the accountable PM
| Step | Call | Notes |
|---|---|---|
| Unassigned list | `GET /received-bids/assignments?cursor=` -> `{items:[{case_id,intake_id,revision,reference,received_at,deadline_status,deadline,owner_access_required}] (max 12), cursor, checked}` | The row key is `case_id`. Rows with `owner_access_required: true` show "You need access to this RFP's owner first" and no Assign button. "Load more" while `cursor` is non-null. The Unassigned queue of `GET /work?queue=unassigned` is not used for these rows. |
| Drawer read | `GET /received-bids/{case_id}/assignment` -> `{bid, setup_required, assignment, roles[], nominees[{id,label}], proofs[{id,label}] (max 26), next_steps[{key,label,api_url}]}` | Opened on a row press. |
| Upload proof (optional route) | `POST /cases/{case_id}/files` (F-85 `EvidencePicker`) -> `upload_id` | `case_id` is the bid's own. The upload is made when the person picks the file. |
| Assign | `POST /received-bids/{case_id}/assignment`, JSON, `X-CSRFToken`: one of two bodies -> 201 `{id, person_id, role, intake_id}` | Common: `intake` = `bid.intake_id`, `revision` = `bid.revision`, `candidate` = a `nominees[].id`, `role` one of `roles[]`, `reason` 1-4000 chars. Plus either `evidence` = one of `proofs[].id`, or `upload_id` (from the picker) with `checked: true`. Never both, never neither. |

Rules:
- Drawer fields: "Accountable PM" (Select of `nominees[].label`, nothing preselected), "You are assigning as" (Select of `roles[]`; shown as plain text when exactly one), "Proof" (required: "Use a recorded proof" chooses from `proofs[].label`, "Upload a file" uses the F-85 `EvidencePicker` with the bid's `case_id`; the person picks one route and the other clears; with no `proofs[]` only the upload route is offered; after an upload a required tick-box confirms it was checked, LC-Q17), "Reason for choosing this PM" (required text, 4000 limit with a counter). Nothing is filtered or chosen by the frontend; the backend names who may be chosen., "Note" does not exist (the contract's `reason` takes its place). The nominee's role and hint are not shown: C-13 says assignment reads return them, but 1.24.0's `nominees[]` carries only `{id,label}` (see Assumptions).
- `setup_required: true` shows "Nobody is set up to assign yet. Ask a PSL admin to finish setup." (plain words, no jargon) and no form. No nominees, with `setup_required: false`: "No one can be chosen for this RFP yet."
- An existing `assignment` (non-null) shows "Already assigned" with the nominee label when `person_id` is in `nominees`, else "Assigned to another person", and no form.
- The POST has no idempotency key. One write at a time (existing `writing` ref guard). On 5xx, timeout or network failure the drawer first re-reads `GET …/assignment`; it offers the form again only if `assignment` is still null, otherwise shows the "Already assigned" state. It never resends automatically.
- Success words appear only after the re-read of the assignment AND the list: "PM assigned: <nominee label chosen>." The row leaves the list only if the re-read list no longer has it; the screen does not assume it will (C-14). Beneath it the "What happens next" block lists the `label` of each `next_steps[]` entry of that re-read, in the order served, as the board draws. A step with a non-null `api_url` is shown as plain text unless the frontend has a page for it; nothing is invented, and no "alerted" sentence appears unless a served label says so. An empty `next_steps` hides the block. The same block shows in the "Already assigned" state.
- Errors: 401 signed-out state; 403 "You can't assign a PM for this RFP."; 404 "This RFP isn't available." with the list kept; 409 (stale revision or already assigned; LC-5 gives no exact `code`, so the screen does not branch on it) "This changed while you were working." and re-read, showing the new state; 422 `action_unavailable` shows the API's `message`; 422 map `fields[].name` (`candidate`, `role`, `evidence`, `reason`) to the field with the API's message; 413/415/429 as for SCR-23 where relevant; other: "We couldn't confirm the PM was assigned. Check before trying again." using the existing unconfirmed copy.

Screen states: list loading, empty ("Nothing is waiting for a PM."), list error, drawer loading, drawer error, setup required, no nominees, already assigned, form, submitting, validation, uncertain, success.

Fixture example (mock): list item `{case_id:"2f0c8a54-6b0e-4f7a-9d1a-0c5b2f6f1a11",intake_id:77,revision:3,reference:"RFP-2026-041",received_at:"2026-11-20T09:30:00Z",deadline_status:"stated",deadline:"2026-12-05T17:00:00Z",owner_access_required:false}`; assignment read `{bid:{...},setup_required:false,assignment:null,roles:["Head of PMO"],nominees:[{id:301,label:"Amara Okoye"}],proofs:[{id:901,label:"Delegation email, 18 Nov"}],next_steps:[{key:"prepare_rfp",label:"The PM prepares the RFP response",api_url:null}]}`. Further fixtures: `setup_required:true`, an existing assignment, an empty `proofs` (upload route only), an empty `next_steps`, the upload body `{...,upload_id:7001,checked:true}`, an empty list and a 409. The `roles` value is fixture text only, not a PSL role.

## Out of scope
- Backend changes, new roles, approvers or business rules; deciding who may assign (the backend names nominees).
- Any other screen, including SCR-25 onward and SCR-16; the generic `GET /lines` path for other lines (F-86); `fileToEvidence` and any file-draft review for Assign PM (the upload goes straight as `upload_id`).
- Opening a work item from the success message (none is returned and none is needed, C-7); finding the RFP in `GET /work?queue=unassigned`.
- Showing the PM's role or hint, "alerted" claims, or any value the API does not serve; following `next_steps[].api_url`; downloading the original (`original.download_url`).
- Editing or re-logging a received RFP, versions and download of the original file, listing earlier receipts.

## Assumptions
- Dropped 1.22-only assumptions: "proof from `proofs[]` only, no upload" (1.24.0 accepts `upload_id` with `checked`, answers §1); "no Note" (1.24.0 stores and returns `note`, C-10); "no next-steps lines" (`next_steps[]` is served); "`context_attested` required" (it is optional and means confirmation of the captured name and instructions, C-8); "duplicate reference is 409 with a field" (it is 422 `action_unavailable`, C-11); "the new item is not looked up" is kept only as a decision, see below.
- Proof upload uses `POST /cases/{case_id}/files` with the bid's `case_id`. Reason: the picker's only route; the answers do not name a bid-specific upload. If the server refuses it for a received bid, the picker's own error words show and the listed-proof route remains.
- The `checked` and `context_attested` tick-box words are LC-Q17 option 1 until answered. Reason: the contract gives no wording.
- Nominee role and hint stay out. Reason: C-13 says reads return the role, but `nominees[]` in 1.24.0 has only `{id,label}`; the answer and contract disagree, so nothing is drawn that is not served. Add them if the contract gains the fields.
- Submission method and target are optional on the form. Reason: the contract marks them optional and PSL gave no rule for when they are required; the server's message shows if it refuses.
- The Log RFP entry opens even though `/lines` may not list it (ownsSubmit, Lanes). Reason: A-25 says the received bid has its own endpoint; the key to register is `received-bid`, to be confirmed against the live `/lines` at build.
- Labels: "Proof" stays and the new field is "Reason for choosing this PM" (C-12: label it as the reason for the assignment). Reason: the design had "Note".
- `prospect_name` is free text, optional, labelled "Client name as written in the RFP" (LC-Q8 option 1). Reason: C-9 confirms it only records the captured name.
- Success after logging is read back from the receipt and links to the Unassigned list. Reason: C-7 answers that the receipt and the assignments queue are the path.
- Size and type limits (5 MiB, Word or PDF) come from the OpenAPI field description for `document`.
- Row-level "needs access" wording for `owner_access_required` is frontend copy only.

## Conflicts with the boards
- SCR-23 Log RFP: the board draws a client picked by name; this spec makes the picker an organisation delegation and adds an optional "Client name as written in the RFP". The Note, the submission method and target and the deadline choices are built as drawn (1.24.0 stores the note). Adds an optional confirmation tick-box (`context_attested`, LC-Q17). Recommendation: accept (LC-Q8 option 1 for the client pair).
- SCR-23: the board's success sentence opens or names the new work item. This spec shows the receipt (reference, time, file, Note) and a link to the list, because no work id exists on this path. Recommendation: accept (LC-Q9 option 1).
- SCR-24 Assign PM: the board draws Proof as optional and a Note. This spec makes Proof required (a listed proof or an uploaded file with a required "checked" tick-box) and replaces Note with a required Reason (LC-Q7 option 1). The "What happens next" block is built as drawn from `next_steps[]`, but without the nominee role and hint, which 1.24.0 does not serve. Adds the setup-required, already-assigned and no-nominees states, which no board draws. Recommendation: accept the required proof and reason; the new states and the upload-or-choose proof control need a board from the design engineer.
- SCR-24 list: rows gain a "needs access" state (`owner_access_required`) and "Load more", neither drawn. Recommendation: accept, small additions that follow the board's row style.
- Questions: LC-Q7, LC-Q8, LC-Q9 (answered, D-182) and LC-Q17 (new, confirmation wording) in `delivery/connect/questions-batch.md`.
