# The app frame loads from the live API: live types and client, session and error handling, role words from role-dashboard

> Tasks: FE-CONNECT-1 part b. Architecture: D-API-STYLE r3 and D-AUTH r3 as built (package v8, D-172); live contract `contracts/psl-factory.openapi.json` 1.22.0. Design: current approved canvas under the D-173 exception; screens: SCR-01 frame (CMP-01 top bar, phone bar), frame states (loading, signed-out, forbidden, error, no sections).

## Summary
- The frontend gets generated live types (`src/api/live-schema.d.ts`) with a drift test, and a live-typed client beside the v7 one. Screens other than the frame keep the v7 client and mock.
- Session and errors follow the live contract: `GET /session` gives the token before sign-in and after a stale token; 403 `csrf_failed` is its own error kind, refreshes the token and tells the person to press the action again (a write is never retried); 400, 413, 415, 429 and 503 get their own kinds; 422 keeps `fields`; `idempotency_conflict` replaces `idempotency_key_reused`.
- The frame (AppShell, TopNav, PhoneBar, HomeRedirect, DestinationPage and every `me.destinations.includes` caller) reads live `GET /me`: destinations are `{key,title,django_url}` objects looked up by `key`; `django_url` and `work_desk_url` are never used.
- Role words come from `GET /role-dashboard` `positions[].name`. If that read fails or is empty the bar shows the name alone.
- The mock `/me` moves to the live shape and is validated against the live contract. The mock also serves `GET /session` and `GET /role-dashboard` in the live shape, so the design engineer's app on port 3000 looks and behaves as today.

## Contract

### Generated types and clients
- Add script `gen:api:live` in `frontend/package.json`: `openapi-typescript ../contracts/psl-factory.openapi.json -o src/api/live-schema.d.ts`. Commit the generated file.
- Drift test `tests/api-live-schema-drift.test.ts` (same pattern as `api-schema-drift.test.ts`): regenerated output equals `src/api/live-schema.d.ts`; the `gen:api:live` source is the same file the live-contract validation in the mock tests reads.
- `src/api/client.ts` exports `liveApi = createClient<livePaths>` with the same `baseUrl`, `credentials`, fetch wrapper and the same `csrfMiddleware`; `call` accepts results from either client. One module-level token is shared. `api` (v7) is unchanged for other screens.
- `src/api/types.ts`: `Me` and the destination type derive from `live-schema.d.ts`. Add `DestinationKey = 'my_work' | 'projects' | 'overview' | 'setup' | 'clients' | 'assistant'`. Types for work items, decisions and the rest stay on v7.

### Session
- `GET /api/v1/session` (liveApi, no auth) returns `{csrf_token, signed_in, next_url}`. New exported helper `refreshSession()` in `client.ts` calls it, runs `setCsrfToken(csrf_token)` and returns the body. It is called (a) when `GET /me` answers 401, (b) after a `csrf_failed`.
- `AppShell.load()`: calls `/me` and `/role-dashboard` (page 1) in parallel. `/me` success: `setCsrfToken(me.csrf_token)`, state ready; the frame never waits for role-dashboard. `/me` 401: call `refreshSession()` (so the token is ready for the later sign-in screen; its own failure is ignored), show the signed-out state. If `refreshSession()` returns `signed_in: true`, reload `/me` once instead.
- Sign-in, sign-out and recovery screens are not built here (SCR-17, wave 1). The signed-out state has no sign-in link and no link to any `/accounts/` or Django page.

### Errors (`src/api/errors.ts`)
`ApiErrorKind` becomes `unauthenticated | forbidden | csrf | not_found | stale | invalid | rate_limited | read_limited | bad_request | too_large | unsupported | server | network`. `errorFromResponse(status, body)` maps:

| Status and code | kind | Message shown (client wording; body message ignored for these) |
|---|---|---|
| 401 any | unauthenticated | body message |
| 403 `csrf_failed` | csrf | "Your session was refreshed. Press the action again. Nothing was changed." |
| 403 other (`forbidden`) | forbidden | body message |
| 404 | not_found | body message |
| 409 (`stale_version`, `stale_evidence`, `conflict`, `idempotency_conflict`) | stale | body message; `code` kept |
| 422 | invalid | body message; `fields` always kept, `[]` when absent |
| 400 | bad_request | "We could not read that request. Reload and try again." |
| 413 | too_large | "That is too large to send." |
| 415 | unsupported | "That kind of file or request is not accepted." |
| 429 | rate_limited | "Too many requests. Try again shortly." No retry-after value is shown or read. |
| 503 `read_limited` | read_limited | "This needs a closer look and could not load. Try again shortly." |
| 503 other, 5xx, other | server | existing "Something went wrong." handling |
| fetch failure | network | unchanged |

- `ApiError` gains `fields: {name: string; message: string}[]` (default `[]`). `call()` must carry `fields` from the body for every 422 so callers no longer need the `postStep`-style reader. Existing callers that read `fields` keep working.
- `call()` on `csrf`: runs `refreshSession()` once, then throws the `csrf` ApiError. It never repeats the original request. If the refresh itself fails, still throw the `csrf` error.
- 429 and 503 on a write are never retried automatically.
- `useStartWork.ts`: replace `idempotency_key_reused` by `idempotency_conflict`. Keep the present message handling.
- Anything that branched on `kind === 'forbidden'` to mean "csrf_failed" must now see `csrf` separately. Existing call sites in the grep list (`DecideView`, `useDecision`, `useResponse`, `BillingContactForm`, `ClientsList`, `ClientDetail`, `useConversation`) keep treating `forbidden` as no-permission and show `csrf` as a try-again notice through their existing generic error path (no new UI).

### Role words
- New `src/shell/useRoleWords.ts` (or inside AppShell): reads `liveApi.GET('/api/v1/role-dashboard')` once per page load alongside `/me`; result `string | null`: unique `positions[].name` values in first-seen order joined with `", "`; `null` when the read fails, the list is empty or every name is blank.
- `TopNav` draws `{name}` and, only when role words exist, ` · {role words}` in the existing `.shell-who-role` span. `PhoneBar` menu draws `<small>` only when role words exist. Below 1080px the visually-hidden-but-accessible behaviour of the role stays. The Setup frame text that quoted `me.roles` reads the same hook (no other `roles` use of `/me` remains).
- A failed read never shows an error, a toast or an invented role.
- While role-dashboard is pending the bar shows the name alone; the role words appear when it resolves.

### Screen states of the frame
| State | What shows |
|---|---|
| Loading | `LoadingState` skeleton; bars show brand only (as today). |
| Signed out (`/me` 401) | `Callout` warning "You're signed out." plus one line "Sign-in opens in a later release. Ask your administrator if you need access now." No link. Menu hidden, bell and Start work hidden. |

## Assumptions
- Role words are the de-duplicated `positions[].name` values joined by ", ": `name` is the backend's own label per role and mode, and several workspaces repeat it.
- Role-dashboard page 1 only: the frame needs words, not completeness; a person with more than 50 positions is not a case for this release.
- Role-dashboard is read in parallel and may arrive after the name: it can be slow (query-limited), and the frame must not wait for it.
- The csrf message and the signed-out line are client wording written here because the sources give none; the design engineer should read them.
- Mock `work_desk_url` and `django_url` use the fixed `/retired/`: the contract requires a non-empty string and the tests prove it is never used.
- The mock keeps per-persona destination subsets in the live shape, so today's design review is unchanged; live always lists six.
- On a 401 `/me`, `GET /session` is called to prepare the token for wave 1 and to catch a session that appeared meanwhile; its failure is ignored.
- 403 `csrf_failed` on `/me` gets one session refresh and one `/me` retry (a read, so safe); writes never.
- `PSL_FRONTEND_ORIGINS` is set to the `next start` origin for the live run because the backend rejects writes from an unlisted frontend origin (connection map).
