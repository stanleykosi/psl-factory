## Findings
- TECH-1-1 | blocking | medium | frontend | A failed session read after a successful accept is reported as a failed set-up. Expected: once accept has returned 201, the page says the account was created (the ready state, "Sign in with <email>."), because the account exists whatever the session read says (AGENTS.md: reconcile uncertain effects; spec "After set-up"). Actual: `refreshSession()` at `frontend/src/features/join/JoinView.tsx:129` sits inside the same `try` as the accept, so its error goes to the accept-failure `catch`. A 5xx then shows "Set-up isn't working right now. Try again in a moment. Nothing was changed.", and a network error shows the connection message, both with the form still showing. `token.current` was already set to `''` at line 125, so pressing Finish setup again sends `token: ''`. That comes back as 422 `invalid_input` on `token`, and the callout shows the field message with no way forward except the small sign-in link. Fix: catch the post-accept session read separately and treat a failure as `signed_in: false`, which shows the ready state. Add a unit case (accept 201, session GET 500 or network) that expects the ready state.
- TECH-1-2 | blocking | low | frontend | The validity line does not use the existing frame date formatting. Expected: spec "Validity line" says to use "the existing Lagos-time date formatting used by the frame". For screens whose board draws no date, that is `formatDateTime` in `frontend/src/components/format.ts` (D-93): "26 Nov 2026 · 15:00 WAT". Actual: a new `Intl.DateTimeFormat` copy, `lagosWhen`, at `frontend/src/features/join/welcome.ts:16-22` prints "26 Nov 2026, 15:00" with no time zone. This duplicates the shared helper and leaves the time ambiguous for someone outside Lagos. Fix: use `formatDateTime(preview.expires_at)`, keep hiding the line when the result is `UNKNOWN`, and update `tests/join.test.tsx:137` and `e2e/join.spec.ts:40`.
- TECH-1-3 | non-blocking | low | frontend | `open()` at `frontend/src/features/join/JoinView.tsx:71-72` sorts errors by kind, without knowing whether the session read or the preview failed. So a 4xx on `GET /api/v1/session` (for example a 400 or a non-csrf 403 from a proxy) shows "This invitation can't be used" rather than the spec's "session read failing: cannot open" callout with Try again. This is unlikely in practice. Splitting the session read into its own `try` would fix it.
