## Summary
- The five work item controls match contract 1.26.0. Reconcile sends `{action, expected_revision}` to `/actions`. Resume and cancel send it to `/control`. Background sends `{expected_revision, enabled}` to `/background` with no `action`. `adopt_profile` and `release_invoice` are never built. A null revision holds every command, and no body ever carries 0.
- `useWorkCommand` holds for the controls row. A double press sends once. After a timeout or 5xx, resume, cancel and both background commands are locked under `id@sentRevision`. They stay locked while the item's revision stays the same, so a background command (live does not bump the revision) stays locked until the page is reloaded. Reconcile is not locked. A 409 re-reads the item and never repeats the press. A CSRF failure refreshes the session once and sends nothing more. Multipart goes through openapi-fetch's FormData path, so the browser sets the boundary.
- One blocking problem is in the shared seam lanes B and D build on. A line's `Actions` is unmounted when its panel re-read fails, and remounting it brings a fresh lock. A line write that timed out can then be sent again at the same revision, without a page reload (TECH-1-1).
- The carried F-85 fixes hold. Descriptor fields win over inputs. `safeHref` refuses `javascript:`, `data:`, `//host` and `/\host`. `useWorkspaceStep` behaves exactly as before on `useWriteLock`.
- The builder's deviations are acceptable: success shown as a toast under D-151, mock ids 4120 to 4123, and `reload` returning the item. One case needs to change: "Sent. We couldn't reload" is a problem, not a success (TECH-1-4).

## Findings
- TECH-1-1 | blocking | medium | frontend | A line form's uncertain lock is lost when its panel re-read fails. `PanelView` draws only the error Callout when `state.status === 'error'`, so `Actions` and the `useWorkCommand` state inside it are unmounted. That state holds the `id@revision` uncertain lock and the unread lock. Pressing "Try again" remounts `Actions` with an empty lock, so a command that just timed out or got a 5xx can be sent again at the same revision. That breaks the spec rule (unlock only on a different revision or a page reload), which the coordinator note extends to every line form. This is the likely path, not an edge case: `useWorkCommand`'s own uncertain branch calls `reload()`, which bumps `attempt` and re-reads the panel against a server that has just failed. Two ways to do it: keep `Actions` mounted on the last good readback when a re-read fails, and show the warning above it; or hold the command lock above `PanelView` (per work item). ## Notes
- Locking against repeated effects on the controls row, checked by reading the code. The hook calls `lock(id@sentRevision)` before `reload()`, and `lockedReason` and the `run` guard both use the current `item.revision`. Live does not bump the revision on background, so an uncertain Pause or Continue stays locked until the page reloads, which is what the spec asks. The lock is per command, so Continue is still allowed after an uncertain Pause, and Cancel after an uncertain Resume. Those are different effects, and the spec says "lock that command". `ItemControls` stays mounted through quiet reloads and failed polls (it unmounts only when the page leaves its ready state), so the row does not have the TECH-1-1 problem. Going to History and back mounts a fresh page read, which is effectively a reload.
- `PanelView` calls `adapter.commands(readback, ctx)` on every render. Descriptors and keys are rebuilt each time, which is harmless for sending but gives `commands` a new identity every render. Lanes should not put it in effect dependencies. Memoizing it is cheap.
- Small things. After a 409 whose reload fails, the page still says "Showing the latest version." A 405 (new in 1.26.0) maps to `server` and takes the uncertain lock, which is conservative. A response with a 2xx status outside `successStatuses` also locks, which is conservative. Cancel uses `kind="secondary"`, although `Button` has `dark` and `reject` kinds and the spec asked for the danger variant when one exists (UI lens).
- The deviations are accepted. Success as a toast follows the repo guard D-151 (`tests/no-success-callouts.test.ts`). Mock ids 4120 to 4123 are fine, because 4107 and 4108 were already F-85 fixtures. `reload` returning `Promise<LiveWorkItem | null>` is a superset of the briefed signature and is needed by the forms. The `lines/index.ts` registry calls `registerLineAdapter` directly instead of relying on a side-effect import. Its comment allows both, and the only importers are the page and the adapter test.
- Criterion 21 was checked live only in part: background returned 202 and an unlisted reconcile returned 422. A live reconcile press is still open, which is for QA and the coordinator.
- Checks I ran myself: diff reading, contract body and enum comparison against 1.26.0, the openapi-fetch 0.17 FormData path, and node URL resolution. I ran no tests; the gate passed on this head.
