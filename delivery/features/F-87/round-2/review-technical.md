## Verified

A failed re-read draws the warning and "Try again" above the sections and leaves `Actions` mounted, and nothing resets `ready` to null. The new test ("a line command that timed out stays locked when the panel re-read fails and Try again is pressed") runs this sequence: line POST 500, panel GET 500, Go still disabled, Try again, panel fails again, Go still disabled with "Check the page before trying again.", panel reads again at the same revision, Go still disabled, and `slotPosts === 1`. On the old `PanelView` it fails because the form had been unmounted. The remount part the coordinator asked about does not hold. That is TECH-2-1.
- TECH-1-2 | verified | `LineActionsProps.onAccessLost` is set to the page's `lose` (`PanelView` gets `onAccessLost={lose}`). The doc example passes it to `useWorkCommand`. The slot test checks `typeof props.onAccessLost === 'function'`, and the TECH-1-1 test's form uses it.

The test sends `https://evil.example/...`, `//evil.example/...`, `/api/v1/../admin` and `/other/x`, and none of them reaches the network. - TECH-1-4 | verified | The "Sent. We couldn't reload…" notice is now `kind: 'error'`, so `ItemControls` draws it as a `problem` Callout and it stays while the controls are disabled. The deferred-POST test checks the kind.

The deferred-POST test checks the case: a poll rerender mid-write, then a failed re-read, and `busy` is still true. A poll set but not yet committed at the very moment `reload()` resolves would still slip through. That window is negligible.
- TECH-1-6 | verified | Added tests: a poll mid-write with a deferred POST (criterion 9).
