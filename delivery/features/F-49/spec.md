## What is sent, and what stays held (read first)

- **Sent (to the local mock only):** one E-EVIDENCE-UPLOAD for the RFP document the moment the file is chosen, then one E-WORK-START per press with the uploaded `evidence_id`, the case revision the last upload returned and the start's `idempotency_key`. Nothing reaches a client, the client register, Tola or any outside system.
- **Held, because the backend has not answered:**
  1. Creating a new client (G-23-1). The picker lists existing clients only. A "New client" row exists only when the line carries the mock overlay `allow_new`.
  2. Which case an RFP lives on (G-23-5). The mock names one fixed intake case. The page never says the RFP "has its own case" or "opens a workspace".
  3. Whether a second logging of the same reference is refused, and how (readiness question 3). The page never checks duplicates; it shows only a backend 409 or 422, as returned.
  4. Upload size and type limits (G-23-6): the backend's 422 only.
  5. Where the submission method and target are read back (G-23-4). They are sent; nothing shows them afterwards.
- **Authority:** only from the backend's grant. The line is drawn only when E-LINES returns it (and `/me` `startable_lines` lists the same key). No task is involved, so no `you_can_act` is read here; none is invented. Nothing is derived from roles, the person's name or the persona. 403 and 404 look the same.
- **Unset Setup values are holds.** The page fills in no default for who may log RFPs, no submission method default, no deadline default and no assigner. Anything the line does not supply is absent or "Unknown", never a made-up value.

## Summary
- Start work gains a Pre-sale line, "Log a received RFP". A PMO Lead presses it, chooses the client, types the RFP reference, adds the RFP document, enters when it arrived, how the client wants it submitted, and the deadline state. "Log RFP" starts one work item and lands on `/work/W-3351`, where the RFP shows as Unassigned for F-36's assign panel.
- The document uploads when chosen, by F-47's `evidence` field and upload chain. Nothing is forked. The page sends the case revision the last upload returned and the start's idempotency key. A double press starts one work item. A 409 re-reads the revision and keeps what was typed. After an uncertain result the page re-reads and never resends by itself.
- The deadline has three separate values, Unknown, Stated and Not stated. Only Stated carries a date. Neither of the other two ever becomes a date.
- Authority comes only from the returned line. The page never checks duplicates, never validates "Received" and never claims an agent has read the RFP. Held backend answers (G-23-1, G-23-5) are mock overlays listed in build.md.
- Contract mock only. 390 and 1440, tokens and components only.

### E-WORK-START `POST /api/v1/work`
- **Request:** `{line: "rfp_intake", case_id: "C-RFP-INTAKE", case_revision: <the last upload's revision, else 5>, intake: {client, rfp_reference, rfp_document: "<evidence_id>", received_at: "<ISO instant>", submission_method, submission_target?, deadline_status, deadline_at?, note?}, idempotency_key}` with `X-CSRFToken`. `client` is the option value, or `{new: {name}}` under the overlay. Empty optional fields are left out. Nothing else is added.
- **No browser rules:** "Received" is not checked (the backend refuses a time in the future). The reference is not checked for duplicates, shape or length. The page does not compare the file's name or hash with anything.
- **Start is off** while the upload is running or failed (F-47), while the form is already writing, and after a 422 until something changes (F-05). Pressing "Log RFP" with a required field empty shows F-05's required message under it and sends nothing.
- **201 `{work_id, state}`:** the drawer closes and the person lands on `/work/W-3351` (the mock's `WORK_IDS.rfp_intake`). The work item shows the RFP as Unassigned. The mock also adds one Unassigned row to `pmo_lead`'s list (count one higher) so the person sees it in My work. `/__mock/reset` removes it.
- **409 stale** (the shared fixed case, G-23-5): re-read the revision from E-LINES, keep every typed value and the uploaded card, sync the upload revision, use a new key on the next press. 409 `idempotency_key_reused` shows its message. Scenario: `psl_mock_scenario=stale` as F-05.
- **422:** field messages under the named fields as returned (`client`, `rfp_reference`, `rfp_document` under the document box, `received_at`, `submission_method`, `submission_target`, `deadline_status`, `deadline_at`, `note`), a top summary, entries kept. The mock's sample 422s: a stated deadline with no `deadline_at` answers `{name: "deadline_at", message: "Enter the deadline the RFP states."}` (the G-23-2 fallback); a `received_at` after the mock's clock answers `{name: "received_at", message: "Received can't be in the future."}`; a repeated `rfp_reference` for the same client answers 422 `{name: "rfp_reference", message: "This RFP is already logged for that client."}` as a backend-stated sample (readiness question 3), shown as returned and never pre-checked.
- **5xx, network failure or timeout (uncertain):** F-05's "Check again" with the same body and key, and "If it started, it will appear in My work." Never "logged". `psl_mock_start_work=start_uncertain` applies the start and then answers 500; Check again replays the key and gets the stored 201.
- **Idempotency and versioning:** the key is made when the drawer opens, never when a file uploads. A double press sends one. A new key only after a 409 stale.
- **Provider failure:** there is no provider. The upload's 403, 404, 422, 409, 5xx and network cases are F-47's; the card reads "Not uploaded" and Start stays off.
