# Operations factory implementation order

Phases are engineering order, not authorization gates or scope ceilings. Build every family in guide/11-FULL-PRODUCT.md and the 122-ID matrix. Reorder independent work when useful, recording the reason. Missing business values should not defer the infrastructure that accepts them. Implement each phase as connected factory work from intake to verified output. Lead with production flow, useful agent execution, decisions, exceptions and handoffs across departments, not independent module menus. Retain source constraints and the existing phase order.

## Phase 0: foundation
Inspect existing work; establish repository/versions, Django/PostgreSQL environment, migrations, shared identity/evidence/audit model, workflow/runtime, typed policy registry and build-memory files. Implement mock adapter/provider interfaces and test harnesses.

## Phase 1: first connected path
Build planning/costing/SOW → PMO completion → Finance handoff with real services/UI/agents and recovery tests. Show intake, scoped agent preparation, required human decisions, completed PMO work and the verified Finance handoff receipt/next task. Test rework and recovery within this flow. Review integration quality, then continue. The detailed first-increment guide is not the definition of the full product.

## Phase 2: PMO and controlled documents
Complete project phase evidence, estimates/approvals, delivery, UAT/release references, closure/support handoff, RFP, issues/change/emergency paths; document templates/reviews/publication, shared views, minutes/reports/escalation and timers. Implement runtime policy slots for unresolved authority/calendar/emergency distinctions.

## Phase 3: Finance
Build imports, mapping/formula lineage, management accounts, BU allocation/performance, usage/service billing, three-stage project billing, receipts/allocations/corrections, receivables, forecasts and internal/group reporting. Implement rule providers, configuration UI and synthetic golden tests even where real oracles are unavailable. Missing policy holds the relevant calculation or financial transition, not the module build.

## Phase 4: BaaS — deferred from the current108-process release
Preserve existing BaaS behavior and all14 process identities. This phase follows the agreed PMO/Finance release and is not required to declare those108 process IDs mapped, implemented or accepted. Retain Finance-owned interfaces that consume BaaS reports within Finance scope. Later BaaS expansion covers support, reconciliation, Engineering corrective requests, partners and usage through the same native controls; do not infer queue or funds authority from infrastructure jobs.

## Phase 5: integration and operational readiness
Complete real adapters against verified target contracts; activate/evaluate real model providers; run cross-family integration, access/privacy, recovery, migration/export/restore, load and user acceptance tests. Deliver configuration/deployment/operator runbooks and monitoring. Track provider credentials, target-system access, infrastructure and owner policy as distinct readiness dependencies. These dependencies do not remove implementation work from earlier phases.

## Continuous work
AF13 evidence/owner-validation workflows support every phase. Reusable agents and gateway integration belong throughout the build, not a final chatbot layer. Each increment updates the coverage matrix/build memory with implemented behavior and actual test evidence. Full readiness requires all families, tested adapters/agents, known operational dependencies and clearly reported remaining policy slots.
