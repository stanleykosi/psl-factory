# Plug-in business decisions without stopping the build

Build the configuration infrastructure and dependent module behavior now. Thirteen decision groups remain wholly/partly unresolved; D02 is already resolved and is not a missing configuration slot. Evidence/adapter gaps are tracked separately from owner policy. Never treat every open group as blocking every action in its process.

## Configuration model
Each independently activated component version records component and parent slot/decision IDs, subject scope (organization/project/contract/service), schema version, policy revision, lifecycle (draft/validated/active/superseded/revoked), effective window, source/evidence references, responsible human decision reference, validated rule implementation/version, a typed value and validation findings. The per-component value schemas are in contracts/policy-slots.json.

Use a registry of reviewed deterministic implementations selected by ID/version, not executable text uploaded by a user or generated by an agent. Parameters carry explicit currency/unit/period/basis/precision where relevant. Credentials and personal secrets are not business configuration values. Store sensitive principals by internal reference, not free-text claimed authority.

## Application contract
ResolvePolicy(component, scope, effective_time, expected_revision) returns ACTIVE with validated immutable version and value, or MISSING/INVALID/EXPIRED/REVOKED with exact keys/evidence needed. Evaluate a proposed transition using that policy plus current actor, data and subject versions. Record the policy version used. A missing rule affects only operations that actually need it. Factory views show the exact work item, held action, required rule and responsible configured owner or explicit unassigned owner. Independent work continues. Routing, priority, capacity and service-target rules require typed configuration where needed, not invented defaults. Factory framing grants no policy values or new authority.

Example: a missing payment denominator makes payment assessment UNKNOWN; exception authority missing prevents exception approval. Neither prevents document work, milestone evidence, Finance inbox UI, receipt infrastructure or exception-request tracking. Missing payroll allocation rules prevent a real allocation result, not import preview, rule-configuration screens, lineage, test harnesses or other reports.

## Configuration UX and lifecycle
Provide a decision/configuration workbench: slot description, current status, required fields/evidence, affected operations/processes, editable draft, schema/semantic validation, preview against golden scenarios, review/activation record, version history and rollback/supersession. Activation checks domain authority and actual evidence. Do not install a real approver merely because a person is an administrator. Schema-valid values are not automatically legitimate business policy.

Changing a rule identifies affected outstanding tasks, snapshots and decisions; recompute/reassess through versioned workflows without rewriting historical evidence. Effective dates and stale revisions matter. Different contracts may have different stage schedules; there is no global default split.

## Development and tests
Each unresolved slot gets absent/invalid/synthetic-active/stale/revoked fixtures. Mark synthetic scope explicitly and keep operational resolution from falling back to it. Test both the configured path and narrow runtime hold. Synthetic human role mappings prove infrastructure, not actual authority. Tests may demonstrate future human exception approval using an isolated explicitly synthetic configuration while operational authority stays UNCONFIGURED.

Real financial oracles, sign/currency/rounding conventions and adapter evidence are still needed to validate operational results. The build should nevertheless supply the complete replaceable interfaces and workflows. Track software implemented, configuration missing and real-world validation pending as three distinct statuses.


## Precise limits of configuration
Confirmed invariants are not editable knobs: PMO/Finance ownership, planning-before-signature, human-only payment exceptions, no debt waiver and independent release controls remain code/contract assertions. Only genuinely unresolved values belong in slots.

The envelope schema is contracts/policy-configuration.schema.json. Structured policy parameters are immutable artifact references (schema ID, artifact reference/version and hash); arrays contain registered record references. Validate the referenced contents against registered domain schemas and contextual rules, not only their references. Draft configuration may be incomplete in the UI, but cannot validate/activate until the schema and semantic checks pass.

A missing executable formula, exact oracle or external API contract can still require engineering and evidence. Configuration interfaces localize that future work; they do not promise every unknown can be resolved by entering a number. Track such implementation work honestly while building all unaffected infrastructure.


## Independent activation, not all-or-nothing decision groups
The 13 D groups organize evidence only. Each field component has its own schema reference, scope, implementation/version review and lifecycle. contracts/policy-slots.json provides operation-to-component dependencies; contracts/policy-configuration.schema.json validates one component record. Never require every D-group field before an unrelated operation works.

D13 payment assessment uses denominator/qualifying-funds components without requiring an exception approver. Human exception decision uses authority/validity components, not the assessment configuration as an invented decision prerequisite. D12 stage terms are resolved at contract+stage scope: signed-SOW invoicing does not wait for UAT/completion predicates. D11 publication recipients/templates and hypercare criteria resolve independently. Other per-operation sets likewise separate import from calculation, receipt verification from allocation, and report projection from restatement.

A parent group may remain partly open while several operational components are active. Test this partial configuration explicitly. The operation dependency list covers policy resolution, not a replacement for immutable business guards or actual actor/evidence checks.


## Process-level gaps beyond the consolidated D groups
The 13 open D groups are not an exhaustive schema of every missing field. Supplemental P14-Q01.commercial_costing_rule_oracle covers the missing PMO calculator, formula/rate/unit/margin/tax/currency/rounding/override evidence and golden examples. It is linked to commercial costing processes and requires a reviewed deterministic implementation, not guessed rates. It is not a new consolidated D group. Evidence capture and human decision infrastructure can proceed while actual cost calculation awaits its rule/oracle.
