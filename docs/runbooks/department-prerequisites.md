# Department-owned prerequisite routing (P02)

P02-M01/M02 in the frozen process definition require shared coordination while departments retain decisions. This implementation is an engineering design: a route delivers a request, a receipt captures a source-owned decision reference, and a later observation records current availability/correlation. None creates a PMO approval. Signed-reference text is not cryptographic verification.

## Configure and use

1. Grant actual principals case.read, approval.read and only the required action grants. Configure current D05 role assignments. The exact source owner requires approval.receive, approval.contract and approval.verify. Source inspection also requires `approval.source.read:<system>` on this case. PMO cannot impersonate a configured QA/Product/Engineering/Security owner through broad grants or admin status.
2. Capture requirements and register a delivery candidate. Add approval_request evidence, then capture the exact prerequisite subject at `/cases/<id>/approvals/`. Unknown build/release references stay null. A successor requires the current predecessor and retains history; even a successor on another candidate invalidates old gate use.
3. Use the typed configuration form for P02.owner_routes and P02.evidence_contracts. Activate through the existing policy lifecycle. Exact source owner label, actual principal/role, source system/actor, subject fields, freshness/order, reminder choices and evidence contract are explicit, versioned inputs. The department owner accepts the exact contract with approval_contract_review evidence. This confirms an evidence exchange protocol, not a release or prerequisite decision.
4. Reserve a request. Run `.venv/Scripts/python manage.py work_approval_routes --limit 20`. The implemented adapter delivers into the configured owner's internal inbox at `/approvals/inbox/`. An immutable delivery receipt is not source approval. Remote route mode holds only dispatch until a reviewed adapter exists.
5. Add approval_source evidence in the strict supplied schema shown in the workbench. Capture is available before policy. Exact case/candidate/requirements/build/release and source identity/version must correlate. Same tenant/system/reference/version is globally claimed once, idempotent for the exact same request and payload; conflicting/cross-case claims hold. No inferred duplicate approval is created.
6. Add approval_observation evidence. Only the configured source owner can attest an available supplied reference; it needs source-read access and current role/contract authority. An authorised coordinator may record an unavailable/unknown/not-found read. New receipts/observations, expiry, role/grant/policy changes and contract withdrawal invalidate earlier current use. Negative decisions and unknown defects never become accepted QA exit.
7. Shared HTML/JSON and source inspection recheck current access. P02 source-decision audit entries are omitted from the generic case timeline; immutable source history uses the scoped endpoint. Raw source/observation evidence is omitted from generic evidence display and generic document/extraction agents; it uses the scoped source endpoint. Stored P02 investigations contain bounded request metadata and follow-up questions, with no source body/reference or approval action.

## Delivery and publication connection

Synthetic cases can bind a current owner-referenced observation to the existing gate services. The gate manifest pins request/receipt/observation context. A later access failure preserves the source receipt and prior binding, shows verification unavailable and holds current delivery checks and publication of earlier gate packets. A fresh observation and binding require a new packet/review. Legacy synthetic verification cannot override an active P02 prerequisite. Operational gate export requires an authoritative native adapter; source capture, owner-reference visibility and internal requests remain available independently.

## Recovery

Worker leases are fenced; immutable intent pins subject, route, owner/authority, policies and contract acceptance. Lookup by stable operation key runs before authority checks or resend, allowing a separate worker to confirm a committed receipt after a crash and subsequent sender revocation. Missing receipts require current authority and exact intent. Timeout/connection loss is unknown, never proof of failure. Unknown jobs cannot be cancelled or blindly operator-retried; worker lookup reconciles first. Held work supports an explicit reasoned retry, cancellation or replacement intent. Replacement keeps old job history and creates a new generation. Active/terminal jobs cannot be changed. Reminders require an owner-enabled contract, confirmed delivery, minimum interval and finite budget; there is no invented universal reminder schedule.

## Remaining engineering versus policy

Native authenticated source reads, source-specific signature/version order semantics, remote tool/notice delivery, actual department examples/acceptance and wider operational load/restore/UAT remain engineering/evidence work. Native/remote/unsupported ordering selections hold their dependent runtime action. Actual owners/delegation/absence cover, source systems/access, prerequisite identities, freshness and reminders are owner policy inputs. The fixture is explicitly synthetic; it installs no PSL policy or real appointment. P02 remains partial.
