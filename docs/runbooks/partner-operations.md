# Partner agreements, onboarding and Finance activity

This is a local, bounded B08–B11 implementation. Source-backed boundaries: business/legal owners interpret agreement clauses and decide renewal/notice actions; stage holders confirm onboarding completion; BaaS/Data owners define activity meaning. Reporting activity is not billing approval. ARCH103–107 distinguish these facts from the finite engineering methods and synthetic test evidence.

Open `/cases/<id>/partners/`. Capture `partner_agreement`, `partner_onboarding` or `partner_activity` bounded JSON evidence and register a reference. Agreement sources carry nullable executed_evidence_id/executed_sha256; term validation needs the exact case signature evidence/hash. Versions preserve partner/customer identity and append history. Capture remains available without policy or executed proof. A known notice date remains usable when expiry is unknown; it does not infer expiry. Supplied tracker dates/stages do not create authorised stage history. Sources are declared evidence, not authenticated portal, legal-signature or meter data.

Four typed interfaces use the normal draft/validate/activate lifecycle:

- D04.deadline_parameters / `schema:psl/partner-deadlines/v1`: explicit timezone, expiry-day boundary, calendar-day review method, notice/expiry lead intervals and owner roles. Dates come from human-interpreted agreement evidence; no clause parser or auto-renewal extension. Optional existing action/emergency/issue/reporting namespaces can coexist and retain their validators.
- D09.onboarding_stage_catalogue / `schema:psl/onboarding-stage/v1`: unique stages, one initial stage, exact transitions, terminal stages, actual holder roles, required evidence kinds, elapsed-second clock, explicit pause method, reset-on-explicit-reentry and optional follow-up threshold. Unknown policy/history means unknown age. A new catalogue requires explicit history reconciliation through a source version; it does not reinterpret old events silently.
- D10.audience_projection_rules / `schema:psl/partner-activity/v1`: permitted sources, timezone/month basis, active/excluded event kinds, partial coverage choice, review/sender roles and separation, actual Finance recipient, aggregate columns, retry/lease bounds. Optional existing Finance and forecast namespaces can coexist. The finite metric counts nonexcluded supplied events and distinct nonnull active user keys per product. Duplicate events, unsupported source/product/period and missing active identity remain findings; subset coverage is always disclosed.
- D08.billing_calendar / `schema:psl/partner-meter/v1`: explicit coverage/partner/product/event kinds/unit, supplied-quantity method and partial-coverage choice for Finance meter acceptance. This finite interface identifies the source period and quantity mapping; native billing cadence/calendar variants remain engineering. Active-user/event counts never fill missing meter quantities. Existing price, tax and invoice interfaces remain separate.

Agreement term approval pins exact source/policy/current human role. Renewal review records review_renewal/review_notice/no_action/undecided intention; it neither executes renewal nor sends notice. Register actual executed amendments as new source versions and obtain fresh validation. Position is date-only under the configured timezone/boundary. Unknown expiry/notice remains unknown. Due review triggers can create one owned internal ActionItem per source/trigger, with actual granted owner and explicit deadline. Existing action history handles work/pause/completion; no external communication occurs.

Authorised onboarding entry requires exact stage-owner role, required case evidence and actual chronological timestamp. Pause/resume requires the configured finite rule. Entering another allowed stage starts its clock; return/reentry resets only explicitly. Terminal entry requires configured evidence and produces no further stage follow-up. Reported missing-document lists remain visible alongside actual holder decisions. Full native document taxonomy, portal reconciliation and richer historical clock recovery remain engineering.

Activity report capture/calculation/review are separate. Human approve/return/reject pins the exact immutable report; changed source/policy/overlap or authority holds pending handoff. Reserve Finance delivery and run `.venv/Scripts/python manage.py work_partner_finance --limit 1`. Leases/fences, receipt-first lookup, bounded retries and explicit held-intent recovery preserve actual receipt after lost response or authority withdrawal. A changed report method requires a new report and review; renewed review of the same report can use an explicit new intent generation. Unknown delivery cannot be optimistically cancelled.

`/finance/partner-activity/inbox/` exposes only aggregate selected fields to the appointed recipient with current receive/read grants. It excludes raw user IDs, event IDs, source rows and quantities. Receipt means report delivery only. The appointed Finance recipient separately accepts explicit meter events using current mapping and supplied quantities. SQL-unique tenant/source/partner/event claims prevent duplicate import across cases, atomically with existing BillingUsage intake. Original source/proof/receipt/mapping lineage remains. Existing Finance pricing can prepare amounts under its own rules; missing prices hold amounts, not reporting/import. No invoice, cash or release is created by partner handoff.
