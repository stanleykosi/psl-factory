# Budget, YTD performance and historical rework

Implemented local subset, with proposed engineering interchange and finite algorithms. Source requirements remain in F10/F11/F24-F27. `fixtures/finance-performance.json` is synthetic and never supplies operational defaults.

Open `/cases/<case UUID>/finance/performance/`. Record grants are independent: `finance.read`, `finance.budget`, `finance.seal`, `finance.performance`, `finance.restatement`, `finance.review`, `finance.publish`, `agent.performance`, plus ordinary evidence/policy/document grants. Current configured real roles remain necessary for decisions and publishing. Administrator flags supply no authority.

1. Capture `finance_budget` CSV and separate `finance_budget_approval` evidence. Columns: `entity,period,scope,bu,metric,amount,currency,unit`. Company rows declare `scope=company` and an empty BU; BU rows declare `scope=bu` and an explicit identifier. Amounts are exact decimal strings; blanks stay unknown. Units must match actual output. Monthly rows identify YYYY-MM. Annual rows identify the owner-configured fiscal year key. Select an explicit version family, cadence, actual effective assertion, accounting basis (or unknown), and complete/partial/unknown inventory. Unknown/mismatched budget basis holds only comparable budget values; mixed actual/prior bases cannot be aggregated. Existing unknown metadata is never backfilled; capture a fresh explicit version. Capture works without fiscal calculation policy. Native account/workbook joins are a future adapter variant.
2. In monthly Finance's policy-draft form save D06 source-conventions/v3, retaining source conventions and supplying the `performance` namespace. Define twelve ordered consecutive monthly fiscal periods, year/entity/BU scope and metric labels/units, sum-versus-last-period aggregation, exact monthly or explicit-weight annual method, variance/ratio definition and multiplier, precision/rounding, prior requirement and exact cited oracle scenarios. Annual month weights must cover the fiscal list once and sum exactly to one; no equal-twelfths default. Annual closing-stock treatment is deliberately unavailable until a distinct supported rule exists; monthly stock budgets remain available.
3. D05 decision-actions/v4 adds independent Finance purposes `budget`, `period_method`, `performance`, `restatement`. Each explicitly names a role, actions and preparer-review choice. Configure actual principal assignments separately. Existing monthly/RFP/PMO namespaces remain compatible. Review the budget version and period method under actual authority. Unreviewed previews remain identifiable; approved comparison publication requires current exact reviews.
4. Complete and review an exact monthly formula output in the monthly Finance workbench, then seal it. The seal preserves source/calculation/review/policy/hash history and accepted metric definitions. Later normal month or arithmetic-policy supersession does not recalculate that month's values. Explicit original-policy revocation or current human authority withdrawal still holds use. A first monthly seal needs no restatement policy. Sealing another result for the same entity/month requires authorised replacement.
5. Build a comparison with an explicit fiscal cutoff, included sealed-month IDs, one explicit budget version and optional explicit prior IDs. The actual month set must equal the configured fiscal prefix. A prior set must have the same number of months and precede the actual window; its exact list is retained. Missing/duplicate dimensions, units, currency, metric semantics and required prior inputs become findings/unknowns. Flow metrics sum periods; stock metrics use the selected closing period. Undefined zero-denominator ratios stay undefined. Charts are bound to exact signed values and have a separate scale for each metric.
6. Review the exact performance output under configured Finance authority. D10 projection/v2 selects exact columns (`actual`, `budget`, `prior`, `variance`, `prior_variance`, `ratio`) and whether charts appear for each internal/management audience, along with existing metric/BU/publisher controls. Prepare the controlled Finance report, inspect its public tables/chart projection, reserve and run `work_publications`. Current facts, review, publisher/recipient grants and projection implementation and calculation/basis lineage are rechecked before actual local receipt creation. The recipient view reads only the immutable public payload; it does not fetch internal Finance data. Source/rule/budget/current-period-head changes hold queued publication. Already-created effects reconcile before retry.
7. For historical rework, register `finance_restatement` written rationale. Request replacement of the exact current original by an exact reviewed proposed monthly output. The request records affected performance IDs and old/new BU scope. D10 restatement/v1 explicitly selects BU scope permission and current-only versus explicitly selected original/current history; it always preserves originals and requires a written request. Obtain configured human restatement approval over exact proposal/policy/output review/impact. If affected reports change, make a fresh request. Seal the proposed output with that approved request. The original remains and old queued reports become stale; there is no automatic historical rewrite or publication.

The bounded investigation cites budget/approval/month/oracle/restatement evidence and finds missing/changed inventories. It has no decision, history mutation, dispatch or ledger tools. It is a deterministic local implementation, not real-model or original-workbook validation.
