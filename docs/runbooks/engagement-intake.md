# Engagement, PM assignment and project identity

P03/P16 source behavior: engagement begins before formal project registration; Route A follows a won RFP, Route B a direct client engagement and Route C a Product paper. PMO/assigned PM own the record. P03 creates no additional registration approval. Planning/costing precede signature. Source tracker identifier formats and real owner assignments have not been supplied.

At `/cases/<case-uuid>/engagement/`, granted staff can capture initial route/source/reference without assignment or identifier policy. Route A requires an existing same-case actual won RFP conversion; Route C requires Product input. Unknown routes are not inferred. Source revisions append history; a successor capture makes earlier assignment/registration stale until source-owned updates are recorded.

D11.engagement_assignment and D11.project_identifiers are independently configured typed, versioned supplemental interfaces under existing D11. The workbench accepts draft configuration with source policy evidence; the standard policy workbench validates/activates/supersedes/revokes it. Missing assignment criteria hold assignment; missing namespace criteria hold formal registration. Neither holds initial case/engagement/evidence work. Fixture values in fixtures/engagement-intake.json are synthetic examples, not approved business conventions.

Assignment requires a configured current PMO source role and an existing active target with current D05 PM role and same-case engagement visibility. It is a recorded assignment, not an added approval. Formal registration requires current assignment, actual planning evidence, current configured source role, and the supplied identifier. It requires no signed SOW. The manual adapter validates bounded source identifiers; it does not invent a tracker API or allocate a guessed sequence.

Namespace normalization is pinned to its history. An incompatible format/case/length contract requires a reviewed namespace version. The tenant/namespace/normalized identifier is unique. Cross-case conflicts are held for explicit human identity investigation. Corrections append registration and identifier history; old aliases are not reassigned to another case or silently merged. The internal UUID remains distinct from the formal identifier.

Current assignment/registration evaluates current policy, roles, grants, active users and capture lineage. Historical records remain visible when current acceptance is held. Export creates same-case immutable registration evidence. Linking to an existing delivery dossier uses the ordinary PMO source service and leaves its owner verification/gate controls intact. No deployment or financial action is dispatched.

A01/A04 investigation reports current holds, identifier history and bounded currently visible duplicate-title candidates. It exposes no merge, SQL, shell, permission or financial execution tool. Actual provider-backed model quality is not claimed by this deterministic investigation path.

Actual PostgreSQL test evidence is recorded in BUILD-TESTS.md.
