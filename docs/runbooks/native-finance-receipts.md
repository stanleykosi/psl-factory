# Native Finance receipt verification and companion publication

Engineering capability for the incumbent `InternalFinanceAdapter` handoff contract. PMO completion, Finance invoice/receipt ownership, debt and independent release controls are unchanged. This verifies an internal Finance handoff, not a bank payment, invoice issue, vendor transaction or recovered application activation.

Use the separate fresh cold-control application. From **Destination contracts**, open **Native Finance verification and publication**. Require complete current recovery/archive scope, `finance.handoff.read`, `reconstitution.native_finance.<purpose>` and the matching `reconstitution.domain.handoff.verify|review` action. Fresh deployed purposes, active scoped users and current D05 assignments remain mandatory. Archived users, source text and model output supply no authority.

1. Record same-case Finance-owned `integration_contract` evidence. Select an exact handoff effect from the complete recovered inventory and capture its mapping with a provider reference. Current physical recovery and original Finance projection access are required before reading the one archived row. The original operation and payload are read internally; only their mapping metadata/digests enter the control record. Original operation identity and actual payload SHA-256 are separate from the archived whole-job-row digest. The sole supported source contract is `psl.internal-finance-handoff/v1`, reflecting `apps/pmo/services.py` and `adapters/finance.py`.
2. Configure typed/versioned `OPS.native_finance_receipts`: fresh independent operator/reviewer IDs and D05 roles, provider/store/destination references, payload/time/lease/attempt bounds, observation/review validity and exact synthetic scope. The fixture contains no real values. Validate/activate through the existing configuration lifecycle. Mapping capture precedes this new policy; missing provider/storage criteria hold only dependent actions.
3. Independently provision the current provider registry and marker described below. A restored historical database cannot become current by renaming it. Source/control/target databases, recovery quarantine flags/schema and cold-control identities are rejected. No provider fallback queries the unavailable source or treats recovered historical Handoff rows as current proof.
4. Obtain independent Finance-owned mapping review. Probe the exact original operation/payload in the current provider. Equality also requires the source case and milestone. Missing rows remain UNKNOWN; operation/milestone/payload/case collisions become conflict. Independently review the exact native observation. Credential/identity rotation, current grant/role/policy changes, expiry, mapping successors or changed provider rows invalidate dependent use.
5. Review destination evidence through the existing destination-contract workbench. Capture a companion packet from one exact accepted native observation and one current independently accepted same-plan destination observation. Individual missing/unknown/unsupported prerequisites remain visible; no all-archive readiness is inferred. A companion explicitly covers one handoff. It may describe UNKNOWN/conflict evidence without implying cancellation or retry authority.
6. Independently review the exact packet/store binding. Reserve a stable-key publication and run `manage.py run_native_finance_publications --limit 1` in the fresh control deployment. The worker leases/fences its own jobs and writes one immutable local metadata artifact. Reconciliation checks that original file before effect authority or the original attempt budget. Retry retains original intent/counters; completed receipts and files cannot be overwritten. No archived business queue is drained.

## Deployment registry

`PSL_NATIVE_FINANCE_PROFILE` points to an absolute nonsymlink UTF-8 JSON file with closed top-level `providers` and `stores` dictionaries. No secrets appear in business configuration, artifacts, logs or UI.

Each provider entry contains exactly `database`, `host`, integer `port`, `user`, `password_env`, `credential_revision`, `identity_ref`, `identity_secret_env`, `classification`, `sslmode`, `revision`, and `case_ids` (exact canonical archived Finance case UUIDs). The currently supported independently provisioned database name is `psl_finance_provider_<lowercase suffix>`. Production uses `sslmode=verify-full`; `disable` is permitted only for an explicitly synthetic loopback provider/case. Dedicated password variables use `PSL_NATIVE_FINANCE_PASSWORD_*`. Identity variables use `PSL_NATIVE_FINANCE_IDENTITY_*` and contain base64 of32 random bytes. Both secret values contribute to a keyed binding; changing bytes without changing revisions also invalidates review. No actual password-authentication or least-privilege proof is inferred from a successful local session.

Run `manage.py initialize_native_finance_provider <provider_ref>` from the independently configured control/deployment process (add `--synthetic` only for an explicit synthetic provider). It connects solely to that separately registered provider, refuses quarantine/control markers and any existing provider marker, and creates only `public.psl_native_finance_identity`. It creates no people, grants, Finance receipts or business policy. Bootstrap credentials must be replaced by separately provisioned read-only runtime access with a reviewed revision before operational use; do not infer suitable production database permissions from test credentials.

Verification uses a bounded REPEATABLE READ READ ONLY session and fixed SQL against `public.finance_handoff`. It checks current database/user, the independent marker/secret/version and exact case scope. Operation/milestone lookup and payload equality preserve the existing Finance adapter semantics and expose conflicts without mutation. Native results are classified `native_postgres_finance_receipt`, with `direct_native_verification=true`, `direct_vendor_verification=false`, explicit fixture scope and `password_authentication_proven=false`.

Store entries contain exactly absolute nonsymlink existing `root` and opaque `revision`. A companion store must be separate from archive, restored attachment, gateway and reconstitution artifact roots; nested paths are refused. It receives bounded immutable JSON files named by the publication operation SHA-256. Artifacts contain hashes, accepted observation metadata, destination prerequisite states and false activation/replay/debt/archived-authority flags. They exclude original payload bodies, raw operation strings, keys and paths. File/registry substitution holds rather than overwrites. Receipt-first recovery needs the original store binding but no provider credentials or restored effect authority.
