# Native pilot operation and deployment bindings

Engineering interface. This is not a source-backed owner policy, business approval, native vendor acceptance or live pilot result. Use the current BUILD-TESTS.md evidence for actual verification outcomes.

From a selected pilot contract, open **Native operation and deployment bindings**. Choose a selected participant, registered native operation, exact permitted subject and expected case revision. The ordinary form captures one guard intent; the typed service supports up to20. Select deployment/key revision references, worker families, observation freshness and expected source/schema/database fingerprints. The code does not install credentials, users, grants or owner policy values. A binding is immutable and belongs to one exact contract; changes require an explicit selected-contract successor. Identical payload hashes cannot transfer a binding between contract versions.

Nine native operations have shared read-only guards: PMO baseline preparation, costing/SOW decision, signature and milestone completion; Finance invoice issuance, delivery, correction application and correction-note delivery; BaaS response release/withdrawal. The normal domain service calls the same guard and retains its normal locks, case revision, audit, mutation, uniqueness and effect controls. Evidence, authority, commercial sequence, generated costing, independent Finance review, source freshness and human response authority are enforced by those existing domain functions. The preview does not call a transition and never rolls back a speculative effect.

Results are READY_AT_OBSERVATION, HELD or EXISTING_RESERVATION_SOURCE_RECOVERY. Existing reservations require receipt-first source-owned investigation. None of these results grants business authority or starts work. Other registered policy operations remain explicitly without a native guard binding; a policy-ready result alone is insufficient. Only IDs, hashes, observed heads, configured policy IDs and redacted finding codes leave the native adapter. Private source permissions are checked before projection and again before historical export.

Another currently authorised human may accept/reject/defer the engineering contract with pilot.binding.review. This technical verdict does not approve the underlying business action. The author needs current pilot.configure rights; reviewers need current read/source/review rights. Revoked authority, source/configuration/receipt/build/schema/security changes, stale case revision and contract successors invalidate applicable observations. An accepted engineering binding may still have held runtime guards or unavailable process receipts.

## Deployment-owned role identities

`PSL_PILOT_RUNTIME_IDENTITIES` is a bounded JSON registry of non-secret references. Its schema is enforced by config/pilot_runtime.py and apps/policy/pilot_binding_validators.py. Each key reference names deployment_ref, revision, role, principal_id, exact case_id, synthetic/operational classification, permitted worker families, secret_env, storage_revision, retention_revision and monitoring_revision. The secret_env key must use the PSL_PILOT_ prefix. Secret bytes are read only from the deployment environment. Web and worker references, environment names and actual credential bytes must be distinct. No registry or key is installed by the application UI, fixtures or this runbook.

Current runtime principals must have exact case.read, policy.read, pilot.read and pilot.runtime.observe grants and be selected participants. These are technical observation capabilities; no business role is inferred. Profile case, classification, deployment and revision must match the binding. Rotation changes the current credential/profile identity and invalidates old signatures. Storage/retention/monitoring revision strings remain deployment declarations; they are not physical storage, retention, monitoring or SLO verification.

On the binding page, a CSRF-protected POST observes the actual authenticated web process using its configured web identity. This stores only a signed local technical receipt. To observe an independent worker, an authorised deployer invokes that family's existing native management command with `--pilot-binding <id> --pilot-observe-only` and any required native scope flags. The command's code-owned family identity is used. Observe-only skips its business handler entirely, including for commands with no normal --limit option. Without the pilot flags, existing command behavior is retained. Normal processing with an opt-in binding emits identity evidence before invoking the existing handler; that observation does not prove business effects or replace per-job authorization.

All16 existing leased families are instrumented: handoff, publication, invoice, engineering, partner, approval, supportresponse, supportchannel, ledgerdata, protection, readiness, application, cold, reconstitution, nativefinance and financefollowup. The registry maps each to its exact existing command module; there is no arbitrary family/module/subprocess/SQL/path tool.

Runtime receipt v2 binds source identity captured early at process startup, actual process boot identity, role/family, current physical schema definitions (columns, constraints, indexes, functions and triggers), applied/pending migration heads, actual database endpoint identity hash and redacted Django security findings. On-disk source changes after startup require restart before a fresh attestation; a filesystem hash alone cannot establish loaded code. Legacyv1 receipts remain historical/unverified. The latest receipt for each selected role/family is checked against the current deployment-owned key/profile, current principal rights, loaded-start/expected/current source/schema/database, current security settings and bounded age. A failed latest receipt cannot fall back to an older success. Web and worker process boot identities must be present and independent. The signed phase/mode distinguishes an observation before a normal handler from observe-only handler bypass. The receipt is a deployment-owned instrumentation attestation, not a hardware or third-party attestation.

Read-only preflight capture/export and the bounded A04 investigator reuse the same native projections. They cannot emit runtime observations, invoke workers, install secrets, copy approvals, reserve/retry jobs or restore archives. Operational acceptance stays false. Native archive/isolated recovery must preserve technical history while restored users/grants remain inert and the application remains quarantined.

## Work that remains separate

Unregistered native operation/variant guards, private/document/correction impact adapters, reviewed source/oracle and staff-run acceptance bindings, physical storage/monitoring evidence and source-native vendor adapters remain software/evidence work. Real deployment identities, actual owner policies, vendor access, business oracles, SSO/Security/load/UAT and supervised operating acceptance remain distinct inputs/validation. Do not mark all122 processes accepted or claim no code gaps remain based on this bounded interface.
