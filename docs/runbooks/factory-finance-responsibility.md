# Invoice responsibility routing

This is a bounded engineering implementation for F30 in the connected P34/F29/F30 factory line. It does not define PSL's actual owners or approvers. PMO's P02 source-owned observations and contract consent remain separate.

Intake and evidence investigation continue through the native billing preparation and invoice draft. ACT09 records the exact native publication-packet hash. ACT10 evaluates the current scoped `OPS.factory_finance_responsibility` configuration and native Finance review authority. Accountability nominations do not confer a business role or permission. The only supported strategy in this interface is the existing native single Finance review; unsupported strategies fail validation.

Open **Invoice responsibilities** from the work detail. Nominate the process, routing-activity and policy owners and optionally the responsibility resolver. Each nomination can be explicitly unknown. Actual nominees must be active and have current access to this project. The resolver also needs configuration permission. Save the evidenced draft, validate it and activate it through the existing policy lifecycle. Configuration authority alone cannot approve an invoice.

The version 2 responsibility interface also asks **Who may review invoices?** Choose assigned Finance reviewers, assigned reviewers or configured delegates, or leave the choice undecided. An undecided mode holds the dependent review while invoice preparation remains available. Existing version 1 configurations retain their direct-review behavior; no delegation mode is silently enabled.

The **Invoice delegates** form records the principal, delegate, qualified role bundle, finite authority and qualification dates, permitted invoice decisions, exact currency and maximum gross amount for this project. Blank decisions, currency or amount confer no delegated financial authority. The limit is inclusive; no currency conversion or aggregation is inferred. The principal must still hold current Finance authority and the acting delegate needs current record/action permissions. Preparation and review separation applies to the person actually reviewing. Overlapping qualified matches require an owner to resolve the conflict.

Version 3 adds **Check reviewer availability?** Choose no availability check, require a confirmed available window, or leave the mode undecided. Existing versions retain their prior behavior; an older form cannot silently remove an active availability requirement. The independent **Reviewer availability** record set has available, unavailable or unconfirmed periods with explicit timezone-aware start/end dates. Windows for one person must not overlap; adjacent windows use an inclusive start and exclusive end. A gap is unconfirmed. Availability grants no role, permission or substitute appointment. An unavailable principal may be replaced only by an already qualified and available reviewer or delegate under current native authority.

Availability drafts preserve other windows and require exact current source/replacement identity. Validate and activate the evidenced version separately. A corrected policy does not complete an existing governance wait: its configured resolver must claim and recheck it. Every current or historical availability/delegation version is separately source-authorised; readable successors do not disclose private predecessors. New claims, decisions and dispatch recheck the availability rule and matched record. Actual expiry/withdrawal retains approval history but blocks new effects; original uncertain effects still reconcile through original receipts first.

Drafting a rule neither grants authority nor changes other delegation rows. Replacing a row requires the exact current source configuration and selected rule identity; stale replacements fail. Source access is required to view or copy private rules and operate their lifecycle. Save, validate and activate the evidenced version separately. The ordinary work screen identifies a configured delegate and exposes only currently permitted decisions; private limits remain in authorised configuration. Revocation or actual expiry preserves earlier decisions but prevents their use for a new invoice effect. Reconcile an original uncertain effect through its original provider receipt before considering any new effect, even after authority is revoked.

The review screen leads with names, unknown assignments and current workspace-access status. Each recorded version retains its lifecycle and effective date; a historical nomination does not claim current approval authority. An account with no remaining membership in this workspace is not named from another workspace's directory. Exact configuration and decision references remain in secondary disclosures. Name/access memoisation is local to a single read-only render; commands still recheck native authority.

When opened from work, configuration carries that authorised invoice work identity and bounded queue/search through draft and lifecycle redirects. **Back to selected work** returns to the same work and filter. An unrelated work identity is refused even when the viewer can access its other workspace; arbitrary return URLs are not accepted. Standalone configuration remains available without a work context. No agent execution, policy mutation or financial command occurs from reading these screens.

Missing configuration, missing/revoked nominations or no eligible native Finance reviewer holds the dependent review/publication and creates a deduplicated native governance task. If a currently authorised resolver is configured, that person can claim the wait, correct assignments through the policy lifecycle and recheck them with a reason. A recheck records no approval. If no resolver exists, the work remains unassigned; no creator, administrator or lowest-ID user becomes a default owner. An authorised operator can recheck corrected prerequisites; the coordinator records resolution of the retained wait before routing a new decision task.

Finance approval remains an `InvoiceReview`, bound to the exact invoice version, amount, currency, destination, source evidence and responsibility configuration. Claims, decisions and new dispatch recheck current eligibility. An assignment-version change requires a fresh exact packet and review; old tasks, decisions and original execution allowance remain. The native invoice worker looks up the original uncertain operation before checking permission for a new send, so a positive prior receipt can be retained after ownership changes without authorising another send.

The task also records the relevant native Finance rule and role authority when routing occurs. Claim, decision and visible controls compare that record with current facts; claims serialize through the existing work/case locks. A changed rule or role configuration needs a fresh routed task. The earlier task remains immutable history. Missing or malformed historical authority is held and replaced through current routing, without backfill or presumed approval. An obsolete native review cannot satisfy or repeatedly block the fresh review. Only the verdicts currently configured for this Finance rule appear in the decision form; the native command rechecks them on submission.

Unrelated namespaces in the D05 decision matrix may change without invalidating an otherwise current Finance review. Equality follows the native Finance rule: compare the matched invoice rule and role authority, excluding the whole-matrix identifier. Original uncertain receipt observation still precedes fresh delivery review. This is the existing single Finance strategy; it does not implement broader delegation, staged approvals or quorum.

A stale review shows **Review needs updating**, the changed-evidence/rules/assignments explanation and an **Unassigned** current decision owner. It appears in Exceptions and, for an authorised operator, Needs my attention; Decisions excludes it until updated. **Update Finance review** invokes the existing scoped agent command, retaining the earlier task and creating a current unclaimed wait. It grants no approval. Active processing, original uncertain effects, cancellation and verified history retain precedence. Accounts without execution permission can inspect the explanation but cannot update routing. PostgreSQL and synthetic browser checks verify these boundaries; real-provider operation and independent user acceptance remain unevaluated.

If relevant Finance rule content is restored, an earlier exact native approval may become current under existing Finance semantics. The coordinator can reuse that approval. After verifying exact issuance, delivery and destination receipts, it returns any newer obsolete review coordination waits with a receipt-linked audit event. It preserves their context and claimant history and creates no new approval, invoice or execution allowance. Current matching waits and other task kinds or works are outside this cleanup. Native PostgreSQL tests cover claimed/unclaimed waits and real lock contention with claim release.

Before continuation, this restoration case shows **Finance approval available** and **Continue approved invoice work**. The current configured executor is named only with current same-project access; an unknown or unavailable executor remains **Unassigned**. Work appears in the authorised operator's attention queue and is excluded from Decisions. Reading these screens changes no native task, approval, job or allowance. The existing command rechecks evidence, authority, budget and effects before acting. Original pending/uncertain jobs, leases and cancellation retain precedence. Actual Codex native-browser checks cover this state, keyboard/filter context, narrow layout and agent continuation through two mock receipts and verified retirement; fixture setup supplies the original approval/policy restoration and does not constitute independent user acceptance or a real integration test.

The additive workflows0049 migration expands only the native task-kind guard to include the governance wait. Task kind, packet and source identity remain immutable. It is not a new approval ledger and it must not be reversed across live governance tasks without an explicitly reviewed migration.

## Original invoice recovery before rework

When a send has an uncertain result, use **Reconcile original operation**. The receipt-only path looks up the reserved operation and cannot send, even if the provider returns no receipt. A temporary missing result leaves the work uncertain. It also handles an actually expired worker lease. An active lease remains owned by its worker; repeated observation does not create another invoice or replenish allowance.

The coordinator follows jobs explicitly bound to this work or recorded in its historical command observations, within the same case and obligation. A human reservation merely associated with the same invoice is not factory-owned. Historical jobs remain recoverable if an earlier implementation replaced the visible invoice draft; both drafts and their history are retained. Conflicting historical scope requires investigation.

An exact positive prior receipt is recorded before considering changed contract terms, reviewer eligibility or the original sender's current status. That observation grants no new sending authority. New factory sends still require the current configured executor, exact review, current sources within their configured age and the existing native release controls. Another invoice's unknown, leased or held work for the obligation blocks new issuance. Native never-claimed pending draft revisioning remains supported; its worker rejects a superseded target before sending.

After recovery, changed terms on an already issued invoice require the native Finance correction workflow. Preserve the original invoice, issue receipt and debt. Rechecking a prerequisite is not correction approval and does not authorise regenerating the obligation. The focused tests include real source-age expiry and an actual child-process exit after durable synthetic mock acceptance; browser evidence distinguishes its native fixture policy change from human UI review/reconciliation. Current acceptance and test results remain in the build ledger.

The bounded scoped invoice delegation, exact currency/amount limit and real expiry controls have focused PostgreSQL and native-browser evidence; broader shared regressions remain pending until the recorded run finishes.
