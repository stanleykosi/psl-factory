# Finance follow-up successor lineage

Engineering implementation; actual business policy/people remain unconfigured. This adds lineage, never a new financial execution path.

Open a source Finance case → normal invoice actions → receipt follow-up. Receive the exact supplied companion metadata and record source evidence. Proposal capture works before missing owner/reviewer criteria. Choose an original job matching the received invoice/correction/variant and a separately created successor from the normal source workflow. Supported v1 relations are later generations of the same intent subject, and a distinct legal correction of the same issued invoice. A changed invoice ID or unrelated obligation is held. Another invoice-version relationship needs a separately reviewed contract; v1 does not guess one.

Draft `OPS.finance_receipt_followup` for the current owner and `OPS.finance_followup_successors` for independent reviewer, role, eligible relations, evidence kinds, validity and exact synthetic/operational classification. Validate/activate through the existing policy workbench with real D05 assignments and purpose grants. `fixtures/finance-followup-successors.json` is an example only; its null reviewer cannot activate. No real approver or financial formula is supplied.

The owner records a current non-declining investigation. An independent configured reviewer approves or holds the lineage with same-case evidence and a rationale. Approval checks current owner, reviewer, policy/role versions, request/proposal validity, exact intent hashes, current successor generation, and uncertain/actively leased work. A competing current accepted proposal requires an explicit hold of the earlier proposal. All proposal/review history is immutable, including direct PostgreSQL update/delete protection.

Missing/revoked/stale criteria hold only dependent acceptance. Existing financial reviews, operator replacement, uncertain-effect reconciliation and independent release controls still apply. Changing D05 assignments can invalidate a previously reserved financial intent; re-review and explicitly replace it through the normal operator path. Do not renew/backdate authority or rewrite the job to force progress. A lineage approval does not make a pending financial intent executable.

Use investigation for live status: proposed, held, current or stale, with a separately looked-up internal successor receipt of unknown/present. Present means a canonical internal source receipt; it is neither a bank/vendor claim nor permission to execute again. Stages, invoices, receipts, allocations and debt remain separate. Bounded agents expose current evidence/holds and next steps with no financial effect tools.

On the recovered/control native Finance page, choose **Read native source successor lineage and separate receipts** for an actually published invoice companion. This explicit opt-in adds the `psl.finance-successor-lineage/v1` metadata supplement to acknowledgement v1; original readback remains unchanged. Exact provider/case/credential/identity bindings, source classification, read-only transaction/router and configured budgets apply. A new observation binds the supplement contract. Independent review and subsequent live checks re-read the exact recorded result; source lineage/reviewer/receipt changes invalidate the observation without rewriting history. Native results expose IDs/status only, excluding human notes, financial document bodies and credentials. No source request is transported by this readback.

Tests use actual PostgreSQL/services and synthetic people/configuration. Mocked HTTP destinations/fault adapters are labelled. Authenticated source request transport, new invoice-ID mappings, vendor contracts and operational security/load/UAT remain separate work.
