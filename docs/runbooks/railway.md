# Railway deployment

Each Railway environment runs a public HTTPS API, a private worker, and PostgreSQL with persistent storage. The API mounts its own volume at `/app/.runtime` for local operator artifacts. The worker handles bounded batches of milestone handoffs, controlled publications, invoice jobs and department approval routes.

| Environment | Public API | Private worker | PostgreSQL |
| --- | --- | --- | --- |
| Production | `psl-production-api` | `psl-production-worker` | `psl-production-postgres` |
| Design acceptance | `psl-design-api` | `psl-design-worker` | `psl-design-postgres` |

Staff start a process from **Start work** or continue an existing department record. The coordinator schedules the assigned specialists and resumes when the required evidence and business decisions arrive. The private storage buckets hold file bytes. PostgreSQL holds the case, source identity, report digest, review, job state and receiving record. The API and worker services use bucket variable references prefixed `PSL_UPLOAD_`. The worker alone holds the operational `OPENROUTER_API_KEY`. Both services use `OPENROUTER_MODEL` to select the model. Its eight specialists work on scoped source projections. Operational model use requires current project authorisation. File intake supports UTF-8 text, CSV, Word, Excel and PDFs with selectable text, within the extraction limits. [Coordinator contract](../design/coordinator-specialists.md)

- The API starts after Django migrations succeed. Configure the Railway health check at `/health/` with a 300-second timeout. Keep one API replica for this startup migration and volume arrangement.
- Set `PSL_ENV=production` and a strong `PSL_SECRET_KEY` on the API. Reference the same secret from the worker and set `PSL_SERVICE_ROLE=worker` there. Give both services private PostgreSQL host, port, database, user and password references from Railway.
- Run `railway up --service psl-production-api --environment production --detach` from the reviewed checkout. Verify migrations, `/health/`, `/api/v1/openapi.json` and `/api/v1/session`. The image defaults to `PSL_DJANGO_UI=0`. Confirm the retired sign-in page and static assets return 404. Deploy the worker when its runtime changes and keep it private.
- Provision named accounts through a Railway shell. For a synthetic-only walkthrough, run `python manage.py seed_demo --username <name>` and deliver the generated password privately. For operational use, create named accounts and configure reviewed tenant and case access. Keep synthetic acceptance data in a separate environment before loading operational data.
- Read the project's **Department handoffs** and the exact work's handoff resource through the API to inspect the source and its receiving record. A named reviewer can resolve a packet that needs more information. Complete the required decision in the department workflow. Release evidence enters as an unverified lead. Finance recognition enters as a preparation packet.
- The former design checks service ran isolated test jobs and has been removed. Its historical runs used `python scripts/railway-native-stations.py --role-access` with a clean migrated template and a fresh test database for each group. The separate OpenRouter checks used synthetic data, one-use tickets and temporary worker references. [Test results](../../BUILD-TESTS.md)
- To reproduce a checks bundle from a reviewed commit, run `python scripts/stage_railway_role_checks.py checks --revision <commit>` and use an isolated test target. The `app` option prepares the matching API and worker image with normal startup and migrations. Neither image provisions trial accounts. Repeat `--group` to rerun a selected checks suite.
- Use `--group directory` for the 63 source and tracking links, the 108-entry role catalogue, and the handoff and API permission checks.
- Use `--group cutover` for the API-only surface checks and shared workflow regression. Use `--group api-only` for the focused contract and API-only tests. The test image enables the archived pages for comparison tests. API-only tests select the backend route configuration explicitly.
- Use `--coordinator-ticket <new-uuid>` with the checks image for the synthetic OpenRouter acceptance. The runner verifies its isolated database and private storage, runs the PostgreSQL controls, then tests model routing, specialist reports, coordinator findings, human approvals, downstream receipts and the assistant answers. Remove the temporary provider variable references after checking the results. The Railway worker shares its configured model across the coordinator, specialists and assistants.
- Core hosting uses no third-party API keys. Actual provider actions require the approved configuration and secret references for the selected integration. See `PSL_INTEGRATION_PROFILE` and `PSL_QUICKBOOKS_MCP_PROFILE` in the runtime loaders. Recovery profiles and an isolated restore target require a separate setup and rehearsal.
