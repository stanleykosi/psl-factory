# Native invoice receipt variants and current Finance follow-up

Engineering implementation of incumbent internal Django/PostgreSQL contracts. This does not establish a vendor invoice, email delivery, bank receipt, cash allocation, password-authentication proof or operational acceptance.

The native Finance mapping workbench supports `issue`, `deliver`, `adjust` and `adjust_deliver`. Correction application supports the existing credit, debit and void documents; the archived prior face and signed delta determine the expected acceptance. Decimal amounts cross the SQL boundary as strings. Invoice document, source intent, archived complete job row and expected receipt have separate hashes. The v1 contract requires exact incumbent invoice/correction/recipient identifiers. Deployments that use different identifiers need a separately reviewed mapping contract; fuzzy matching is unavailable.

Capture requires fresh current control authority, the complete archive's physical proof, exact source-case purpose permissions and supplied mapping evidence. It can precede missing downstream configuration. `OPS.native_finance_receipts` controls provider, independent humans, destination, freshness and publication. `OPS.native_finance_variants` selects allowed installed receipt variants with `exact_incumbent_ids_v1`. Use the existing policy draft/validate/activate UI; unconfigured variants hold their probes/reviews/publications, not invoice modules or capture.

The variant configuration shape is `{"variants":["issue","deliver","adjust","adjust_deliver"],"identifier_contract":"exact_incumbent_ids_v1"}`; an owner chooses the enabled subset. The source follow-up shape is `{"owner_id":<current internal user ID>,"owner_role":<assigned role>,"resolutions":[<permitted investigate/link_current_intent/decline choices>],"request_valid_seconds":<explicit bounded duration>,"allow_synthetic":<exact case classification>}`. These are shapes, not installed choices. See `apps/policy/invoice_receipt_validators.py` and the deliberately unconfigured synthetic fixture template for validation limits.

Current PostgreSQL providers must pass the existing independent database registry, session, credential-binding and marker checks. Recovery/control/source/target databases are refused as providers. Native reads are bounded, repeatable-read/read-only. Missing exact records remain UNKNOWN. Incorrect document, case, canonical obligation, payload, correction or recipient conflicts are not treated as successful effects. A canonical receipt may have been committed by another generation; a job-generation match alone is insufficient.

An invoice companion uses the same independent mapping/observation/packet review and durable receipt-first publication worker as the handoff companion, with scope `single_invoice_companion`. The follow-up export action requires the current reviewed packet and an exact confirmed physical publication receipt. It exports only typed invoice/correction identifiers and metadata hashes, outcome and inert flags.

At `/cases/<case>/finance/receipt-followup/`, a current Finance human records the supplied handoff evidence and receives its metadata. This input is explicitly human-supplied evidence, not automatically authenticated control authority. Intake works before owner criteria exist. `OPS.finance_receipt_followup` configures a currently assigned D05 owner, permitted resolutions, fixture scope and validity. The owner may investigate, decline or explicitly link a same-case invoice/correction intent. Decisions are append-only, idempotent and pinned to current owner policy, role and intent hash. Revocation or expiry makes current disposition false while preserving history.

Cancelled/replaced intents and superseded generations cannot be linked as current; a later generation invalidates the current link projection. Canonical receipt verification remains independent: a receipt committed by a successor generation can still prove the original canonical obligation effect. These two questions must not be conflated.

An investigation link does not authorise execution, prove a financial effect or waive debt. New replacement/correction intents must use the ordinary source invoice/correction workflow and its normal reviews, uncertain-effect reconciliation, approval and release controls. Bounded agents report current holds and propose investigation steps; they have no effect tools.

Separate remaining engineering includes independently reading back current source-owner dispositions through the native provider, transporting handoffs with an authenticated adapter, and a supported cross-identifier mapping contract. Actual vendor semantics, production principals/credentials/configuration, owner oracles, destination provisioning, security/load/UAT and operational acceptance are separate evidence slots. Synthetic fixture criteria must never be installed as production policy.
