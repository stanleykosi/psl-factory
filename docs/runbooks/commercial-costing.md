# P14 commercial costing and independent oracle

P14 is discovery and owner validation: the actual calculator/version, rate/formula/unit/tax/margin/currency/rounding/override explanation and independently confirmed examples remain source inputs. The source specifies no calculator-change approver. This implementation does not appoint one or replace the existing case-cost approval chain.

## Evidence and configuration

At `/cases/<id>/costing/`, capture typed `p14_rule` JSON and an exact reference/version. `SuppliedCostingContractAdapter` reads a declared structured contract; the supplied calculator SHA is a provenance claim, not proof that an Excel workbook was inspected or executed. Parameters cite same-case `p14_parameter` evidence. Rules select only `declared_decimal_graph_v1` version1. Pending owners/roles and parameter values may be null; the relevant confirmation/calculation holds until its inputs are usable. Rule-owner confirmation does not wait for an oracle owner. Capture remains available before the original P14 policy is active.

The bounded graph accepts explicit inputs/units, parameter values, topologically ordered add/subtract/multiply/divide nodes and selected outputs. Every node explicitly declares units, decimal places and rounding. Addition/subtraction units must agree. Product/quotient units are source declarations; this is not a general dimensional-analysis or unit-conversion engine. No implicit exchange rate, tax, margin, rate or zero fallback exists. There is no uploaded-code/eval/macro path. Per-node rounding, exact operand lineage and finite magnitude/complexity budgets are recorded. Unknown operands and division by zero produce held results, preserving null values. Changes/overrides require a new rule version and independent validation.

A configured rule owner with current D05 role and record/action/source grants confirms, disputes or withdraws the rule evidence. Capture separate `p14_oracle` JSON identifying the exact rule hash and calculator version. Expected normal and exception values are supplied independently, never generated by the implementation. Mismatches can be captured and investigated; they cannot be confirmed or activated. An oracle reviewer must differ from the rule preparer and owner, have its explicit configured identity/role and current source-read/review authority. These evidence confirmations are not model-change or project-cost approvals.

Draft and activate the original `P14-Q01.commercial_costing_rule_oracle` component using the existing registered structured artifact envelope, exact rule/oracle hashes and current review IDs. The frozen original component schema is unchanged; no new D group or supplemental component is introduced. Missing/revoked/superseded policy holds only dependent calculations and use of generated costing; legacy supplied costing and unrelated workflows remain independent.

## Connected calculations and human decisions

A calculation pins current policy, rule/oracle confirmations, plan, Engineering estimate, Security estimate and exact `p14_inputs` evidence. Inputs must identify every declared key/unit exactly once; an unknown value is null. Persisted results include formula/rounding lineage and actual local comparisons against each independently supplied example. This proves the declared graph against those examples, not equivalence to an uninspected native calculator.

Binding a known current result creates ordinary `costing` evidence containing only IDs/hash lineage, not raw financial amounts. Existing baseline and commercial services check the binding's exact plan/current policy/source authority at preparation, decisions, signing, proposal drafting and controlled publication/adoption. Existing PM / Head of PMO / CEO approvals and separate SOW quality review remain required. A costing hold leaves independent SOW quality review and configured return/reject/withdraw actions available. Unrelated supplied costing acquires no invented global gate. A later rule, oracle, review, policy or authority change preserves historical results and holds dependent new use; it cannot rewrite an existing signed baseline.

For process recovery, run `.venv/Scripts/python manage.py run_costing --case <id> --actor <id> --plan <id> --engineering <id> --security <id> --inputs <id> --key <stable-key>`. Repeating the same committed intent returns the persisted result; changed intent must use a new key. No remote or financial effect is dispatched, so there is no second outbox or speculative invoice worker. PostgreSQL transaction atomicity, case/grant locks and unique intent keys protect concurrent calculations/bindings.

## AF13 and access

Bind a current known calculation to an exact P14-only AF13 package selecting the costing policy. AF13 meaning/expectations reviews must be current, and their reviewers must have source access. Every oracle scenario is represented by an AF13 example containing its immutable hash references, without copying raw input/amount data into generic discovery views. Binding records actual local rule/oracle execution separately from the generic supplied-report comparator. It grants no AF13 acceptance, deployment or invoice authority. Changed inputs require reassessment; acceptance and native operational evidence remain separate.

Workbench/report/source endpoints check record/action access and use no-store responses. Source/oracle/parameter/input/review bodies are excluded from generic evidence/document/AF13 and extraction/meeting-agent paths. Source JSON and amounts/lineage require costing.source.read; metadata viewers see recorded versus current usability without raw values. The bounded P14 investigation examines at most20 rule versions and20 runs, tracing missing/stale evidence and independent-example questions without generating expected values, reading raw source bodies, approving case costs or issuing invoices.

## Remaining engineering and owner inputs

Authenticated native calculator/workbook acquisition, formula/cell/macro/dependency inventory and controlled native execution/equivalence remain engineering work against verified target contracts. Broader native calculator methods, source-specific variants, real-provider evaluation and operational/UAT/restore/load evidence remain. Actual owners/access, calculator files/versions, all financial parameters/formulas/units/rounding/override contracts and independent expected outputs remain policy/evidence inputs. Explicit synthetic fixtures are not PSL policy or real appointments.
