# B14 human-controlled response release

Engineering design over B14 Support case-flow standardisation (a proposed improvement), B01 channel evidence and B03 clock definitions. This is not a real Support SOP or channel approval matrix.

The private draft workbench links to `/cases/<case>/support/responses/`. Configure B14.response_release using the JSON draft form and existing policy validation/activation lifecycle. The synthetic fixture is an example only: exact releaser/recipient IDs remain null until supplied. Unknown values are never inferred. Closed fields are body, issue_ref and case_type; metadata must already exist in the approved native field projection. The local route and receipt meaning are explicit constants, not a configurable assertion of customer delivery. New channel implementations require verified engineering contracts.

1. Prepare the exact currently approved draft through the UI or bounded `apps.agents.support_responses.prepare` tool. The configured owner and native source permissions apply. A stable reference pins draft hash, exact draft review, source/result/flow lineage, release policy, destination, selected fields and lease budget. Preparation sends nothing.
2. A separately authorised configured human chooses release. Current Support summary/D05 authority and inherited preparer independence still apply; the supplement cannot relax them. A release creates an immutable decision and one durable job. Withdrawal appends a decision. A draft approval does not substitute for release authority.
3. Run `.venv/Scripts/python manage.py work_support_responses --case <UUID> --limit 1`. Only this case is claimed. Lease/fence state is separate from immutable packet/decision intent. Current draft/source/result/flow, human authority, configured destination and grants, release lifetime, field projection and attempt budget are checked under Case/grant/principal locks immediately before the local effect.
4. The adapter stores one immutable recipient receipt with the exact payload hash and stable operation key. The worker independently verifies the persisted native receipt; an adapter success return alone cannot confirm a job. An uncertain attempt reconciles that original receipt before any new effect. Permission revocation does not erase a committed receipt. It still prevents new sending and protected reading.
5. A current authorised source reader with response.read may inspect the private workbench/report. Recipient receipt access additionally requires response.receive, exact recipient identity and current destination configuration. Responses are no-store. Generic evidence/public timelines never contain response bodies; audits use the existing private agent.data namespace.
6. Operators may cancel eligible uncommitted jobs or retry a held job only within its original attempt budget and unchanged current release. Active/confirmed/cancelled jobs and intents with receipts cannot be retried/cancelled. Changed policy/source/draft requires a newly reviewed packet reference, not rewritten history.

Receipt classification is always `internal_storage_only`. It does not prove customer delivery, recipient reading, actual Teams/WhatsApp/native channel access, or response-clock attestation. No packet/release/receipt mutates SupportEvent, first_response_at, resolution, invoices, cash or Engineering requests. Existing human response evidence/transition controls remain separate. Actual channel receipt verification and clock evidence are further adapter/owner work; this interface deliberately cannot represent them as completed.

Missing release policy holds packet preparation/release, while private draft review, configuration, normal human investigation and existing Support interfaces remain available. Actual permitted fields, recipients, authority/independence, lifetimes and attempt/lease budgets need sourced owner decisions. A configured value cannot make an operational case bypass its existing AF13/SOP controls.

Verification references are recorded in BUILD-TESTS.md after actual runs. Tests use real Django services/PostgreSQL and the existing authenticated loopback extraction provider mock. No actual model or customer channel is exercised.
