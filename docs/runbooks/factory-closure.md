# Controlled project closure

This describes the bounded synthetic `delivery-closure/v1` station accepted after run486’s70 PostgreSQL tests and run487’s canonical metadata checks. It is a development path, not operational acceptance or permission to close a real engagement. Current build status is in HANDOFF.md and BUILD-TESTS.md.

## Start and prepare the report

Open **Start work → Close a project** from the work queue, or continue from the project’s closure evidence page. Select the existing delivery dossier and describe the work. Choose the actual recorded retrospective version, PM closure-report evidence and controlled project-artifact template. Leave an unavailable record unselected; an unknown value is never treated as complete.

The agent investigates current scope, go-live acceptance, stability, archive inventory, Support receipt, retrospective and Finance notification coverage. It can prepare the controlled report once the native prerequisites hold. It cannot invent a retrospective, signature, Finance confirmation or Head decision. Use the linked project tools to obtain those actual records. Missing execution configuration does not prevent capturing the intake and reviewed source corrections.

The template determines whether a native quality review is required. A currently authorised reviewer approves, returns or rejects the exact report. The Head of PMO then makes the prescribed decision on that version. A quality review is not the Head decision. Return/reject buttons appear only when the configured decision-action rules permit them.

After an actual approval, the agent may invoke native finalisation through the configured currently authorised PM. The service checks current scope, source records, controlled version, quality review and Head authority again. The station verifies the actual recorded closure before showing **Verified**. A successful agent activity alone does not establish project closure. Debt, invoices, receipts, payment exceptions and deployment controls remain independent.

## Correct and recover

For missing or changed inputs, record **Review source changes** with the exact replacement references and a reason. This preserves the previous private intake and report, invalidates reliance on its old decision and requires a fresh exact report and prescribed review/decision. It retains the original lifetime allowance. Do not create a new work item merely to evade a hold or exhausted allowance.

When an operating profile changes, a permitted operator explicitly adopts the reviewed settings. Existing work keeps its original lifetime allowance. Appointment through a technical execution profile does not confer a PM or Head role. Missing current owner authority holds only its dependent action.

After worker interruption, first inspect the current work and native records. A local closure that committed is recovered by its recorded identity and verified again under current authority. An interruption before commit leaves no native closure and can resume the original bounded work. There is no external closure call to resend. Never reset receipts, source heads, decisions or the allowance to make a recovery appear successful.

Cancellation before closure prevents new work once the active worker has settled. Resuming stopped work needs a fresh human instruction and exact report decision, within the original allowance. If closure already committed, cancellation records follow-up; it cannot reopen the delivery or erase the closure. The closed project scope reads **Closure recorded**, and preparation remains unavailable for reopening. Changed scope or authority still appears as a current-evidence hold.
