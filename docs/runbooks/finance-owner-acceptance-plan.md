# Finance evidence to AF13 recipient validation — implementation proposal

Status: original engineering proposal retained below. The bounded native F01 implementation is now verified; see docs/runbooks/finance-recipient-acceptance.md, HANDOFF.md and RUN190/192/193/194/195. Additional Finance source variants and operational acceptance remain distinct gaps. Source-backed boundaries remain Finance-owned QuickBooks posting and separately authorised human owner validation/acceptance. The existing private Finance approved-evidence export does not create an AF13 acceptance.

Inspection findings: apps/documents/validation.py deliberately rejects restricted evidence in capture_source. Its package manifest currently binds public DiscoverySource/ValidationExample and policy references; it has no native Finance draft binding. Bypassing that restriction or copying a private draft into generic procedure_source would lose native source authority. Existing AF13.owner_validation_rules assigns actual process-scoped human purposes (meaning, expectations, acceptance); AF13.acceptance_rules separately limits supported acceptance levels. Preserve both controls.

Build the next connected path in this order:

1. Add an immutable native Finance-to-validation handoff binding the exact case, latest Finance draft/review, source/projection/extraction/result-review pins, approved packet hash, target ValidationPackage version/hash, explicit recipient and preparing owner. Use a stable intent and explicit successor; do not copy private bodies into generic evidence. Add database lineage/immutability constraints.
2. Implement typed versioned recipient/package configuration where existing AF13 assignments cannot express routing. Validate actual active native Finance/private and AF13 grants, original D05/owner assignments, exact process/package scope and independence. Leave real people/criteria/budgets unset in fixtures. Missing routing holds only handoff preparation or acceptance.
3. Prepare through the configured Finance owner and current-approved evidence service. A native adapter reads the existing exact packet and returns bounded references/hash only. The recipient's private inspection rechecks every historical source participant, the original owner's continued current authority, provider/result/draft validity and exact target package. A stale source/target does not silently select a successor.
4. Add a recipient inbox and explicit accept/return/withdraw actions; receiving evidence and AF13 meaning/expectations/acceptance are separate decisions. Native AF13 package current-use/reporting must re-evaluate any attached Finance bindings. Existing public-only packages remain independent. The human owner still supplies acceptance criteria and actual source/SOP evidence; no operational acceptance from a synthetic test receipt.
5. Expose bounded live investigation/drafting tools without approval or posting tools. Keep private rows, bodies and source IDs out of generic agents/timelines/exports. Metadata protection includes references only through the native source-authorised registry.
6. Test actual PostgreSQL/services/HTTP: absent/invalid/active/superseded/revoked configuration; exact owner/recipient and mandatory scopes; prepare/inspect/receive/return/withdraw; separate AF13 review sequence; expired/withdrawn source and target revisions; cached cross-case revocation; idempotence, single successors and concurrent independent identity writers; adapter/provider uncertainty; immutable SQL guards; unchanged unrelated modules and old acceptance reports.

Reuse existing modular Django/server-rendered patterns. A provider loopback is synthetic transport evidence. Native QuickBooks, real model/provider, owner criteria, full operational recovery/security/load/UAT and acceptance across all thirteen families remain distinct work and evidence requirements.
