# AF13 evidence, owner validation and acceptance

## Source-backed boundaries

B13 asks for actual Product/Support/Reconciliation procedures, normal and exception walkthroughs and process-owner confirmation. The recovered meeting sources do not replace the referenced missing Support SOP or Henry/Reconciliation brief. P13 records receipt of the revised17-page PMO SOP v1.1 (revised12 October2026, stated owner Head of PMO), extracts approval clauses and preserves later clarifications. A specific SOP-revision approval/publication workflow is not supplied. P15 asks process users to validate meaning, independently state expected outcomes and review later test evidence for selected scope. Source receipt, a demo, architecture approval and mock success do not establish owner acceptance, implementation savings or native operational readiness. See the frozen B13/P13/P15 definitions, guide01 and guide11 AF13.

## Finite implemented design

The case workbench `/cases/<case UUID>/validation/` provides a reference library, selected review packages, a decision/test board and links to shared document publication and action/deadline services. Capture remains available without owner policy. Versioned sources retain exact evidence/hash, stated version/date/owner, provenance classification, exact quoted clauses/locators and affected original process IDs. Source labels and named owners are supplied claims, never grants. Source and example revisions preserve history and invalidate packages using superseded versions.

The frozen-pack adapter only reads bounded UTF-8 text paths present in SOURCE-MANIFEST.json after verifying the actual bytes/hash. It cannot traverse arbitrary paths or import credentials. Copies become ordinary scoped immutable evidence; importing a secondary source does not turn it into a native SOP, a verified practice or a new current business rule. User-supplied source evidence follows the same record/action boundaries. Primary native source authenticity and safe redaction remain operational evidence requirements.

Packages select exact source/example versions, original process IDs, required domain policy components, declared gaps and acceptance level. A package can represent B13 collection, P13 clause interpretation or P15 acceptance work; selected process IDs may describe a connected cross-family scope. Explicit open gaps are not automatically resolved when an action completes or a source arrives. Revise the package with resolution evidence and obtain fresh reviews. Normal and meaningful exception coverage is required for every selected process before expectations can be approved.

Two supplemental engineering components, AF13.owner_validation_rules and AF13.acceptance_rules, use the shared independent configuration lifecycle. They are not additional consolidated D groups. Actual humans, scoped process/purpose responsibility and D05 role assignments must be supplied; administrator/source/model text grants nothing. Meaning review, expectation review and acceptance are distinct. Configured independence applies to preparers, expectation owners, testers and acceptors. The source's stated Head-of-PMO document ownership is not silently expanded into acceptance or SOP-publication authority. Configurations are drafted here and separately validated/activated in the policy workbench; accepting a package never activates business policy.

D09.support_sop_ref is a separate explicit link to exact source/hash, selected process scope and a current owner meaning review. Changed source, disputed interpretation, revoked owner policy or lost owner grants invalidates the dependent reference. It does not establish all Support process rules or silently replace native system-of-record responsibilities. Unrelated source capture continues.

Expectation review precedes supplied-result comparison. The local adapter accepts a bounded typed report containing exact example/build/run/environment references and reported evidence class. The deterministic json_equality/v1 implementation compares finite canonical JSON hashes (booleans and numbers remain distinct). It records matched/mismatched output, exact owner-approved expected version and actual supplied evidence. **This comparison does not execute the underlying workflow.** Synthetic and reported-external evidence classes remain distinct; a supplied claim of a real integration does not authenticate one. The application has not gained a generic arbitrary-code or shell-execution tool.

Definition acceptance records only definition/expectation agreement. Selected synthetic implementation acceptance additionally requires configured criteria, current matching post-review comparisons for every example, exact build, explicit role list/manual fallback/rollout/migration context and an active scoped support nominee. Open gaps, changed sources/examples/domain policy, current human review or authority changes, mismatches and configured independence violations hold acceptance. Operational acceptance remains unavailable until reviewed native execution/source adapters and actual owner/UAT evidence exist; this is engineering readiness, not a request to enter a guessed policy value.

The scoped local report adapter exports historical acceptance evidence with current-use status, exact selected IDs, package hash and explicit whole-product/deployment/policy boundaries. A historical approval remains visible when it becomes stale or revoked; it is not relabelled current. Exports contain no raw source document or example output. Current case/read/export permissions are checked every time. No external report delivery or deployment effect is dispatched.

All accepted changes persist in PostgreSQL. Case/grant locks serialize review/revocation and duplicate operation intents. Unique source/example/package versions and request/replay keys prevent silent replacement. Immutable review/result/follow-up records have SQL append-only guards. Repeating the same operation returns historical receipt; changed intent conflicts. Current-use checks still re-evaluate the evidence and authority. No outbox is invented where the local operation has no uncertain external effect.

## Staff path

1. Capture the actual procedure, walkthrough, clarification or source review. State its real type/version/date/provenance and owner label. Quote exact clauses and map affected original IDs; do not overwrite the frozen process definitions.
2. Prepare a selected package with precise missing documents, disputed clauses and owner questions. Assign open gaps to actual scoped action owners with explicit deadlines. This uses the existing shared action register; follow-up completion is not acceptance or gap resolution.
3. Capture normal/exception examples and independently stated expected JSON. Nominate actual owners and configure review/acceptance interfaces using owner-decision evidence. Synthetic examples in fixtures/evidence-validation.json are infrastructure tests, not appointments.
4. An authorised owner records meaning review (approve/disputed/return/reject/revoke), then independently validates exact expectations. Changed source/example/selected rules require a revised package and new reviews.
5. Record supplied results against the approved examples and exact build; inspect mismatches and provenance. A result comparison is not an execution/provider evaluation or proof of a native integration.
6. An authorised human accepts only the selected supported level when its configured and fixed source requirements hold. Preserve manual fallback, rollout/migration and support responsibility. Keep actual operating-system/tool/source/UAT gaps separate.
7. Use the bounded cited A02/A03/A08 investigator to compare exact clauses/versions, identify conflicting statements and missing examples, inspect stale reviews and draft decisive owner questions. Its tools cannot approve owners, resolve a gap, activate policy, publish a procedure or accept the product.
