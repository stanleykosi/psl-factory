# Domain receipt and destination contracts

Engineering implementation of the proposed recovery companion path. Source business ownership, PMO/Finance responsibilities, debt and independent release controls are unchanged. No real vendor protocol, destination topology or human appointment is inferred.

Use the separate fresh cold-control application and the reconstitution workbench link to **Receipt and destination contracts**. The normal recovered application startup guard remains unconditional. All screens and JSON reports require current fresh deployment identity/purpose, case/action and complete archive-scope access. Provider review additionally requires `reconstitution.domain.<family>.review`; provider verification requires `reconstitution.domain.<family>.verify`. Destination equivalents are `reconstitution.destination.review` and `.verify`. These are explicitly provisioned scoped grants, not role names supplied in evidence.

1. Record source-owned contract evidence in the workbench (requires current capture purpose and `evidence.add`), then capture a provider or destination contract against the exact recovered reconstitution plan with that same-case `integration_contract` evidence. Capture accepts typed unconfigured references without downstream criteria. A changed contract requires its explicit current predecessor and creates a version; history is immutable.
2. Draft `OPS.domain_contracts` through this workbench and validate/activate through the existing configuration lifecycle. Supply distinct fresh operator/reviewer IDs and D05 roles, allowed provider references, exact destination, observation/review validity and explicit synthetic scope. The structural fixture supplies no actual values. Independent archive/reconstitution criteria and physical recovered review must also be current before review or verification.
3. Deploy reviewed endpoint and secret-reference registry entries using the existing `READINESS_ENDPOINTS` and `READINESS_SECRET_REFS` facilities. Credentials stay in the referenced environment variable. No UI-supplied URL or credential is accepted. HTTPS is required except explicitly synthetic loopback. Redirects/proxies are disabled, replies are bounded to16KiB, and transport timeout is5seconds. Credential bytes are keyed into the binding so unversioned rotation also invalidates review.
4. Obtain independent source-owned review of the exact contract and current deployment binding. Only `authenticated_json_v1` with the two documented PSL metadata protocols is installed. `reference_only`, unknown protocol versions, missing source owner/payload mappings or unavailable registry entries hold review/probes without preventing capture.
5. Request read-only receipt verification or destination preflight with a stable operation key. Duplicate exact requests converge on the same immutable observation. A different request cannot reuse the key. HTTP is observational: a process failure before the PostgreSQL observation commit can repeat a read; no business effect is dispatched. Completed observations survive process restart. New evidence uses a new key; no response or receipt is overwritten.
6. Independently review the exact current observation. Inspect the report/agent investigation for current versus stale authority, contract, physical recovery and observation age. Missing receipts remain UNKNOWN, conflicts remain conflicts, and destination prerequisites remain individually missing/unknown/unsupported where applicable. A verified prerequisite must have a configured reference.

## Installed metadata protocols

`psl.domain-receipt/v1`: authenticated POST `/domain-receipts/verify`. The request includes contract/plan/archive SHA-256, intended destination, exact archived source case/family/effect, SHA-256 of original operation key and SHA-256 of complete archived PostgreSQL job row, explicit source payload version and mapping identifiers. The row digest is deliberately described as a row digest, not a canonical original vendor payload. A provider must implement this reviewed mapping; inventing a vendor lookup from these hashes is unsupported.

The closed response includes request SHA-256, exact provider/principal/protocol, aware observed/expiry timestamps and outcome `present`, `unknown` or `conflict`. Only present observations carry both bounded receipt reference and SHA-256. It is classified as an authenticated remote receipt claim, with synthetic/remote transport classification preserved. `direct_vendor_verification=false` is invariant. Health or historical archived receipt presence cannot supply this observation.

`psl.destination-preflight/v1`: authenticated POST `/destinations/preflight`. The exact plan/archive/destination and identity/database/store/provisioning/outbound references are sent. The response binds that request hash and reviewed identity/version, freshness and a closed per-prerequisite `verified|missing|unknown|unsupported` result. `activation_enabled=false` and `provisioning_executed=false` are mandatory. This is provider preflight evidence, not independently inspected physical destination state.

Both protocols use the existing fixed endpoint registry and authenticated HTTP transport; neither supplies arbitrary commands, SQL, source bodies or archived credentials. Private case identifiers and hashes remain within the complete archive-authorised control scope and the reviewed endpoint. Do not promote a synthetic endpoint or result to operational acceptance.

## Current limits and next work

The new companion report does not replace the existing gateway-based reconstitution dispositions, authorize replacements, publish directly verified vendor evidence or enable recovered startup. Current source-specific vendor/native receipt implementations, independently inspected destination/provisioning adapters, reviewed evidence attachment to durable successor publication and source-owned replacement intent workflows remain engineering work. Actual provider credentials/contracts, source owners, destination access, production security/SOP/UAT evidence are separate deployment/owner inputs. All122 process rows remain partial.

PostgreSQL guards preserve append-only contracts/observations/reviews, same-case lineage, inventoried effect bindings, independent review and false activation/vendor-proof flags. Services validate closed schemas, freshness, current permissions/criteria, credential bindings and complete physical recovery. SQL guards do not authenticate an external endpoint or establish real business correctness by themselves.
