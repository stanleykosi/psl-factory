# D13 payment controls

## Source-backed boundaries

Current folder12 AMENDMENT.md / U06–U08 state the 80% payment expectation, ability to grant a human exception, absence of an appointed approver, debt preservation and independent release controls. The actual denominator, qualifying funds, principals/delegation and validity rules remain owner configuration. Recording a configured human decision does not require Engineering/Security approval; using it for release separately requires current independent controls. See guide/01 and guide/10. Historical source restrictions are preserved evidence, not present build instructions.

## Implemented finite design

`/cases/<case UUID>/payment-controls/` connects real Finance issued invoices, accepted credit/debit/void corrections, active cash lots, allocations/reversals and accepted corrected-lot successors to the existing PMO delivery dossier, signed baseline and exact GLPI request. Immutable assessments pin the complete current financial manifest, current policy versions and exact deployment context. They are not a contractual assertion that captured invoices equal the full contract.

The version1 denominator implementation is explicitly selected **adjusted issued invoices in a selected current complete billing coverage**. The owner must confirm that this scope is suitable. Contract-value, stage-specific, tax/net conversion and multi-coverage denominators require additional reviewed implementations; entering arbitrary text cannot execute a formula. An unconfigured method, partial coverage, nonpositive denominator, currency/basis conflict, unresolved correction or uncertain issuance returns UNKNOWN, never zero. Coverage pricing basis may differ from invoice basis: the configured invoice/funds basis must match the actual financial records. Source 80% comparison is exact decimal arithmetic before display; excess qualifying funds can exceed100% without creating an allocation or extinguishing debt.

Funds method is separately selected: active allocations to the selected invoices, or verified cash currently assigned to selected coverage (less live allocations already consumed by other coverage). Unverified reports, reversed lots and reversed allocations never count. Corrected parent/successor money never counts twice. Full source manifest changes require reassessment conservatively, including other captured case financial evidence. Date rollover changes the current-day assessment manifest; historical replay is not implemented.

Each of the six D13 components has a version1 JSON schema, semantic validator and draft UI. Authority requires explicit human attestation, an active principal and exact role under D05, actual case/action grants, an explicit disabled/structured delegation catalogue and explicit validity/reassessment/revocation rules. Categories and superuser flags confer no authority. D13 delegation names principal/delegate, aware start/end and scoped evidence; direct principal retains current underlying role and permission. The directory's human attestation remains an owner/source claim until identity provisioning and live source validation are accepted. Synthetic fixtures are never installed into operational cases.

Exception preparation/requests and own withdrawal work without assessment or approval policy. A human can decide an UNKNOWN assessment under independently configured authority; release use remains held until payment basis is known and current. Approved requests bind the exact financial/contract/deployment context and requested validity window, subject to configured maximum duration and self-decision rule. Return permits an explicit later decision; reject/withdraw are terminal. Approval can be revoked by current configured authority even after underlying evidence becomes stale. New context requires a new assessment/request; old records remain immutable. Current requester and decision permissions, actual principal/delegation, policy versions, validity and source manifest are checked for use.

Combined release reservation separately invokes existing signed-baseline, Planning/kickoff, QA/UAT/Engineering Go/No-Go and exact Security/CTO/CEO GLPI evidence checks. A below-expectation assessment requires a current exact human exception; meeting expectation requires no exception authority. Missing policy never prevents PMO milestone completion or unrelated work. Existing PMO readiness records still describe independent evidence and never dispatch deployment. A reservation's local receipt also does not deploy anything. The local adapter revalidates both paths on every prospective downstream use; native GLPI/Engineering dispatch requires its own reviewed transactional effect/reconciliation adapter and is not built here.

Mutations serialize on the case and current grant rows. Request and reservation operation keys reject changed intent; repeating a reservation key returns the historical local receipt, which cannot be treated as current without revalidation. Revocation after a historical reservation preserves evidence and invalidates new use. No automatic rollback is promised if a future native external deployment races with revocation; reconcile the actual external receipt/incident before retry. There is no external effect job to retry in this bounded local adapter.

## Staff path

1. Capture Finance coverage/issued invoices and receipt/allocation evidence in the existing Finance workbenches; prepare the PMO delivery dossier and GLPI request independently.
2. Capture an assessment, including UNKNOWN. Inspect exact scope, invoice/funds basis, holds and pinned source/policy lineage.
3. Draft each required component using actual owner-decision evidence. The workbench exposes schema fields; `fixtures/payment-controls.json` contains **synthetic examples only**. Validate and activate in the policy workbench. The human principal field is a list; delegation is one catalogue; validity is a registered artifact; denominator/funds/role are registered references.
4. Reassess after basis activation. Request a human exception with evidence, reason, operation key and aware requested validity. Requests are not approvals.
5. The configured human uses the decision form to approve/return/reject. The requester alone may withdraw undecided/returned work. Current configured authority may revoke a prior approval.
6. Reserve combined controls with an exact assessment/request and operation key, then explicitly revalidate for any downstream use. A changed independent gate holds use without erasing the decision or financial obligations.
7. Run the cited deterministic investigator to inspect current/stale snapshots and decisions and obtain draft follow-up. It exposes read/comparison/drafting tools only; it cannot approve exceptions, change money or deploy.
