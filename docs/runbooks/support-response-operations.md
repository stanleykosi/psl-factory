# B14 private response operations and readiness

This is engineering integration over proposed Support-owned B14 flow standardisation. It does not prove an actual Support SOP, customer-channel API, response clock or operational acceptance.

The closed operator/readiness family name is `supportresponse`. It maps to the native SupportResponseJob and immutable internal receipt. The adapter verifies a separate native PostgreSQL session's principal/database/SELECT capability and a scoped receipt lookup. Observations contain only found/not-found and an operation-identity digest, never response text, recipients or draft/source identifiers. Password/TLS authentication, customer delivery and model quality remain unproven.

Operator inventory and export require the original native source grants plus support.response.read. Source recovery additionally requires configured OPS.operator_rules purpose/role, ops.recover, an explicit supportresponse route/action and support.response.operate. Only retry/cancel are supported; replace_intent cannot retarget an immutable packet. All recovery delegates to the native response service, retaining its original attempt budget, source/draft/human-release/destination controls, leases and receipt checks. Unknown effects must use the case-scoped worker; generic operator actions cannot force retry/cancel. Missing operator rules hold recovery only, not authorised inventory or normal human release/delivery.

Existing project-case inventory/manifests are unchanged; the additional family is relevant only to Support. New metadata bundles pin the complete source-read grant set. Download, backup and restore recheck it. Metadata export/backup/isolated PostgreSQL restore do not contain response bodies, recipients, credentials or business-job replay. Restored metadata does not recreate live jobs or receipts. This is not full application/database recovery.

Readiness enrollment is explicit through the existing integrations workbench. Capture a native adapter contract for supportresponse/internal:supportresponse, configure INT.adapter_readiness principals with actual current Support/D05/source permissions and bounded budgets, reserve health and optionally required scoped receipt probes, assess, obtain independent human review and select the family. A not-found native receipt can prove lookup capability before initial delivery; it does not assert delivery success. Only enrolled effects acquire the readiness dependency. Readiness never replaces human release or recipient authority.

Worker `.venv/Scripts/python manage.py work_support_responses --case <UUID> --limit 1` reconciles committed native receipts before resolving readiness/current source permissions. An enrollment with no reviewed assessment holds a new effect, while an already committed internal receipt still confirms exactly once. Source/readiness/credential/reviewer/selector changes hold dependent new work. To retry held work, restore legitimate current authority/evidence through existing successor workflows; never refresh/backdate historical approvals simply to make a test pass.

Private integration contracts and their probes, observations, assessment reports, selections and form choices require current native source access, including historical source endpoints. Revocation omits these rows from shared workbenches while other operations remain available. Private metadata artifacts cannot be downloaded after source revocation. Private audit entries use the existing hidden agent.data namespace; source-related captured evidence is also excluded from generic timelines.

Live guidance at /cases/<case>/support/responses/operations/ uses the bounded support_response_operations agent tool. It requires current source/read, agent.operations, ops.read and integration.read grants. It inspects metadata, recommends receipt-first reconciliation or appropriate source controls and reports readiness without reading response bodies or taking recovery actions. It is not stored in a generic AgentRun. Generic persisted operator/integration investigations exclude private response job/probe/assessment details to avoid later leakage through shared agent history.

Policy fixtures are explicit synthetic examples; they do not add routes to previously active policies or appoint real people. Real operators, roles/grants, readiness freshness/budgets, destinations, approved database identity/revision and later channel/clock contracts remain sourced inputs. Actual test results are recorded in BUILD-TESTS.md after execution.
