# Private readiness evidence and AF13 owner acceptance

Engineering contract: a native Finance publication capability assessment, its independent transport review and exact health/receipt observation hashes are projected to closed metadata and bound to a separate fresh AF13 package. Do not reuse the original Finance handoff package: that would make source acceptance recursive.

1. Configure actual private Finance/integration read/source grants and existing AF13 owner/D05 authority. Source text and agent outputs confer no authority.
2. Probe the exact native publication job, assess and obtain independent human transport review through the existing integration workbench.
3. Prepare a separate AF13 package with identified supplied source, selected F01/AF13 scope, normal/exception expectations and explicit evidence gaps. Operational acceptance is unavailable through capability metadata.
4. Open `/cases/<case>/finance/readiness-acceptance/`. Select the exact assessment and fresh unreviewed package, and prepare the packet. The agent uses this typed preparation service; it cannot record human reviews.
5. Draft `AF13.acceptance_rules` v2 using `private_readiness.inventory` pairs of exact `package_id` and `assessment_id`, explicit `freshness_seconds`, `receipt_requirement` (`observed` or `found`) and `independent_transport_acceptor: true`, plus existing acceptance fields. The UI creates a draft only; use the policy lifecycle UI for validation/activation. The unset fixture is an interface, not appointments or defaults.
6. Configured owners record separate meaning, expectations and acceptance decisions. The acceptor must also be independent of packet/transport preparation and transport review. Existing examples, replay and independent tester requirements still apply to synthetic implementation acceptance.
7. Source-authorised readers can inspect packet metadata; only a current configured owner acceptance permits the native accepted metadata export. Generic AF13 historic reports preserve history without asserting current acceptance.

Fresh probes, changed receipts, withdrawn reviews, replaced policies, superseded packages or expired evidence require reassessment and explicit packet succession on a fresh package. Never rewrite old reviews or renew evidence merely to make a gate green. Negative human decisions remain available when a positive current-use approval is held. Revoked source access denies historical reads and cached exports too. All packet reference participants retain source checks.

The projection contains IDs, hashes, classification and receipt state, never outward document sections, Finance quotations or credentials. Generic persisted validation agents and public audit timelines omit private proof. Private guidance is bounded and live, with no generic AgentRun or business effect tools. HTTP responses use no-store.

Tests and actual run outcomes are in BUILD-TESTS.md. Local PostgreSQL capability proof, authenticated synthetic upstream fixtures, real-provider evidence and actual owner operational acceptance must be reported separately. Main operational evidence is not seeded by this increment.

## Policy revision and prior business history

The v2 extension reuses the case-scoped AF13 acceptance component. Activating any new version makes owner acceptance snapshots pinned to its previous version historical, including original Finance handoff acceptance where applicable. Reassess affected business/document decisions explicitly before new delivery; do not infer renewed financial approval from a current transport assessment or new private evidence packet. Receipt-first recovery preserves already committed effects. A native capability assessment can describe current health/receipt lookup of an immutable historical publication while its original business approval is no longer current. The packet export states its selected evidence scope and never grants accounting, operational, whole-product or deployment acceptance. When criteria require a committed receipt, obtain and reconcile that actual source receipt before capturing the final assessment/packet; configuration does not manufacture a receipt.
