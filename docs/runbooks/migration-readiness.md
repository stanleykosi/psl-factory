# D11 migration evidence and AF13 operational readiness

P15/Q14–Q16 require owner-tested examples, roles, fallback, rollout/migration and support arrangements, with operational controls and acceptance evidence still to be supplied. D11.migration_evidence_rules is an original independent policy component. The workflow below is an engineering design, not a newly inferred business approval chain.

## Connected workflow

1. In AF13, capture exact source versions and normal/exception examples for the selected processes. Prepare an operational-scope package with an exact build, role list, fallback, rollout/migration context and an actual granted support owner. Meaning and expectations reviews remain the existing owner decisions. An operational package is a request for evidence review, not accepted automation.
2. Open `/cases/<id>/migration/`. Capture a versioned plan using migration_plan evidence. It identifies source/target systems, references and versions, build/process scope, selected evidence IDs, declared expected count/digest, and optionally the exact AF13 package. Unknown count/digest stays null. Revisions require the exact current predecessor; history is immutable. Capture is available before policy or AF13 readiness exists.
3. Draft D11.migration_evidence_rules through the typed form and activate using the existing policy lifecycle. Configure exact process scope, inventory mode, required report kinds, source-system allowlist, freshness, actual owner and independent reviewer with D05 roles, and the owner/preparer review choice. Reviewers also require current migration.evidence.read access. The independent reviewer is always separate from preparers and owner. The fixture is synthetic, not an appointment or an acceptance threshold.
4. Capture strict migration_proof JSON receipts. Every receipt correlates exact plan/hash/build/source/target versions. Tenant/system/external reference/receipt version is claimed once; identical input is idempotent and conflicting/cross-case claims hold. New versions preserve failed/unknown/older reports. Supplied execution/restore reports never become native execution evidence. Synthetic reports are barred from operational cases.
5. Use the read-only local inventory action. The implemented adapter reads at most 200 selected immutable evidence metadata rows in the exact case: id/kind/version/hash. It reads no bodies, selects no arbitrary table or file, writes no target data and executes no migration or restore. The source must explicitly be psl-evidence, the exact case UUID, evidence-manifest-v1. The observation stores real local read results with coverage limits. Remote/native modes require their own reviewed implementation and hold only dependent readiness.
6. Assess. Current D11 policy, required proof heads, freshness, actual count/digest, AF13 source/example/policy and meaning/expectations snapshots are pinned. Missing evidence, unknown values, failed reports, missing context/support ownership or open AF13 gaps prevent a documentary-ready result. Changed policy/evidence/observation/package/reviews or revoked source/operator/reviewer grants require reassessment.
7. The configured owner reviews the exact assessment, followed by the independent reviewer. Return/reject/withdraw preserve history. Approval means only documentary and selected-inventory readiness. A replayed operation key is a historical receipt, not proof of current approval. The AF13 acceptance-authorised principal can bind the reviewed assessment to the exact package. A changed review requires a fresh assessment/binding, not overwriting the earlier one.

## Human and agent views

The migration workbench shows plan versions, unknown counts, readiness findings, current review status and AF13 binding history. JSON reports recheck permissions and current inputs. Raw supplied receipt payloads require migration.evidence.read on this case; generic evidence display/timeline, document/extraction agents and AF13 source repackaging do not expose them. AF13 views show a scoped migration readiness status. A validation-only viewer receives access_required rather than migration details.

The bounded deterministic agent examines at most 25 plan versions and their status/findings. It asks for precise unknowns, changed inputs, missing evidence and native execution proof. It reads no raw receipt body, runs no shell/SQL/network command, changes no target and grants no acceptance.

## Readiness limits and recovery

Documentary completeness, actual native inventory read, supplied execution/restore evidence, reviewed readiness and operational implementation acceptance are separate fields. `operational_ready`, `native_migration_execution_verified`, `native_restore_verified` and deployment authority stay false until actual reviewed execution adapters and evidence exist. Existing AF13 operational acceptance remains held for native workflow execution; documentary binding does not bypass it. This is an engineering/evidence gap, not a value that can be enabled by a policy flag.

No migration effect or delivery outbox is created, so there is no blind retry of an uncertain data mutation. For new/failed/unknown source reports, capture the corrected immutable version, reassess, obtain current reviews and bind a new assessment. PostgreSQL case/grant locks and source identity advisory locks serialize decisions, capture and revocation; unique constraints and SQL append-only guards protect history. Existing AF13 follow-up actions support owner/deadline work on declared package gaps.

Remaining engineering includes authenticated remote inventories, native workflow/migration/restore execution and receipt verification, broader source/target reconciliation contracts, operational restore/load/UAT and actual owner acceptance. Policy inputs remain actual owners/roles/access, source contracts, expected inventory and acceptance criteria, required evidence/freshness and operational support arrangements. No source ID, source title, financial balance or approval ownership is changed.
