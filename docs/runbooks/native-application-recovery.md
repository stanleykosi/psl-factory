# Native PostgreSQL and managed attachment recovery

Engineering implementation contract. Actual verification results, failures and run source fingerprints belong in BUILD-TESTS.md and docs/test-evidence/2026-10-27-application-recovery-*. It is separate from the portable case metadata adapter and its AF13 capability evidence. A successful isolated restore is not operational deployment approval.

## Scope and authority

The native archive contains the application's public PostgreSQL schema, data, sequence state, constraints, indexes, guard functions/triggers and every registered managed attachment. A single REPEATABLE READ exported snapshot is shared with pg_dump. Complete per-table SHA-256 row/content inventories and a schema/migration/application-build fingerprint bind the result. PostgreSQL sequence changes are not MVCC snapshots: this version checks positive noncycling sequence structure and observed monotonic lower bounds, allowing the native dump's later safe advancement. Source-case IDs and managed attachment IDs must match the authorised inventory exactly. Arbitrary folders and external document repositories are not included.

Schema comparison normalizes only PostgreSQL's observed round-trip distribution of unbounded varchar-to-text casts over simple status literal arrays in constraint/index definitions. Columns, functions and triggers remain exact. Changed literals, lengths, functions, predicates and extra constraints are not discarded. The five original deparser differences and actual tampering tests are retained as evidence.

Archive credentials are removed by a fixed code transformation: auth_user data is omitted from pg_dump and replaced by inactive/nonstaff/nonsuperuser principals with unusable passwords and no last login; identity_grant and django_session data are omitted. Historical policy, evidence and approval records remain history. No environment, runtime profile, secret file or source repository is swept into the archive. Restore therefore uses a separately supplied compatible application build; it does not reconstruct an external build or secret store.

Require explicit recovery.database grants on every current source case, including foreign/private cases, in addition to recovery.read/capture/operate/review actions on the control case. Recovery principals must independently appear in the deployment-owned registry. No superuser/staff or case-backup permission implies database-wide authority. The configured operator/reviewer must be actual active people with current D05 roles; reviewer independence and fresh exact authorization are mandatory. Agents require recovery.agent and can prepare or investigate; they cannot approve, run effects, execute SQL, choose paths or retrieve keys. Private results are live and not persisted in generic AgentRun/timelines.

## Provision and configure

Provision a PostgreSQL target with a distinct `(test_)?psl_recovery_...` name and no application tables or extra schemas. The application never creates, drops, resets or clears a target database. Provision three disjoint nonsymlink directories for archives, source managed attachments and recovered attachments; targets must be empty or already bound to the exact same interrupted intent. Provision pg_dump, pg_restore and psql compatible with the database major version. The first tested runtime uses an isolated synthetic database and owned temporary directories; production host/role/ACL/SSO/provider/load/security/owner evidence remains separate.

PSL_APPLICATION_RECOVERY_PROFILE selects a deployment-owned absolute JSON profile with exactly `sources`, `targets`, `key_env`, `principals`, `build_ref`, `pg_bin`. Sources name the current database, archive and managed-attachment directories and a reviewed revision. Targets name the isolated database, recovered attachment directory and revision. `key_env` maps versioned opaque key references to dedicated `PSL_RECOVERY_KEY_...` environment variables containing base64-encoded 32-byte keys. Keys and actual runtime identities have no installed defaults. Keep old versioned keys and compatible builds for their retention period. Do not commit actual profiles or keys.

Use the case's native application recovery screen, linked from Operations. Capture exact source/target/key references and register managed attachments using bounded uploads. Draft OPS.application_recovery criteria through its typed form and validate/activate through the existing configuration lifecycle. Its versioned schema covers actual purpose principals/roles, complete managed attachment IDs, archive/attachment budgets, per-command/query timeout, lease/attempt limits, minimum retention, human authorization validity, archive recovery validity and synthetic/operational scope. No financial rule, recovery SLA or real owner is invented. Capture works before these downstream criteria exist; authorization/effects hold.

Record an independent authorization, queue archive, and run `manage.py work_application_recovery --limit 1`. The archive is a native custom-format PostgreSQL dump and a closed attachment package encrypted with AES-256-GCM and a fresh random nonce. A minimal format/operation/key-reference header is authenticated associated data; the full exact immutable intent is encrypted with the package and checked against the durable job. Final sealed files publish atomically and are never overwritten. The encrypted manifest records capture/retain-until times. Automatic expiry deletion is deliberately absent: retention evidence is not a claim that storage or key lifecycle has been operationally accepted. This first bounded adapter limits complete sealed archives to128MiB, aggregate managed attachments to64MiB and individual uploads to1MiB; larger/streamed and external repository variants remain engineering work.

`manage.py inspect_application_archive --source-ref REFERENCE --operation-key SHA256` performs host/operator read-only metadata inspection with provisioned archive/key references and no database connection. The self-describing sealed archive carries its own encrypted intent, so inspection still works when the source database is unavailable. It exposes no dump, financial/HR bodies, principals, paths or credentials and explicitly confers no restoration authority. A cold-start restore workflow with fresh independent authority when the source control database is lost remains separate engineering work; do not use archived human grants or criteria as a substitute. Normal queued restore/review currently uses the source application's current human control plane.

After confirming physical archive evidence, queue restore. PostgreSQL major version, migrations, code/build and schema/data inventories must match. Source sessions/grants/credentials are never restored. Target quarantine is set before restore. Pre-data SQL, inert principals, native data, post-data constraints and the exact recovery receipt execute in one psql transaction. A failed transaction leaves no partially restored application schema. Same-intent attachment files can survive an interrupted SQL transaction and be verified on retry; unrelated files or conflicting bytes hold. The target directory has an immutable exact-intent marker and a closed content inventory.

Normal Django application, authentication and worker startup on recovery-prefixed databases always raises a quarantine error. There is no activation bypass. Offline read-only verification uses the code-owned adapter with the separately provisioned target connection. Human recovered-phase review checks exact receipt, current policy/build/runtime pins and physical rows/constraints/functions/attachments. It confers no deployment or live business authority. Fresh operational activation, principal provisioning, production identity and owner acceptance require distinct future work.

## Failure and recovery

Jobs retain immutable intents, operation keys, attempts, leases/fences and append-only human decisions. Workers reconcile actual encrypted bytes or target receipts before authority/attempt gates. A committed effect can thus be discovered after revocation/expiry without authorizing new work or resetting attempts. Target verification rechecks complete row/schema and attachment bytes despite a cached source completion. A worker process lost after native commit can resume by its original receipt.

Use Reconcile original held intent for an uncertain job. Missing/changed keys, storage/build identity, corrupted/missing archives/attachments, changed source inventory, withdrawn grants, stale authorization, expired policy/archive or exhausted new-effect budgets hold the affected action. Create a separately reviewed new plan reference for corrected intent/policy/runtime criteria; do not replace historical intents, reuse approval for a different target, overwrite a receipt, clear a failed nonempty target or renew another person's authority. Corruption tests deliberately alter owned synthetic artifacts only.

The adapter does not turn a receipt into a real-provider evaluation, production RPO/RTO result, complete external attachment backup, security/load/UAT pass, process-owner/SOP acceptance or product completion. Existing PMO/Finance/BaaS business responsibilities and all 122 source process identities remain unchanged.
