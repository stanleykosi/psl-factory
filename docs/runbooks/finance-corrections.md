# Finance invoice corrections and cash successors

This is a tested local finite implementation. Frozen billing sources interpreted through current payment-exception precedence require separate invoices, receipts, allocations and preserved correction history. Positive gross credit/debit, full terminal void and amount-only successor methods below are engineering choices requiring explicit versioned configuration. No actual legal/tax/ledger/bank equivalence is claimed.

## Staff path

Open the case Finance corrections workbench. Capture case legal note evidence as invoice_credit_note, invoice_debit_note or invoice_void_note with JSON fields document_ref, invoice_reference, kind, amount, currency, amount_basis (gross_including_tax). Unknown credit/debit amount is null and holds dependent review/application. A null full-void amount binds current adjusted face. Capture written reason and separate cash_correction evidence when configured reversal of all live allocations is requested. Capture does not require complete correction policy.

Configure D08.duplicate_correction_rules invoice-identity/v2 with correction canonical_adjustments_v1, explicit allowed_kinds/decimal_places/credit_allocation_conflict/void_allocations/void_amount/void_terminal. Configure exact D14.adjustment_correction_rule_refs financial-correction/v1 and D14.legal_document_requirements financial-legal-evidence/v1 for invoice_credit/debit/void. Use D05 decision-actions/v6 purposes invoice_correction/cash_successor and exact human role/action/preparer separation. Fixture finance-corrections.json is synthetic, never an operational default. Old identity/reversal schema versions continue working for old actions; cross-component substitution is rejected.

Review the exact current note and original obligation/adjusted face/allocation snapshot using financial_correction_review evidence. Reserve application, then run `.venv/Scripts/python manage.py work_invoices --limit 20`. Original debt changes only after an actual immutable local acceptance. Note delivery is a separate reservation/worker/recipient receipt available only after proven application. The invoice operator handles held/uncertain work; reconcile proof before retry/replacement. Credit conflicts hold or explicitly reverse all live allocations under current reversal permissions in the same transaction. No minimal-allocation selection, implicit refund, tax recomputation or new obligation. Full void is terminal in this method.

For a corrected cash amount, fully reverse the current parent lot under existing configured authority. Capture a new cash_report statement, separate cash_verification statement and cash_correction evidence/reason. It preserves original source/transaction/customer/currency/basis/received_at and corrects only amount. Review exact source/policy/assignment/parent reversal, then accept through configured successor executor/recorder authority. D14 cash_successor method successor_after_full_reversal_v1 explicitly chooses preserve_current_contract or unmatched; resetting assignment also requires current matching/reassignment permission. One accepted child per parent, multiple generations, same logical receipt/source transaction. New lot is available for explicit matching/allocation; old lots/reversals stay immutable. Supplied proof is human attestation, not authenticated bank evidence.

Build a current-day receivable snapshot. Original and adjusted face, actual open debt, active corrected cash and unallocated cash are separate; pending notes/uncertain effects/successor requests cannot silently change proven values. Older manifests become stale, historical snapshots remain untouched. Currency/basis groups do not mix. D13 payment/release authority is not inferred. Bounded investigation cites exact history and holds; it cannot approve or move money.
