# Native private file capability evidence through AF13

Status: historical engineering proposal, subsequently implemented/tested as BUILD-PRIVATE-FILE-ACCEPTANCE. See docs/runbooks/file-acceptance.md and actual RUN233 onward evidence. The proposal below is design history, not business policy. The implemented file readiness contract is described in `docs/runbooks/private-file-readiness.md`.

The connected path should take one exact independently reviewed private export/backup assessment into a fresh AF13 package, separate human meaning/expectations/acceptance decisions and a current closed metadata export. It must retain the original Finance publication/source acceptance and all historical source permissions. A transport review is not an owner decision.

Inspection shows `documents.PrivateProtectionPacket` binds a unique package to an immutable assessment/snapshot and successor chain. `documents.protection_acceptance`, its adapter and SQL guards currently require native restore evidence. `AF13.protection_owner_rules` and `AF13.protection_acceptance_rules` independently configure owner authority and acceptance criteria, avoiding the original source-policy cycle. Their current inventories and packet schemas must retain their meaning. File evidence must not be relabelled as restore proof or smuggled into general/migration/costing/Finance packages.

Before implementation, compare an explicit forward-versioned packet/criteria extension against a separate file binding using the existing AF13 services. Prefer the smallest model that makes native kind and exact lineage unambiguous at both service and SQL boundaries. Preserve applied migrations and historical restore snapshots. Do not automatically add policy components; justify any independent interface against the actual dependency graph.

The increment needs these connected contracts:

1. Closed native file evidence pins exact assessment, contract, file binding, job kind, plan/intent/manifest/storage hashes, source packet inventory and actual health/receipt observations. Require current independent transport review when capturing a new packet. Never include paths, credentials, raw manifest bodies, source quotations or financial payloads.
2. Typed versioned owner/acceptance configuration validates actual active principals, scoped D05 purposes, exact package/assessment/native-kind inventory, original private grants, independent tester/acceptor, freshness and required receipt state. Capture can precede missing owner criteria. Configured negative owner decisions must remain available when positive acceptance/current use holds. Fixtures must not appoint real people or invent criteria.
3. Reuse source-filtered server-rendered workbench forms, policy draft/validate/activate/history, bounded live investigation and typed packet preparation. Agents cannot approve, release effects or persist private evidence in generic runs. Current and historical reports/export recheck every original reference participant and source grant under ordered locks.
4. Changed receipt state, bytes, policy, owner decision or selected successor requires explicit fresh proof/package/review where relevant. Preserve history and distinguish source revocation from current-use withdrawal. No restored or accepted packet may grant business authority or recursively accept its own source.
5. Reuse AF13 comparison/follow-up/testing services with explicit synthetic classification. Extend SQL immutable/lineage/uniqueness/one-successor/anti-cycle guards. Test actual PostgreSQL services and HTTP, real temporary bytes, missing/corrupt/unavailable receipts, current/historical access, policy revision/revocation/expiry, negative decisions, duplicate capture/review, foreign-source revocation and fresh-process export. Include existing restore acceptance regression.

Acceptance is limited to selected capability evidence. Actual provider/process-owner/SOP evidence, production identities/storage/security, full application/database recovery, load/security/UAT and operational acceptance remain separate gaps. All 122 process IDs/titles and their partial coverage remain preserved. Exact inventory/principal/criteria/runtime target inputs are policy/deployment slots, not missing module implementation.
