# Proposed next: fresh-authority cold-start application recovery

Engineering design; implementation and actual test status are recorded in BUILD-STATE.md. Native PostgreSQL/managed attachment archive and isolated recovery are implemented in bounded scope; their original queued human controls require the source application database. Self-describing encrypted archives can be inspected without that database, with no restoration authority.

Build a separately authenticated durable control plane for source-unavailable restore/review. Actual fresh principals, independent human decision roles and purpose grants must be configured independently of archived user/grant/policy rows. Never bootstrap authority from archive contents or source text. Reuse typed versioned policy lifecycle, server UI, bounded investigation/preparation agents, immutable exact archive/key/build/target inventories and native isolated adapter. No actual owners, values or identities have defaults.

Authorise exact immutable intent against a fresh current decision, then reconcile receipts before effects. Execute without querying the unavailable source authority. Retain target empty/no-reset protocol, encrypted self-description, compatibility/row/schema/sequence/attachment verification, failure evidence and unconditional authentication/outbound startup quarantine. Operational activation is a separate fresh-authority decision/workflow, not a backup receipt.

Test real separately owned synthetic control/source/target databases, actual unavailable-source behaviour, two actual independent fresh principals, forged/archived/cross-purpose/expired/revoked authority, duplicate workers, SQL failure, fresh-process receipt recovery and foreign-scope privacy. Never reset existing main/test/drill databases or alter operational identities. Larger/streamed/external repositories, deployment/provider/security/load/UAT and actual owner/SOP evidence remain separate.

Implementation direction,27 October2026: deploy a separate PostgreSQL control database through config.cold_settings, with a deployment-secret-bound immutable control identity and independently provisioned users, scoped purpose grants and D05 assignments. The control application exposes only recovery/configuration endpoints. An exact deployment-registered archive fingerprint, opaque key/target references, current build and separately bound control identity enter each immutable versioned request. Archive policies, user IDs and human approvals are provenance only; none is copied into the control authority context. The adapter reads sealed bytes and connects only to the isolated target; no source connector or source authority lookup is necessary. Receipt-first reconciliation remains possible after revocation, but a new effect requires current independent approval and purpose authority. Capture and investigation precede missing dependent criteria. Recovered application startup remains unconditionally prohibited.

Test harness setup: new unique source/control databases may copy the existing test schema only after every table except migration/content-type/model-permission definitions is checked empty. No users, sessions, scoped grants, policy, reviews or business records may be copied. Each database then applies pending forward migrations and provisions its own synthetic participants. The source creates a real native archive before its new connections are disabled; the control receives fresh independent identities afterward. These are synthetic deployments with real PostgreSQL/native CLI/files, not actual owner or operational acceptance.
