# Policy scope sources — design and implementation boundary

Guide10 requires independently versioned organization/project/contract/service policy sources. The implementation now materializes an explicitly selected source as a normal target-local configuration so existing domain decision/job foreign keys remain valid. Scope source publication and its provenance are independently persisted; a scope label alone does not activate local policy.

Build explicitly selected reusable policy sources, with no inferred organization default, contract precedence or cross-case authority. Reuse existing domain envelope/schema/implementation validators and local Configuration records consumed by decisions/jobs. Keep an immutable source-scope version and lifecycle plus explicit case application/provenance; changes/revocation/expiry must identify affected derived versions and hold only their dependent transitions. A locally configured successor must be an explicit reviewed choice, never an automatic fallback.

Source and target authority must both be current and exact. Organization/bootstrap authority cannot appoint business approvers. Cross-tenant or synthetic/operational applications must fail closed. Context-dependent evidence, staff, destination, contract/stage and principal references cannot be copied as though portable: require typed authorized bindings and validate the resulting local value against the actual target case, through the same domain validators. Source text and labels cannot authorize reference rebinding or override values. Define allowable contextual bindings explicitly and version them.

Preserve historical decisions and receipt-first uncertain-effect recovery. Scope changes may invalidate new execution while existing committed receipts remain reconcilable. Coordinate with source-unavailable recovery: archived policy/scope state must never restore live authority. Inspect actual archive/reconstitution rules before adding models or resolver hooks, and add PostgreSQL scope/lifecycle/concurrency, permission, stale-source, job/receipt and recovery tests. No owner/organization/source policy values are installed during the build.

The source/application services, immutable models, independent lifecycle, target materialization, typed binding adapter, workbench and bounded investigator are implemented in apps/policy/scopes.py and related files. Verification is recorded in BUILD-TESTS.md and the policy-scopes evidence prefix. See docs/runbooks/policy-scopes.md for exact scope identity and authority semantics. Scoped sources are explicitly namespaced by an authority case; no implicit organization governance, default or inheritance has been introduced. Contract/project/service subject identities stay within their actual case. Cross-case organization application uses explicit contextual scalar bindings and actual target domain validation.

Comprehensive domain-specific pending-task/snapshot reassessment UX, broader source-specific variants and operational acceptance remain distinct engineering/evidence work. This increment must not promote any of the122 process statuses or claim only operating decisions remain.
