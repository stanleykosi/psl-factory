# Pilot evidence bindings — follow-up engineering plan

Proposed follow-up to the implemented bounded read-only preflight, not source-backed policy or test evidence. All122 process acceptance statuses remain partial. The selected preflight's current flag means matching observed heads, freshness and current access; operational acceptance remains false.

Implement in connected slices using native records and their own permission interfaces:

1. **Declared operation guard adapters.** Inspect the exact domain operation services, action grants, case-kind guards, human authority, evidence and source pins. Register explicit operation/version adapters only after comparing them with the existing policy dependency catalogue. Distinguish read-only checks from transitions that cannot safely be evaluated without constructing a domain successor. Reuse source guards; do not invoke transitions speculatively, infer approvers from technical grants or claim every declared participant action list is sufficient. Return typed ready/held/unknown findings and declared variant coverage. Start with one PMO planning/review path, then selected Finance and BaaS consumers.
2. **Worker/deployment observations.** Bind an explicitly selected deployment identity to independent web and worker build/schema observations, current quarantine status and exact artifact/receipt provenance. A filesystem source hash in the preflight process alone is insufficient. Accept bounded deployment-owned revision references and redacted check codes, never credentials, environment dumps, arbitrary paths, subprocess commands or caller-supplied URLs. Include storage/retention/monitoring findings as observed evidence, not invented owner requirements. Evaluate authority/freshness through typed current interfaces and preserve unavailable findings.
3. **Source/target/oracle evidence.** Link exact native source contracts, reviewed destination contracts, current authenticated receipt/evaluation evidence and separately verified business oracle cases. Preserve synthetic/internal/operational evidence classification and source-owned private access. Native internal inbox acceptance must remain distinct from incumbent QuickBooks acceptance, real-model validation, external channel delivery and human clock attestation. Use the existing integration/domain contracts and AF13 acceptance records instead of another readiness authority.
4. **Source-owned staff verdict.** Bind a supervised rehearsal/run to exact current selected contract/observation heads, actual human evidence and source-owned acceptance. Keep an engineering pack review, actual operational run and business approval as separate facts. Missing operational evidence must remain unknown; historical acceptance, archived accounts and restored grants cannot authorize fresh work. No preflight service acquires dispatch, retry, probe or restore tools.

Each slice needs actual PostgreSQL service, SSR, agent, adapter, private/access-before-lookup, stale/changed-head, unknown-effect and independent recovery tests. Extend native archive/restore evidence for newly introduced history models. Keep source facts, proposed guard coverage and tested runtime behavior distinct in the evidence pack and build records.

Owner values stay deferred. Build these interfaces and synthetic fixtures now; later enable only the dependent runtime operation when its actual policy/source/provider/authority evidence is supplied. This plan does not convert missing source interfaces, deployment evidence, privacy/load/security testing or UAT into owner policy slots.
