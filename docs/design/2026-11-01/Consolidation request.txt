## Architectural defaults

- Keep modular Django, Postgres, native domain services and the current server-rendered application unless inspection proves a specific approved reason to change them.
- Keep one authoritative business, human-decision, command/outbox and evidence chain. Agent SDK state, plans, browser state and vendor checkpoints are subordinate to native records. No second approval ledger, process-state database, scheduler or business-status authority.
- No new workflow engine, agent SDK, policy server, ERP or frontend framework by default. The research shortlist is conditional. Propose a dependency only with a reproduced gap, focused alternative, exact version/license review, integration/operating cost and rollback plan. Do not install an entire platform to obtain a pattern.
- Preserve original process branches, parallel work, rework, waits and cancellations. A representative PMO-to-Finance line proves shared behavior; it is not a universal linear workflow.

## The factory must be genuinely agent native

Implement the bounded observe/constrain/plan/validate/act/verify/replan loop. Agents must choose useful eligible activities and execute permitted low-risk commands, not merely produce drafts for humans to click through. They remain inside the versioned process envelope; deterministic services enforce authority, arithmetic, invariants, concurrency, evidence and acceptance.

Map the reusable ACT01–ACT15 catalogue to current services and actual process IDs. These are proposed activity identifiers, not business process IDs and not fifteen mandatory new microservices. For each activity record trigger, typed inputs, preconditions, context/evidence freshness, role, permitted tools/actions, outputs, autonomy gate, handoff, shared budget, retry owner, failure route, postconditions and tests. Reuse capability profiles across 108 processes rather than create 108 unbounded agents.

Persist logical activity identity separately from attempt, parent-child linkage, plan revision and observed action results. Recover from durable facts, not chat history. Enforce shared budget reservations across delegates/retries, bounded recursion, no-progress detection, scope narrowing and cancellation. Preserve effect_unknown and reconcile before any duplicate-capable retry. Model output validity or agreement does not establish business truth. Finance services calculate amounts; agents cannot self-approve, publish policy changes or broaden tools.

Implement deterministic activity/action-to-policy/version-to-owner-to-approval-role-to-active-principal routing. ACT10 is a service resolver, not an LLM choosing authority. Handle scope, effective dates, amount/currency/risk, approved FX conventions, SoD, delegation, absence, sequential/parallel/quorum/veto, expiry, rejection, revocation and material changes. Explain routing using evaluated service facts. Missing or conflicting ownership blocks the consequential action and routes to the configured governance resolver; if that resolver is also absent, expose owner_needed and stop the dependent action rather than inventing an owner. Unknown use cases enter the governed extension route.

## Make the operator console the main product surface

Extend existing UI and routes rather than deliver a KPI dashboard or detached prototype. Build work queues, stable case detail, a decision panel, observable agent activity, evidence/version inspection, exceptions and receipts/verification. Preserve filter and selected-case context. Show owner, blocker, next action, current step and evidence as-of time immediately. Metrics are secondary and disclose coverage.

All buttons derive from backend capability checks. UI, agents and workflows use the same command authority. Show loading, empty, stale, denied, conflict, waiting, retry requested, effect unknown and verified states accurately. A queued action, successful agent run or receipt acknowledgment must not become business completion without postcondition checks. Expose readable tool/evidence history, not hidden chain-of-thought or raw logs as the only explanation.

## Acceptance and reporting

Run relevant baseline and targeted tests, then the broader appropriate suite where feasible. Retain exact commands, environment, revision/manifest, results, assertions and evidence paths. Include negative and concurrency tests, not only happy paths:

- Racing claims, duplicate commands/callbacks and payload collisions.
- Stale evidence or approval, changed destination/amount, revoked authority and in-flight dispatch races.
